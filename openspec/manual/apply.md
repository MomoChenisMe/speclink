# 實作：完成任務

這一站把提案裡的任務一項一項做完、勾掉。你會用到 `/speclink-apply` 技能，或直接下 `speclink task done` 指令。變更第一次有任務被勾掉時，就自動從「提案中」進到「進行中」。

> [!NOTE]
> apply 技能本身的內文行為（怎麼讀任務、怎麼寫碼）規格未載。本頁只寫規格有寫的部分：任務行的格式、勾選與取消勾選的指令、手動任務的規則、開工標記，以及做完之後的交棒。

## 進入這一站之前

apply 技能開始前，會先跑一段前置檢查。如果這個變更閒置了一陣子，前置檢查會提出「漂移警告」。看到警告就先走 [續作與需求變更](drift-ingest.md)，再回來實作。

## 任務長什麼樣

任務都寫在變更目錄的 tasks.md，每一行是一個 checkbox。有兩種東西會跟著任務行：

- **手動任務標記 `[M]`**：緊接在 checkbox 後面，表示這件事要你親手做、agent 做不到。不限於測試，人工驗收、去外部服務建帳號、放金鑰都算。
- **任務身分註解**：引擎產出 tasks.md 時，會在每一行的行尾放一個看不見的註解，裡面是這個任務的固定 ID（以 `tsk_` 開頭）。桌面 app 與清單顯示時會把它藏起來。任務重排、改描述、增刪其他任務，都不會改變這個 ID。

`[M]` 的位置一定要緊接 checkbox，checkbox 後面恰好一個空格。寫成「編號在前」（例如 `- [ ] 6.2 [M] 手動驗收`）引擎不認，變更驗證會報 error，並用正誤例告訴你怎麼改。

舊檔裡的 `[P]` 前綴引擎會忽略，只是不再有任何意思。

## 勾掉一個任務

```
speclink task done <任務序號或 ID> --change <變更名>
```

任務可以用兩種方式指定：清單上的序號（純數字），或行尾的 `tsk_` ID。序號會隨重排改變，ID 不會。tasks.md 裡如果出現兩行同一個 ID，指令會拒絕並點名重複的 ID，不會亂選一個。

勾掉任務時會發生三件事：

1. tasks.md 那一行變成已勾。如果那一行還沒有 ID，引擎只在這一行補上 ID，其他行一個字都不動。
2. 如果這個變更還沒開工，引擎會在同一次操作裡蓋開工章：記下日期，git 身分可得時記下是誰。已經開工的變更保留第一次的章。
3. 如果這次有新的髒檔（之前的任務沒認領過的），引擎把它們記成這個任務的證據：任務 ID、誰做的、哪個 repo、當時的 commit、動了哪些檔案、什麼時候。證據寫在變更目錄的 .evidence.json，跟著變更一起封存或廢棄。沒有新髒檔就不寫。

會失敗的情況，全部不寫任何檔案：

- 任務已經勾過：指令以「already done」訊息結束。
- 變更沒有 tasks.md：指令以「tasks.md not found」訊息結束。
- 序號超出範圍或 ID 查無：報錯，形狀與序號超界一致。
- 變更的 .openspec.yaml 壞掉解析不了：報錯並指出檔案位置與原因。引擎不會把壞檔當成「未開工」。

## 取消勾選

```
speclink task undone <任務序號或 ID> --change <變更名>
```

這只是把 `[x]` 翻回 `[ ]`。它不會動開工章、不會寫證據、不會補 ID。任務本來就沒勾、任務不存在、tasks.md 不存在時都會報錯，且不寫任何檔案。

## 手動任務怎麼處理

`[M]` 任務由你親自執行、親自勾選。apply 技能守兩條規則：

- 寫碼任務全部勾完時，技能就回報「實作完成」，並把還沒勾的手動任務列給你。技能不會替你勾。
- 某個寫碼任務要靠一個還沒勾的手動任務才能做（例如外部服務的帳號還沒建），技能會停下來，請你先完成那個手動任務。技能不會代勾、也不會繞過。

「寫碼任務全部完成」是後面品質關卡和封存共用的判斷標準。零任務的變更、或全部都是 `[M]` 的變更，也算成立。手動任務在桌面看板上怎麼呈現，見 [看板與任務](desktop-board.md)。

## 開工標記

勾任務會自動蓋開工章。你也可以手動蓋：

```
speclink in-progress add <變更名>
```

這個指令靜默完成、重複執行不會改章。名字打錯也靜默成功、不寫檔，這是刻意保留的舊行為。

誤開工的變更可以退回提案中：

```
speclink in-progress remove <變更名>
```

只有「零工作痕跡」才會成功：沒有任何已勾任務，也沒有任何 touched 檔案記錄。否則指令拒絕，並列出已勾任務數與 touched 檔案清單。已勾的任務可以先取消勾選再重試；touched 記錄要你或 agent 自己判斷怎麼處理。這個指令沒有強制旗標。名字打錯會明確報錯，與 add 的靜默刻意不對稱。

## 放棄一個變更

```
speclink discard <變更名>
```

這會整棵刪掉變更目錄與它的 touched 記錄，並把來源討論解鏈。有動工痕跡（已蓋開工章、或任何一個任務已勾）時會拒絕，要帶 `--force` 才放行。.openspec.yaml 壞掉時就算帶 `--force` 也拒絕，修好再刪。remote 模式下 CLI 的 discard 會報「不支援」。變更的各種狀態見 [認識資料：變更、討論與規格](data-layout.md)。

## 需求中途變更

實作到一半需求變了，走 ingest，見 [續作與需求變更](drift-ingest.md)。另一種情況是：這個變更曾反映某份討論，之後那份討論又重新下了結論。這時變更會帶「待重新反映」記號，`speclink analyze` 會出一條資訊性提示，告訴你要重新 ingest。

## remote 模式的差異

remote 模式下每個變更恰好屬於一個 repo。建立變更時歸屬到你所在的 repo（單 repo 的專案自動預設），清單也只列這個 repo 的變更。需求跨 repo 時，拆成多個變更，每個各屬一個 repo。

## 做完之後

apply 技能結尾只給建議、不會自動叫下一個技能：

| 結束狀態 | 建議下一步 |
| --- | --- |
| 全部任務勾完 | 跑品質關卡（審查、驗證或兩站合跑），或直接封存。直接封存可走 `/speclink-archive`，或用 `/speclink-commit` 的「先封存再一起提交」一步到位 |
| 只剩手動任務 | 品質關卡可以先跑；封存等你做完手動任務並勾選 |
| 需求中途變更 | `/speclink-ingest` |
| 在 worktree 裡實作 | 在 worktree 內提交，再走 [平行實作與合回](worktree.md) |

品質關卡的說明見 [品質關卡總覽](quality-stations.md)，封存見 [封存](archive.md)。
