# 溯源：一個功能怎麼來的

想知道某個功能怎麼來的、為什麼這樣設計，有兩個入口。`speclink trace <capability>` 印出這個能力的演進鏈。`/speclink-trace` 技能接受你的自然語言問題，讀完鏈上的資料後，用敘事的方式回答，每項陳述附來源路徑。

## 指令：speclink trace

```
speclink trace <capability>
```

輸出是一棵縮排樹，內容有三段：

1. **動過這個能力的封存變更。** 只算已封存、且封存目錄含這個能力的 delta 的變更，依封存日期由舊到新排。每個變更帶封存目錄名與來源討論的 slug，沒有來源討論就標示無。進行中的變更不會出現。
2. **來源討論與它轉出的變更。** 討論項下列出它轉出的全部變更，以及每個變更觸及的能力名。
3. **每條需求現在歸屬哪個變更。** 取自正典規格裡每條 Requirement 的溯源註記。

每個入鏈的變更還會列出逐任務的觸及檔案清單。清單來自封存目錄裡的證據檔（.evidence.json）。封存目錄沒有這個檔時，輸出標示無記錄，指令照常成功、沒有警告。規格註記裡的舊程式碼檔案清單不會被讀取或輸出。

加 `--no-color` 只省略色碼，內容不變。

### 找不到能力時

能力沒有正典規格時，指令失敗。錯誤訊息報該能力不存在，並列出至多三筆近似的既有能力名。沒有近似名時只報不存在。

### 資料有缺時照常輸出

鏈中某個環節缺欄位或指到不存在的東西，不會讓整個輸出失敗：

- 需求的歸屬指向找不到封存目錄的變更：歸屬照列，變更清單裡缺它的明細。
- 變更沒記錄來源討論：來源討論標示無。
- 來源討論的檔案不存在：討論清單裡沒有它，變更那一行仍列出它的 slug。

## 技能：/speclink-trace

用自然語言問，例如「這個功能怎麼來的？」。技能依序做：

1. 用正典規格清單比對出你問的是哪個能力。
2. 呼叫 `speclink trace` 取得演進鏈。
3. 讀來源討論的結論與輪次，以及各變更提案的動機段落。
4. 依證據取得觸及的檔案。
5. 最後閱讀現行程式碼，確認現在的行為。

答案是敘事形式，包含四樣東西：決策內容與理由、被否決的替代方案、一起演進的關聯能力，以及每項陳述的來源路徑。關於「現在的行為」的陳述，一律以現行程式碼為準。證據與提交記錄只當歷史快照引用。

> [!NOTE]
> 資料不齊時技能會自己補查，不會要求你補資料。某個變更沒有證據檔時，技能改用版本控制的提交記錄反查觸及檔案（依提交訊息帶變更名的慣例），查不到就以討論與提案內容作答。你問的功能對不上任何規格時，技能改以程式碼庫考古作答：關鍵字檢索、git log 與 git blame 追引入的提交、以提交訊息當決策線索。格式與命中規格時相同。這兩種補查在答案裡不會被點出，也不會出現「降級」「資料不完整」這類字眼。

技能隨 `speclink init` 與 `speclink update` 發佈到各工具的技能目錄。見 [建立工作區與指令檔](init-workspace.md)。
