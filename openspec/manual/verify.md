# 驗證站

驗證站看實作有沒有符合變更的產物：規格寫的都做了嗎、做對了嗎、彼此一致嗎。技能是 `/speclink-verify`，底下的工單指令是 `speclink verify ...`。審查面怎麼決定、章怎麼失效，見 [品質關卡總覽](quality-stations.md)。工藝品質的檢查在 [審查站](review.md)。

## 三個維度

驗證從三個維度檢查：Completeness（完整）、Correctness（正確）、Coherence（一致）。發現分 CRITICAL、WARNING、SUGGESTION 三級。

## 技能怎麼跑

檢查由一個分支 agent 執行，結束時依寫碼任務完成度分流：

- **寫碼任務全部完成**（含只剩 `[M]` 手動任務）：先用 `speclink verify scope` 取得凍結的差異，再用 `speclink verify add-round` 把這一輪寫進工單，報告裡告訴你工單已建立與輪次。只剩手動任務時，報告一併點名剩餘的手動任務。
- **寫碼任務還沒完成**：技能只給對話式的進度盤點，列出未完成的任務。它不算範圍、不落工單，變更目錄不會出現 verify.md。引擎那一側也守同一條：寫碼任務沒全完成時，add-round 直接拒絕。

沒有工單時執行唯一一次 discovery：讀全部產物，以凍結的差異加上判斷所需的呼叫端與測試作為證據，完整跑三個維度。程式碼的檢查面限定在凍結的差異段落，不掃描工作區其他既存問題。

已有工單時執行 validation：只把上一輪未解的發現、已接受清單、修正差異與必要脈絡交給分支。逐筆判定已解或未解，只回報修正本身直接引入的退化。未解的發現以原本的嚴重度、路徑與文字寫回新一輪，不改寫文字假裝進步。已解的移除。不重掃整個變更、不重掃發現所在的整個檔案、不新增沒改到區域的問題。

## 處置與三選項

主線接手分支的報告後做處置分類。必修＝CRITICAL 與 WARNING；可裁事項一律以 SUGGESTION 記錄，不進接受機制，不擋章。修正一律回主線依專案 TDD 慣例做，分支不改任何檔案。

第一輪有必修時問三選項：修正後重驗、接受現狀蓋章（`speclink verify stamp --accept`）、先不蓋章結束。零發現或只有 SUGGESTION 時：單站直接呼叫就記錄這一輪並蓋乾淨章；在 `/speclink-quality` 合跑時改成「先不蓋章」結束，章留到合跑的收尾補蓋。

收尾補蓋的呼叫在入口就分流：最後一輪必修已清空、凍結點之後內容沒動，就跳過檢查直接蓋章，不多落一輪空輪；內容有動，就在同一次呼叫裡先跑一輪 validation，必修清空後再蓋。不會對沒驗過的變動直接補章。

每輪 validation 寫入工單後的收尾規則：

| 情況 | 結果 |
| --- | --- |
| 必修清空，且沒有已接受的必修 | 執行 `speclink verify stamp`，結果 passed clean。殘留的 SUGGESTION 不擋章 |
| 必修清空，但有已接受的必修 | 等你明示執行 `speclink verify stamp --accept`，結果 passed with reservations |
| 必修數減少但沒清空 | 再問一次三選項 |
| 必修數沒有減少 | 記錄這一輪後以 failed 結束，工單留著、不蓋章、不自動重試 |

必修數減少只決定能不能繼續，不是品質分數。技能沒有固定的最大輪數。沒有互動選單工具的環境，技能用純文字問並等你回覆。

## 續輪遇到重大新問題

規則與審查站相同：與修正無關的新問題不進目前的發現，也不重開第一輪。只有同時有現實觸發路徑、有重現方式或失敗測試或明確不變量破壞、且影響安全、資料損失或錯誤行為時，技能以 scope changed／failed 結束本站，工單留著、不蓋章，建議另開一輪或衍生一個變更。

舊格式工單有發現、卻沒有對應的快照時，技能無法精確重建修正差異，會保留工單，等你明示放棄後再重跑第一輪。

## 工單指令

| 指令 | 做什麼 |
| --- | --- |
| `speclink verify scope <變更名>` | 算出並凍結審查面。無工單時是第一輪，有工單時是續輪 |
| `speclink verify add-round <變更名> --stdin` | 從標準輸入讀一輪內容，追加到工單。寫碼任務沒全完成時拒絕 |
| `speclink verify show <變更名>` | 印出工單原文。無工單時報錯「該 change 無驗證工單」 |
| `speclink verify stamp <變更名> [--accept]` | 蓋章。條件與審查站同一組 |
| `speclink verify discard <變更名>` | 刪掉工單，不寫任何章，並清掉本站的快照。無工單時報錯 |

scope 停下要你決定範圍的情況與審查站一樣：基準點不可信、開工前就髒的檔案、與另一個進行中變更重疊、挑選時內容漂移、快照缺失。這時不會建立快照，也不會退回整檔檢查。驗證站與審查站的快照分開存；`verify stamp` 或 `verify discard` 只清驗證站的快照，審查站的快照與 apply 的基準點不動。

add-round 會拒絕的內容與審查站相同：缺少範圍行；階段與指紋兩欄只出現其中一個；第二個 discovery；變更不存在。拒絕時工單零寫入。

stamp 通過時，同一次原子寫入把驗證章寫進變更的 .openspec.yaml 並刪掉 verify.md，然後清掉驗證站的快照。章裡記蓋章時的任務總數（含 `[M]`）與審查面每個檔案的內容指紋。失效規則與審查站同構：任務總數改變、任何寫碼任務未完成、任何審查面檔案內容不符，章就失效；補勾 `[M]` 與行尾差異不影響。

## 封存時的處置

變更還有 verify.md 時，`speclink archive` 預設拒絕，列出三種處置：`verify stamp`、`verify discard`、或帶 `--carry-verify` 把工單一起搬進封存區。審查與驗證兩張工單同時在時，並列兩組處置，`--carry-review` 與 `--carry-verify` 可以同時帶。詳見 [封存](archive.md)。

## remote 模式

工單走 store 讀寫。離線、版本衝突、認證失效時，指令以非零結束並在 stderr 說明；離線時追加輪次，遠端與本機投影都不會變。`verify scope` 仍在你本機的 checkout 上算，與 apply 的基準點、touched 記錄、驗證快照共用；server 不會收到差異或快照。本機的 git 錯誤不會被包裝成版本衝突。

## 蓋章之後

蓋章之後往哪走，見 [工作流總覽](workflow-overview.md) 的交棒表；封存的規則見 [封存](archive.md)。
