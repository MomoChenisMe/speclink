# 審查站

審查站看實作的工藝品質：專案慣例有沒有守、有沒有 code smell、有沒有 bug。它不裁決「有沒有符合規格」，那是 [驗證站](verify.md) 的事。技能是 `/speclink-review`，底下的工單指令是 `speclink review ...`。審查面怎麼決定、章怎麼失效，見 [品質關卡總覽](quality-stations.md)。

## 技能怎麼跑

1. 選定要審的變更。
2. 檢查寫碼任務完成度。還有寫碼任務沒完成就停止，不算範圍、不派子代理（主對話另外派出、只讀不改檔的助手）、不寫工單。只剩 `[M]` 手動任務時繼續，結果會點名剩餘的手動任務，並說明「章可以先蓋、手動任務完成後再封存」。
3. 開審前用 `speclink workflow-config show` 讀專案的審查規則（見下一節）。讀不到（例如 config.yaml 無法解析）就原樣回報錯誤並停止，不算範圍、不派子代理、不寫工單。
4. 用 `speclink review scope` 取得凍結的差異。沒有工單時是首輪；有工單時是複驗。首輪範圍有歧義時，技能等你提供可信的基準、明確的段落挑選、或改用隔離的 worktree，不會拿整個檔案代替。
5. 讀變更的產物（提案、設計、規格、任務）當判斷脈絡。產物很薄時，子代理只憑程式碼與測試判斷，不編需求。
6. 依輪次分流：首輪完整檢查，複驗只驗收修正。
7. 並列呈現結果（開頭先印一行套用的規則），並對每筆發現給處置分類。
8. 用 `speclink review add-round` 把這一輪寫進工單。首輪會一併記下套用的規則。

## 專案審查規則

`openspec/config.yaml` 的 review 區塊叫審查規則，有兩部分：預設清單模式，以及依嚴重度分成 critical、warning、suggestion 三個清單的專案規則。怎麼設定見 [工作流政策與設定](policy-config.md)。

- **預設清單模式**：extend（沒設定時就是它）照常檢查下一節的 12 條 code smell，再加上專案規則；replace 不帶這 12 條，不檢查、也不入單。
- **只進 Standards 軸**：首輪時，專案規則依嚴重度分組、以原文交給 Standards 子代理；Correctness 子代理不會收到。
- **嚴重度由清單決定**：違反哪個清單的規則，發現就是那一級（critical 對 CRITICAL、warning 對 WARNING、suggestion 對 SUGGESTION），子代理與主線都不能自行升降級。發現的描述會原文引用被違反的規則，其餘部分照工作區的語言寫。
- **專案規則優先**：專案規則與 repo 文件化的標準衝突時，專案規則勝出。
- **複驗不因規則新增發現**：首輪之後才加的規則，不會讓複驗冒出新發現。
- 三個清單都空、模式為 extend 時，審查行為與完全沒寫 review 區塊相同。

語言設為 tw 時，一筆違反 critical 規則的發現在工單裡長這樣：

```
- [CRITICAL] crates/x/src/db.rs — Standards: 違反專案審查規則「所有 SQL 一律用參數化查詢，不得用字串拼接」：第 42 行以 format! 拼接 WHERE 子句
```

### 呈現開頭的那一行

每次並列呈現結果，技能會先印一行，寫明 Standards 軸套用的預設清單模式與三個清單的條數；replace 而三個清單都空時，寫明 Standards 軸只依 repo 文件審查。這行用工作區的語言寫（沒設語言就用英文），extend、replace 與嚴重度標籤維持英文。它只出現在呈現中，不寫進工單。

| 語言 | 設定 | 開頭行 |
| --- | --- | --- |
| tw | extend，2／1／1 條 | 審查規則：預設 12 條（extend）＋專案規則 CRITICAL 2、WARNING 1、SUGGESTION 1 |
| ja | extend，清單皆空 | 審査ルール：既定の 12 項目（extend）、プロジェクトルールなし |
| en | replace，清單皆空 | Review rules: replace, no project rules — the Standards axis judges against repo documents only |
| 未設定 | replace，critical 1 條 | Review rules: replace, project rules CRITICAL 1, WARNING 0, SUGGESTION 0 |

### 首輪工單記下套用的規則

首輪寫進工單時，技能在差異指紋那一行之後、範圍行之前多寫幾行：先一行標明預設清單模式（沒設定時寫 extend），再依 critical、warning、suggestion 的順序，每條專案規則一行，清單內保持原順序。例如：

```
**Rules**: extend
**Rule**: CRITICAL 所有 SQL 一律用參數化查詢，不得用字串拼接
**Rule**: SUGGESTION 偏好以提早返回取代深層巢狀
```

- 記下的就是 Standards 子代理實際收到的規則，記錄前不會重讀設定。
- 規則原文有換行時，技能把換行連同前後空白換成一個空白，寫成一行。
- 這幾行不隨語言改變，規則原文照設定裡的文字寫，不翻譯。
- 沒有 review 區塊時只寫一行 `**Rules**: extend`。
- 複驗不寫這幾行。

這和上面「呈現開頭的那一行」是兩件事：開頭那行只出現在對話裡，這幾行才進工單。

## 首輪：兩軸平行檢查

同一份凍結差異交給兩個只讀的子代理平行看，各自用 400 字內回報，發現分 CRITICAL、WARNING、SUGGESTION 三級：

- **Standards**：專案慣例文件、專案審查規則，加上 code smell 基準（模式為 replace 時不帶基準）。專案文件優先：專案明文允許的做法不報。smell 一律是「possible X」的提示，永遠不當硬性違規；工具已經自動強制的規則不報。基準的 12 條 smell 名稱維持英文原文：Mysterious Name、Duplicated Code、Feature Envy、Data Clumps、Primitive Obsession、Repeated Switches、Shotgun Surgery、Divergent Change、Speculative Generality、Message Chains、Middle Man、Refused Bequest。
- **Correctness**：找 bug。

兩軸只看變更的差異段落，加上判斷所需的呼叫端與測試。兩份報告原樣並列，不合併、不重排。

發現的描述用工作區設定的語言寫；工作區沒設語言就用英文。嚴重度標籤、`Standards:`／`Correctness:` 前綴、檔案路徑維持英文。

## 子代理簡報的查找紀律

為了讓子代理查得快、不亂翻，技能派出的簡報守這幾條：

- 凍結差異在 25 KB 以內就直接貼進簡報；超過時只給檔案路徑與每段差異的行號範圍。
- 自動產生的檔案（golden snapshot、assets.lock、由 `speclink update` 再生的技能檔）只給路徑，子代理對它們最多搜尋一次。
- 子代理不整份讀大檔（只按行號範圍讀），也不做沒有目標的遞迴搜尋，只搜簡報列出的函式名、型別名與檔案。
- 首輪不限工具呼叫次數；複驗限 5 次。
- 簡報結尾要求「沒查完就直說，不要猜」。子代理回報沒查完的部分，會原樣列進結果，不當成已確認沒問題，由你決定要不要補查。
- 發現指向凍結差異以外的呼叫端時，要錨在差異內被呼叫的那個檔案，路徑不帶行號。工單會拒收不合這條的路徑，見 [品質關卡總覽](quality-stations.md)。

在 `/speclink-quality` 合跑時，簡報照同樣的規則組成，由合跑技能和驗證站的簡報在同一則訊息裡派出。

## 處置分類與三選項

技能在問你之前，先把每筆發現分成兩類：

- **必修**：CRITICAL 級；Correctness 軸判定有現實觸發路徑的 bug（含 WARNING 級）；專案明文標準的明確違反；違反專案審查規則 critical 或 warning 清單的發現。
- **可裁**：「possible X」的 smell 判斷、違反 suggestion 清單的發現，以及其他 SUGGESTION 級事項，每筆附一行修繕成本與效益的理由。可裁事項一律以 SUGGESTION 級記錄，不會用 WARNING。

有必修時，技能問你三選項，推薦「修正後重審」並列出必修清單：

- 修正後重審。
- 接受現狀蓋章。
- 先不蓋章。

只有可裁項時不問。單站直接呼叫時，技能記錄這一輪後直接蓋乾淨章。在 `/speclink-quality` 合跑時，改成「先不蓋章」離場，章留到合跑的收尾補蓋。

沒有互動選單工具的環境，技能用純文字問並等你回覆。

### 接受 CRITICAL 要逐條確認

不管你走哪一條路接受必修（修正後重審時挑幾筆不修、選「接受現狀蓋章」、或照推薦明示帶 `--accept` 蓋章），只要接受的項目裡有 CRITICAL，技能會先逐條列出這些 CRITICAL 的原文，請你明確確認一次，確認後才記下 `(accepted)` 或帶 `--accept` 蓋章。你不確認，就回到原本的選擇，不記 `(accepted)`、不蓋章，工單不變。只接受 WARNING 時不多問。

這一步不改引擎的蓋章規則：CRITICAL 與 WARNING 一樣擋乾淨章、一樣能用 `--accept` 放行。

在 `/speclink-quality` 合跑時，合跑技能如果已經在停下處逐條確認過、呼叫本站時明示「CRITICAL 已逐條確認」，本站就不再問；轉交時漏列的 CRITICAL，本站只補問漏的那幾筆。

## 修正與複驗

修正一律由主線依專案的 TDD 慣例做，子代理不改檔案。

### 修復迴圈的驗證門

修正完、派下一輪子代理之前，技能先跑建置與受影響範圍的測試，全綠才進下一輪；沒過就先修到全綠。受影響範圍依序判定：

1. 修正改到的檔案落在某個任務說明列出的路徑內：跑那個任務說明寫的驗證指令。
2. 任務沒涵蓋的檔案：依專案文件寫的測試政策（CLAUDE.md、AGENTS.md 或 config.yaml 的產出規則）挑測試。
3. 專案完全沒寫測試政策：跑 repo 慣例的完整測試。

建置一定照跑，不因範圍判定而略過。結果會列出這次跑了哪些測試指令、略過哪些範圍，並註明略過的部分交給 CI 守門。

> [!NOTE]
> 例如修正只改了任務 2.1 列出的檔案，而任務 2.1 寫明用 `cargo test -p speclink-core` 驗證，技能就只跑建置與這一條指令，不跑完整測試，並在結果裡列出略過的其他 package。

修正動到產物（規格、design、tasks）時分三種情況：

- **只改程式碼讓它符合規格**：不動產物。
- **規格字面要修、意圖不變**：主線直接改產物，`speclink validate <變更名>` 通過後才進下一輪。結果會列出改了哪幾段，下一輪的簡報附上改過的段落原文。複驗的差異不含規格目錄，不附上的話，下一輪看不到這個修正。
- **意圖或範圍改變**（修正需要新增任務，或改變某條 Requirement 的意圖）：技能以「範圍改變」結束本站，工單留著、不蓋章，建議先跑 `/speclink-ingest` 再重跑。技能不會在迴圈裡自己新增或退回任務。

### 複驗只驗收修正

複驗只做兩件事：逐筆判定上一輪的發現已解或未解，以及回報修正本身直接引入的問題。未解的發現以原文寫進新一輪；已解的移除；沒改到的區域裡的新 smell、既存問題都不加進來。修正差異裡如果有「相鄰」段落（沒被點名但被改到的檔案），子代理會逐段確認確實屬於這次修正，不是的話當作退化回報。範圍外的變動只轉知你，不進工單。

每輪之後，技能比較「未接受的必修數」與上一輪：

| 情況 | 結果 |
| --- | --- |
| 必修清空，且沒有已接受的必修 | 執行 `speclink review stamp`，結果 passed clean。殘留的 SUGGESTION 不擋章 |
| 必修清空，但有已接受的必修 | 推薦你明示執行 `speclink review stamp --accept`，結果 passed with reservations |
| 必修數減少但沒清空 | 再問一次三選項 |
| 必修數沒有減少 | 記錄這一輪後以 failed 結束，工單留著、不蓋章、不自動重試 |

必修數減少只決定能不能繼續，不是品質分數。技能沒有固定的最大輪數。

## 已接受的事項

你裁定「接受、不修」的必修發現，複驗會兩軌處理：子代理收到不重報清單，不再報同一件事；工單新一輪照樣列出這些事項，行末加 `(accepted)` 標記，讓最後一輪忠實反映保留事項。換一個 session 接手時，技能從標記行重建不重報清單。接受機制只適用必修級；SUGGESTION 不需接受。

## 複驗遇到重大新問題

複驗偶然看到與修正無關的新問題時，技能不會把它塞進目前的發現，也不會重開首輪。只有同時滿足「有現實觸發路徑」、「有重現方式、失敗測試或明確不變量破壞」、「影響安全、資料損失或錯誤行為」時，技能以 scope changed／failed 結束本站，工單留著、不蓋章，建議另開一輪或衍生一個變更。證據不足的事項只列為後續提示。

## 蓋章後查歷史紀錄

蓋章會把完整審查工單另存到變更的 `checks/review/`，檔名以審查開始的 UTC 時間加紀錄 ID 組成；索引記錄其相對路徑。活動 `review.md` 會被移除，但完成紀錄保留在提案內，之後重跑審查或再次蓋章也不覆蓋舊紀錄。使用 `speclink review history CHANGE_NAME` 列出歷史，加入 `--id RECORD_ID` 查看指定紀錄；已封存的變更也可查。

## 工單指令

| 指令 | 做什麼 |
| --- | --- |
| `speclink review add-round <變更名> --stdin` | 從標準輸入讀一輪內容，追加到工單。工單不存在就建立 |
| `speclink review show <變更名>` | 印出工單原文，首輪的規則記錄隨原文出現。無工單時報錯「該 change 無審查工單」 |
| `speclink review stamp <變更名> [--accept]` | 蓋章。條件與效果見品質關卡總覽 |
| `speclink review discard <變更名>` | 刪掉工單，不寫任何章。無工單時報錯 |

add-round 會拒絕的內容：

- 缺少範圍行。
- 輪次階段與差異指紋兩欄只出現其中一個。
- 第二個首輪（首輪之後只能是複驗）。
- 變更不存在。
- 規則記錄格式不對：模式不是 extend 或 replace（區分大小寫）、一輪有兩行模式、有規則行卻沒有模式行、嚴重度不是三級之一、規則行沒有原文。
- 規則記錄出現在首輪以外的輪，包括複驗與沒有階段標記的舊格式輪。
- 發現的路徑帶行號，或不在工單範圍內（規則見 [品質關卡總覽](quality-stations.md)）。路徑問題和變更不存在、輪次順序不對同時發生時，先報路徑問題。

拒絕時工單零寫入，stderr 點名問題。舊格式的工單（沒有階段與指紋）仍可讀可追加。

stamp 會拒絕的情況：寫碼任務沒全完成（列出計數）；最後一輪還有未解必修且沒帶 `--accept`（提示 `--accept` 或先修正重審）。最後一輪只剩 SUGGESTION 時照常蓋章。

蓋章後工單刪除，fs 模式只剩 git 歷史，remote 模式不可回讀。

## 兩種特殊收尾

如果先前蓋章因為別的守門失敗而留下了零發現的工單，守門恢復後技能直接重試蓋章，不重審。舊格式工單有發現、卻沒有對應的快照時，技能無法精確重建修正差異，會保留工單，等你明示放棄後再重跑首輪。

蓋章之後往哪走，見 [工作流總覽](workflow-overview.md) 的交棒表；封存的規則見 [封存](archive.md)。

**出處**：`review-skill`、`review-station`
