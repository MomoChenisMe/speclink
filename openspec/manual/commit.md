# 提交單一變更的檔案

工作樹裡常常混著好幾個變更的改動。`/speclink-commit` 只挑某一個變更的檔案做一次 git 提交，不會把無關的檔案順手掃進去。它是隨叫隨用的工具技能，不是每個變更必經的一站。

> [!NOTE]
> 技能怎麼判斷哪些檔案屬於這個變更，規格未載。本頁只寫規格有寫的部分：確認閘門的規則。

## 所見即所簽

技能守一條原則：你看到的清單，就是最後簽下去的那一份。流程如下。

1. 技能先生成 commit 訊息。
2. 技能把 commit 計畫（分組後的檔案清單）與 commit 訊息，以可見文字一次輸出在對話裡。
3. 技能才向你提出確認問題。問題只會指涉上面已經輸出過的內容，不會提到你沒看過的東西。
4. 你確認後，技能才暫存並提交。

沒有互動確認工具的環境，技能以純文字提出同樣的問題並等你回覆；一樣是先輸出計畫與訊息，再問。

## 先封存再一起提交

確認時有一個選項是「Archive first, then commit together」。選了它，技能先跑封存子流程。封存完成後，技能重新輸出更新後的 commit 計畫，以及含「Archived: yes」的 commit 訊息，再問你一次確認。第二次確認通過，才真正暫存與提交。封存本身的規則見 [封存](archive.md)。

這個子流程本身就是一個封存入口，所以它帶著與 archive 技能相同的順序提示與收尾提醒：

- **封存前**：技能先執行 `speclink plan --json`，看三件事。
  - 目標封存要等別的變更（兩者動到同名 requirement）時，提醒「plan 建議先封存 <那些變更>；它們封存後，重讀本 change 對同名 requirement 的區塊、對照正式規格重寫（走 ingest）再封存 <這個變更>」。
  - 目標與別的變更衝突（都新增或改名成同一個名稱，或都移除或改名掉同一個名稱）時，提醒要先改掉其中一邊。
  - 目標的宣告前置還沒封存時，另提「宣告前置 <名稱> 尚未封存」。

  三者都只是建議，不擋你；你確認後照常封存。技能不會叫你「跑 drift 就好」。三者都沒有、目標不在 plan 裡、或 plan 失敗時，不提順序。技能同時記下「封存要等目標」的其他變更。
- **封存後**：技能提醒三件事。
  - 工作區有 `openspec/manual/` 時，提醒可跑 `/speclink-manual` 檢查手冊是否過期（只看目錄存不存在）。
  - 封存前記下的變更不是空的時，提醒它們先對照正式規格重寫（走 ingest）再封存。這一條不會另外問你問題，也不會代跑 ingest。
  - 技能再執行一次 `speclink plan --json`，算得出下一個可開工的變更時，提一句「plan 的下一個可開工：<變更名>，執行 /speclink-apply <變更名>」；有效的 worktree 政策開啟且第 1 波有兩個以上可開工時，再列出可並行名單。沒有可開工的變更或 plan 失敗時不提。

兩段都只是提醒，技能不會代跑封存以外的任何技能。封存順序與衝突怎麼算，見[執行順序：plan 與依賴](plan.md)。

| 情況 | 技能的提示 |
| --- | --- |
| 目標變更封存要等 add-a | 封存前提醒「plan 建議先封存 add-a；add-a 封存後對照正式規格重寫再封存 <變更名>」，你確認後照常封存 |
| 目標變更封存不必等別人、沒有宣告前置未封存、也沒有衝突 | 不提順序，直接封存 |
| 封存成功、有 `openspec/manual/`、封存前 add-c 封存要等目標、下一個可開工是 add-b | 提醒手冊可能過期，提醒 add-c 先對照正式規格重寫再封存，並提「下一個可開工：add-b，執行 /speclink-apply add-b」；三者都只是提醒 |
