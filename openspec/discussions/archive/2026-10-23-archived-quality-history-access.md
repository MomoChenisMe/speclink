## Context

使用者發現已封存 desktop-workflow-and-offline-security-review 的品質關卡「已審查／已驗證」無法展開歷史，詢問封存是否保存及是否需要查閱，接著追問完整保留與只留最後一次的取捨，以及手動刪除紀錄的影響。目標具體，直接核對資料與行為，不需泛化追問。現有封存內實際有六筆審查與六筆驗證，共156209 bytes；兩類 CLI history 清單及各一筆全文均讀取成功。ArchivedDetailPage.tsx 只有靜態狀態籤，未接品質紀錄清單。desktop-app「文件區只顯示進行中的審查與驗證」另明文排除已封存詳情的歷史清單，需釐清獨立文件清單與品質關卡展開入口的界線。
相關正式規格為 desktop-app、change-lifecycle、review-station、verify-station，目前沒有進行中的變更。既有保留政策預設三類完整保留；先前討論已要求封存時帶走紀錄供後續查閱，這次不重新質疑保存目的，討論聚焦查閱入口、歷次保留範圍與手動缺檔處理。quality/history.rs:index 會在任何類別查詢前檢查共用索引的全部文件及內容指紋，任一缺檔會使整個查詢失敗；record 也先呼叫 index。這是讀程式核對出的現況，尚未操作真實檔案進行刪除測試。

## Rounds

### Round 1 — assumptions (2026-10-23)

**Focus**: 封存後如何保留歷次檢查的可追溯性，以及手動刪檔是否會影響其他紀錄。
**Position**: 已查證保存與讀取現況，以下保留及顯示方向仍是建議，尚待使用者裁定。
- 一次蓋章保存的是該次活動工單的完整輪次，不代表後一次完成紀錄必然包含先前每次蓋章的問題、修正理由與接受情形；quality/station.rs:write_stamp 將 gate.ticket_text 原文保存至獨立紀錄。建議封存完整保留歷次紀錄，預設先呈現最新，展開歷史才列其餘，兼顧簡潔與追溯。這張工單十二份 Markdown 約153 KiB，沒有只為節省這些檔案而刪歷史的明確需求。
- 現行 check_records.archive 是各類保留與否的布林值，沒有只保留最後一次的政策；只留最後一次將是新行為，不假定已支援。
- 手動刪除索引仍列明的任一紀錄會觸發 missing_check_record；修改內容會觸發 integrity_error。quality/history.rs:index 會逐筆驗證所有類別，record 也先驗證完整索引，因此可能連帶阻擋同一提案其他仍完整的紀錄，這不只是該筆打不開。不可直接刪除整份 index.json，否則現行讀取會視為空索引，剩下文件將無法從正常清單找到。
- 建議封存頁沿用品質關卡展開入口、開始時間新到舊及唯讀全文；人工缺檔應保留索引證據並明示該筆缺失，其他完整紀錄仍能讀取；內容變更仍需明示驗證失敗，不隱藏缺檔、不自動更新指紋把修改當成可信。這是擬議改善，現行程式尚不具備；也不預判新一輪驗收及寫入流程應放寬完整性守門。
**Open**: 待裁定封存後是否開放品質關卡歷史展開、採完整保留或只留最後一次、是否將缺檔隔離與明示警示納入此次範圍；尚未要求新增刪除或清理工具。

### Round 2 — assumptions (2026-10-23)

**Focus**: 確認完整保留、封存後歷史入口與單筆缺檔隔離的共同方向。
**Position**: 使用者以「好」採納前輪建議，三項待裁定方向均已定案。
- 封存預設完整保留歷次審查與驗證紀錄，清單依開始時間由新到舊排列；不新增只保留最後一次的模式，沿用既有各類封存保留設定。
- 已封存詳情的品質關卡「已審查／已驗證」可各自展開對應歷史，選取後在閱讀區唯讀查閱完整內容；不新增文件區或獨立歷史清單，不觸發重跑或改動原章。
- 索引仍列明但文件遭手動刪除時顯示該筆文件缺失；內容指紋不符時顯示該筆完整性錯誤，其他完整紀錄仍可查閱，不自動修改索引或指紋。依政策未保留、沒有紀錄與真正讀取失敗必須區別呈現。
**Ruled out**: 只保存最後一次紀錄（失去先前問題與接受理由）；任一缺檔就封鎖其他完整歷史（不利查閱）；刪除索引或自動重算指紋掩蓋缺失（抹除完整性證據）。
**Open**: 無待裁定的產品方向；共用讀取契約、單筆錯誤表示及測試範圍交提案設計；刪除／清理工具與寫入／驗收完整性守門的變更不在此次範圍。

## Conclusion

**Decision**: 封存預設完整保留歷次審查與驗證紀錄，從品質關卡唯讀查閱歷史，單筆缺檔或內容異動不拖累其他完整紀錄。
- 延續既有 check_records.archive 各類保留設定，預設完整保留各次審查與驗證的全部輪次及完成紀錄，不改成只留最後一次、不增加只留最後一次的政策選項。
- 已封存詳情的品質關卡「已審查」與「已驗證」分別作為歷史展開入口，兩類獨立操作；清單依開始時間由新到舊呈現時間、結果與紀錄識別，選取一筆後在閱讀區唯讀顯示其全文。例如此封存有六筆審查及六筆驗證，點「已審查」只展開六筆審查，再點一筆即可查看該次完整內容，不混入驗證紀錄。
- 文件區維持不另列已完成紀錄，也不建立獨立檢查紀錄清單；活動提案的文件區只顯示進行中的工單。調整 desktop-app 對已封存詳情歷史清單的排除文字，明確允許品質關卡內展開，保留不另列文件節點的原意。
- 沿用同一份保存紀錄、索引與既有讀取分層，不建立第二份權威文件；歷史查閱不觸發重跑、不重新蓋章、不改動已封存內容及原章。
- 索引仍列明但文件被手動刪除時，保留該筆索引證據並明示文件缺失；內容指紋不符時明示完整性錯誤，不把異動後內容當成通過驗證的文件。其他仍完整的紀錄繼續可讀，同一提案其他類別缺檔亦不得使完整審查或驗證紀錄全部不可查。例如六筆審查中的第二筆被刪除，清單仍列六筆並標示第二筆缺失，其餘五筆及完整驗證紀錄仍可查閱。
- 區分依封存政策未保留完整紀錄、確實無紀錄、單筆缺失或完整性錯誤，以及索引／來源讀取失敗；來源失敗提供重試，不假裝空清單，不靜默刪索引條目或重算指紋來掩蓋資料問題。不得以刪除或重建整份索引作為自動修復方式。
- 沿用既有紀錄顯示元件及專案隔離原則；切換專案或封存項目不得顯示前一項的內容，展開入口可用鍵盤操作。共用讀取改動需核對活動與封存、本機與遠端的讀取行為，具體介面與測試案例交提案設計。
**Rationale**: 每次完成紀錄只保有該次活動工單的輪次，最後一次不必然涵蓋先前問題與接受理由；現有十二份文字紀錄共156209 bytes，完整保留有實際追溯價值。資料已保存且封存後 CLI 能讀，主要缺口是 Desktop 入口；共用索引驗證目前會讓一筆缺檔阻擋整組查詢，應隔離查閱時的單筆錯誤並保留完整性證據。
**Rejected alternatives**:
- 只保留最後一次審查與驗證 — 無法追溯先前發現、修正過程與接受理由。
- 封存頁只保留靜態品質章、要求改用 CLI 或檔案系統找歷史 — 資料已有保存，仍未達成封存後可從 Desktop 查閱的目標。
- 在文件樹另列所有歷史紀錄 — 違反既定品質關卡為唯一 Desktop 歷史入口的操作方向。
- 任一缺檔就封鎖其他完整歷史 — 不必要地讓其餘可查的紀錄也失去查閱能力。
- 靜默刪索引條目、重建索引或更新指紋接受異動 — 會隱藏資料缺失與內容完整性問題。
**Deferred**:
- 新增刪除／清理紀錄工具與自動修復功能 — 本次處理保留、查閱及缺檔呈現，未要求管理或修復歷史文件。
- 放寬新一輪審查、驗證、封存及寫入時的完整性守門 — 查閱可隔離單筆錯誤，不代表缺損歷史可作為新驗收證據；沿用現有守門，若讀寫共用程式需拆分，提案必須確保寫入與驗收不被放寬。
