## Context

**起因**：使用者回報「本地模式下 desktop 無法針對卡片進行 reorder」——桌面看板的變更卡（change card）不能手動拖排。

**模式（assumptions）**：掃到足夠相關程式碼（`KanbanBoard.tsx`、`TaskList.tsx`、`store.ts`、adapter 層、`apps/desktop/core/src/query.rs`），以假設清單推進。

**掃描到的關鍵事實**：
- 看板變更卡目前**無手動排序**：順序來自 `query.rs:21` 的 `sort_changes(store, &mut changes, "modified")`（依最後修改時間），欄位（proposed／in-progress／ready）由**任務完成度推導**（`changeStage`）。`KanbanBoard.tsx` 的拖曳目前**只**接封存落點（拖到 ArchiveDropZone，`:173`），欄間、欄內都不能拖排。
- 任務列（`TaskList.tsx`）**已有**完整拖排，走 `move_task` Tauri command → `manage.rs:move_task_at`，本地可用。
- 桌面 app 只有一條 data source：`createTauriDataSource`（讀本地檔）。`web-*`（web-server-postgres 等）是另一套 server-backed 變體，不是桌面內的模式開關。

**相關變更**：`desktop-nav-reorder`（側欄導覽重排，與看板卡排序不同）。CLI 尚未支援 `discuss --slug`，故沿用 repo 既有中文 slug 慣例。

## Rounds

<!-- `### Round N — <mode> (<date>)` entries are appended here by the CLI. -->

### Round 1 — assumptions (2026-07-07)

**Focus**：釐清「卡片」「本地模式」所指，以及這是「缺功能」還是「本地壞掉」，並定調使用者要的排序型態。

**Position**：使用者確認——
1. 「卡片」＝看板的變更卡（非任務列）；「本地模式」＝檔案式桌面 app（相對於在建的 web／server 版）。
2. 這是**從未實作**：全庫無變更卡 reorder 程式碼，順序是 modified-time 計算值，無任何持久化手動序。
3. 使用者要的是**真正的手動拖排**（記住每張卡位置），**不是**換排序規則。
4. 順序需**跨機器同步（進 repo）**，非只存 app 本機。

**Ruled out**：
- 任務列排序失效——任務列已能本地拖排（`move_task`），非本題。
- app 本機持久化（如分頁那樣）——使用者要進 repo 跨機同步，排除。
- YAGNI 替代「只換排序模式選單」——使用者明確要真正手動序，排除。

**Open**：
- 持久化表徵：單一 board-order 清單檔　vs　每張卡 frontmatter 寫 `board_order` 序號。
- 座落層（seam）：core 概念（CLI／未來 web 共用）　vs　僅桌面 core крate（`apps/desktop/core`）。
- 對帳規則：清單與實際變更集漂移時（新建／封存／刪除）怎麼調和；新卡預設落位。
- 語意邊界：跨欄拖曳（stage 由推導，應否 snap-back）、討論卡是否納入。

### Round 2 — assumptions (2026-07-07)

**Focus**：順序（與其他共享狀態）可否存 SQLite 並讓 db 檔進 repo？

**Position**：否——維持「文字檔進 repo 當真相、SQLite 只當本機快取」的既有格局，順序採表徵 B（單一 board-order 文字清單檔）。證據：(1) git 無法合併二進位，兩機並行修改時 .db 整檔二選一、另一邊靜默丟失，「更好共享」前提不成立；(2) 使用者點名的建立人／開工人已在 change frontmatter 以文字跨機同步（archive.rs:467 測試斷言 created_*/started_* byte-for-byte 存活封存）；(3) 開工章正是從 SQLite 遷出到 frontmatter 的（inprogress.rs:4 "pre-migration SQLite database"）；(4) 已結論討論「四情境預設-gui-工具矩陣」明文否決「桌面用 SQLite 當真相」（放棄 git 跟隨、與 spectra 架構分歧）；(5) SQLite 的正確角色是 .speclink/desktop-cache.db 式的本機衍生快取（不進 repo、可刪可重建），真·多人共享是 web-server-postgres 的職責。

**Ruled out**：
- SQLite db 檔進 repo 當共享真相——二進位不可合併、翻既結論案無新論據，排除。
- 表徵 A（每卡 frontmatter 寫 board_order 序號）——一次拖排改多檔、重編號、N 個合併衝突點；順序本質是一串有序名稱，A 只是其反正規化編碼。

**Open**：
- 使用者確認表徵 B。
- 新卡（不在清單中）落位：欄頂或欄底（我傾向欄頂，貼近現行 modified 新在前手感）。
- 跨欄拖曳：stage 由任務完成度推導，建議僅欄內排序、跨欄放開彈回。
- 討論卡（第 0 欄、現按 slug 排）：本次納入或先擱置（我傾向擱置）。
- 清單檔的座落與檔名（openspec/ 下何處）、對帳規則細節。

### Round 3 — assumptions (2026-07-07)

**Focus**：使用者選表徵 A 且要求四欄（討論／提案中／進行中／已就緒）全部可排——A 的第 2 輪否決是否成立？

**Position**：撤回第 2 輪對 A 的否決，改採「A＋稀疏 rank」。第 2 輪按「整數序號、每次拖排重編號」的天真版本評估；改用 fractional ranking（rank＝前後鄰居中點，浮點或 LexoRank）後：一次拖排只改被拖卡一個檔一行；兩機各拖不同卡改到不同檔，git 自動合併零衝突（優於 B 的單檔衝突面）；封存/刪除時 rank 跟卡走、免 B 需要的清單對帳；且與專案「狀態存實體 frontmatter」慣例（created_by/started_at）一致。四欄統一機制：討論 doc 已有 frontmatter，加同款 rank 欄位即可。A/B 的畫面效果本相同，差異只在存放與合併行為——此點已向使用者澄清。

**Ruled out**：
- 表徵 B（單一 board-order 清單檔）——兩機並行拖排必撞同一檔；殘名需對帳邏輯；新增檔案類型。在稀疏 rank 版 A 面前失去優勢。
- 「討論卡先擱置」（我第 2 輪的傾向）——使用者明確要四欄全可排，且統一 rank 機制下納入成本低，擱置反而留下不一致。

**Open**：
- 新卡（無 rank）落位：欄頂或欄底。
- 跨欄拖曳：stage 由任務完成度推導，變更卡跨欄放開是否彈回（僅欄內有效）。
- rank 欄位名與格式（浮點 vs LexoRank 字串）、重平衡時機——可留設計階段。

### Round 4 — assumptions (2026-07-07)

**Focus**：要不要「順便」把儲存手法整個重構（狀態遷入 SQLite）？

**Position**：否，本變更保持小而完整。(1) 重構要解的問題不存在——排序痛點由 rank 欄位解決，建立人／開工人／狀態已在 frontmatter 跨機同步；(2) 第 2 輪結論未變：db 不進 repo 則狀態停止跨機同步、進 repo 則二進位不可合併，無贏面，且「四情境預設-gui-工具矩陣」已明文否決；(3)「狀態存資料庫」的正確出口是進行中的 web-server-postgres（server 中介 DB），非檔案模式改造。

**Ruled out**：搭載式儲存層重構——把小功能綁上全域遷移（Store trait／CLI／golden／封存語意），純風險零收益。

**Open**：無——新卡落欄頂、跨欄彈回均已由使用者確認，餘者（rank 格式、重平衡）明列 Deferred。

## Conclusion

**Decision**：桌面看板四欄（討論／提案中／進行中／已就緒）加入欄內手動拖排。順序以稀疏 rank（fractional ranking）存於每張卡自身的 frontmatter（變更 meta、討論 doc），進 repo 跨機同步。新卡（無 rank）落欄頂；變更卡跨欄放開彈回（stage 由任務完成度推導，拖曳不改變階段）；討論卡僅於討論欄內排序。不搭載儲存層重構。
**Rationale**：稀疏 rank 使一次拖排只改被拖卡一檔一行；兩機各拖不同卡改到不同檔、git 自動合併零衝突；封存時 rank 跟卡走、免清單對帳；與專案「狀態存實體 frontmatter」慣例（created_by／started_at）一致。核心 trade-off：合併行為 vs 順序集中一處——選前者。介面深度：seam＝rank 欄位＋排序邏輯（core 讀、桌面寫）；單一 adapter（一支 reorder Tauri command）；深度＝中點計算、新卡預設落位、重平衡；刪除測試＝拿掉即退回 modified 排序，通過。
**Rejected alternatives**：SQLite 當真相（git 無法合併二進位；開工章正是從 SQLite 遷出；「四情境預設-gui-工具矩陣」既結論否決；DB 共享屬 web-server-postgres 職責）；表徵 B 單一 board-order 清單檔（兩機並行拖排必撞同檔、殘名需對帳）；整數序號版 A（一次拖排重編號改多檔）；只換排序模式選單（使用者要真手動序）；app 本機持久化（要跨機同步）；搭載式儲存層重構（無問題可解、純風險）。
**Deferred**：rank 欄位名與格式（浮點 vs LexoRank 字串）、重平衡時機與中點精度耗盡處理——留 design 階段。
