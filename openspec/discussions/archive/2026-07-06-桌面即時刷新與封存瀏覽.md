## Context

使用者回報桌面 app 兩個問題（附截圖，含 Spectra 2.3.1 對照）：(1) 看板卡片與詳情抽屜的任務數顯示 0/0，但任務 tab 內容正常列出 28 個任務；(2) 已封存變更只有「日期＋名稱＋複製鈕」列，無法像 Spectra 一樣展開檢視提案／設計／任務／規格。

模式：assumptions（相關原始碼充足——apps/desktop/src/store.ts、App.tsx、apps/desktop/core/src/query.rs、cache.rs、packages/ui/src/components/ArchivedList.tsx、crates/speclink-fs/src/lib.rs）。

Scout 事實：CLI speclink list --json 對同一 change 回報 totalTasks: 28，且桌面 list_changes_at 與 CLI 走同一條 listing::changes_json 路徑——計數引擎無誤。refresh() 僅在掛載與 app 內動詞操作後觸發，無檔案監看。封存文件實體完整保留在 changes/archive/<dated-name>/，但 Store trait 只有 read_archived_meta，無封存 artifact 讀取；SQLite 快取（CACHE_VERSION 1）僅存 meta。

相關 change：desktop-config-multiproject（已 propose 完成、未動工）會大改 App.tsx／store.ts，與本題有檔案衝突面，須定先後。

## Rounds

<!-- `### Round N — <mode> (<date>)` entries are appended here by the CLI. -->

### Round 1 — assumptions (2026-07-06)

**Focus**: 兩個問題的根因判定與修法方向（六項假設一次過堂）
**Position**: (1) 0/0 非計數 bug——引擎與桌面共用 listing::changes_json 且 CLI 回報 28；根因是「無外部變更刷新」：refresh 只在掛載與 app 內操作後跑，任務 tab 內容是點開時即時讀檔所以看得到新任務、徽章卻是啟動時的清單快照。使用者確認 Spectra desktop 有即時刷新，且要求監看範圍涵蓋整個 openspec/（規格、proposal、design、tasks），雙向收斂（外部手改 tasks.md 與 app 內勾選都反映）。(2) 封存瀏覽是功能缺口：檔案實體都在，缺 Store trait 的封存 artifact 讀取縫＋前端展開式列。縫開在 Store trait（read_archived_artifact，隱藏 dated-name 佈局）＋ SpeclinkDataSource（封存瀏覽屬「change 瀏覽」抽象本體，web 版同需）；任務徽章計數擴進 SQLite 快取（CACHE_VERSION 1→2）。兩題併一個 change，排在 desktop-config-multiproject 之前動工（後者大改 App.tsx／store.ts，先小後大降 rebase 成本）。
**Ruled out**: 手動刷新鈕／輪詢／僅聚焦刷新作為主方案（SDD 常態是 CLI 與 agent 外部寫檔，被動方案治標）；以 document_at 拼 "archive/<dated-name>" 路徑的 hack（把 fs 佈局假設寫死，remote store 斷裂）；展開時現場解析 tasks.md 取徽章（違背快取存在理由——歸檔量無上限成長）。
**Open**: 封存列的復原／刪除鈕（Spectra 有）是否納入——使用者已定為此次 Non-Goal；監看實作細節（notify vs plugin、debounce、與未來執行期換 root 的相容）留給 propose/design。

### Round 2 — assumptions (2026-07-06)

**Focus**: 看板「進行中」欄的狀態來源——SQLite 標記的消費缺口與 remote 三情境衝擊
**Position**: 看板欄位現由前端 stage.ts 以任務數近似（0 任務=提案中、全完成=已就緒、其餘=進行中），不讀任何 SQLite；引擎的 in-progress 標記（inprogress.rs，.git/speclink-app/speclink.db，Spectra 同款 DDL）由 /speclink-apply 開工時寫入但全 repo 零讀取者。後果：propose 完成、尚未開工的 change 會被錯置到「進行中」欄。remote 衝擊分析：標記存 .git/ 是 host-local 狀態——情境 3（本地 CLI＋遠端文件）web 看板永遠看不到標記；情境 1（PO/PM 在 web）無法區分「提案完成」與「進行中」；情境 2（agent 跑 SDD）標記必須落在 server 端共享狀態。跨機縮影：使用者換機工作，A 機標記 B 機不可見——此為 Spectra 既有缺陷（db 在 .git 不隨 repo 走）。定案：標記真相遷入 change meta（.openspec.yaml）——隨 repo 走修跨機缺陷、騎在文件真相上使 store 同步到哪標記就到哪（remote 三情境零新縫）、桌面經既有 change_meta 讀取路徑消費。看板中欄改為標記驅動。
**Ruled out**: 維持 .git/ 下 SQLite 並補讀取端（parity 純儀式性——Spectra 用 spectra-app 路徑、兩者本就無法互通，且繼承跨機缺陷、remote 需另開 store 狀態縫）；SQLite 檔案進版控隨 repo 走（二進位無法合併、page 重寫致工作樹無故髒、Windows 檔案鎖阻擋 git checkout、且 remote 模式文件真相在 store 不在 repo——仍然無解）；Store trait 現在就開狀態 API 縫（單一實作即開縫違反不過度設計；meta 方案使此縫根本不需要）。
**Open**: 標記欄位形狀（裸布林 vs 結構化歸屬）；歸檔時標記欄位的處理（保留 vs 剝除）。

### Round 3 — assumptions (2026-07-06)

**Focus**: 標記遷入 meta 後，生命週期狀態歸屬要強化到什麼程度
**Position**: 檢視實際 meta 檔發現生命週期歸屬已完成三分之二——created/created_by/created_with 與 from_discussion 建立時即有，archived_by/archived_at 歸檔時蓋章；唯缺中間站「誰何時開工」。定案：標記做成結構化欄位 started_by/started_at/started_with（與 created_by 同一套身分機制，寫入成本零），補齊 created → started → archived 對稱生命週期。看板三欄對映：無 started＝提案中、有 started＝進行中、任務全完成＝已就緒。remote 收益：PO 看板可見「誰在做」，情境 2 可區分執行 agent。強化邊界（防事件溯源兔子洞）：meta 只放現況狀態＋三站里程碑歸屬；完整操作稽核不做——fs 模式下 git history 本來就是稽核日誌，meta 重複記錄即雙真相；逐任務歸屬、狀態變更歷史、event log 明確不做，remote 若需要屆時是 server 端另一刀。
**Ruled out**: 裸布林 in_progress（欄位形狀日後升級需 migration，而歸屬資訊寫入時免費、remote 情境必需）；meta 內記完整操作歷史（雙真相、無上限成長，git history 已覆蓋）。
**Open**: 無——歸檔時 started_* 欄位隨檔案移入 archive（與 created_*/archived_* 並列完整生命週期記錄），不剝除。

### Round 4 — assumptions (2026-07-06)

**Focus**: 討論記錄要不要進看板——狀態列如何調整
**Position**: 看板擴為四欄，「討論」為第 0 欄，實體＝討論記錄（與 change 卡不同型）。狀態判斷零新機制：open（討論中，卡片唯讀——回合推進在 CLI/agent）、concluded（已結論，卡片行動 promote／archive）、promoted（離欄，其 change 帶 from_discussion 徽章現身提案中）、archived（已封存頁新增「討論」節，含最後 change 歸檔時的自動歸檔）。基建現成：狀態在文件（discuss list --json 已吐）、Store trait 已含 discussions 讀取、watcher 已涵蓋 discussions/；騎在 Store 上使三種 remote 情境免費獲得（情境 1 PO 於 web 參與討論可視）。範圍定位：此為 Speclink 自有增強（Spectra 無 discuss），與 parity 四項性質不同且體量約等於封存瀏覽整項——獨立為本討論扇出的第二個 change（討論看板），排序：第一刀 parity 四項 → 第二刀討論看板 → desktop-config-multiproject。
**Ruled out**: 併入第一刀（把 parity change 撐到 30+ 任務，且混合 parity 與增強兩種性質）；討論放側欄獨立頁不進看板（生命週期連續性不可見——discuss 是 propose 的前站，使用者要的正是狀態列呈現）；GUI 做 conclude（結論內容由 agent/CLI 撰寫，GUI 只做 promote 與 archive 兩個推進動詞）。
**Open**: 無。

### Round 5 — assumptions (2026-07-06)

**Focus**: 一份討論扇出多個 change 時的狀態與 UI 設計（第二刀細化）
**Position**: 促轉是「代表權轉移」非終點——promoted 討論仍活著（changes 在飛）但飛行已由 change 卡代表。兩級呈現：actionable 狀態（open/concluded）用全尺寸卡；promoted 降級為討論欄底部收合細列，每列列出 promoted_to chips 與各 change 的 stage 點（○ 提案中 ◐ 進行中 ● 已就緒 ✓ 已封存），全數 ✓ 時該列隨自動歸檔消失。討論抽屜含「促轉」tab（各 change 現況＋跳轉＋「再促轉」入口——扇出下一刀的 GUI 動詞放此處不放欄上）。change 側反向連結：💬 徽章＋抽屜「來自討論」標頭＋同源 change（兄弟刀）清單互跳。狀態全由既有檔案派生（討論 frontmatter 的 promoted_to ＋各 change 的 meta/tasks），零新狀態機制，remote 三情境同一套派生。
**Ruled out**: promoted 討論維持全尺寸卡留欄（與 change 卡重複表達、欄擁擠）；promoted 即完全離板（丟失再促轉入口與同源視角）；per-discussion 顏色編碼分組看板卡（同時在飛的討論個位數，💬 徽章＋同源清單已足，色彩分組過度設計）。
**Open**: promoted_to 中的 change 被刪除（非歸檔）的語意——傾向 chip 標「已刪除」、討論維持 promoted（歷史不回滾），全數刪除是否回退 concluded 待第二刀 propose 時查證引擎現行行為定案。

## Conclusion

**Decision**: 本討論扇出兩個 change，依序動工，皆先於 desktop-config-multiproject。第一刀（parity 四項）：(A) 即時刷新——後端檔案監看覆蓋整個 openspec/ 樹（含 discussions/），事件 debounce 後前端整批 refresh，雙向收斂；wiring 留 apps/desktop，SpeclinkDataSource 不加訂閱介面。(B) 封存瀏覽——Store trait 新增封存 artifact 讀取（read_archived_meta 對稱擴充），SpeclinkDataSource 加封存文件讀取，SQLite 快取 CACHE_VERSION 1→2 加任務計數徽章，ArchivedRow 擴為 Spectra 式展開列（唯讀 tabs）。(C) in-progress 標記真相遷入 change meta——結構化 started_by/started_at/started_with 補齊 created → started → archived 生命週期；speclink in-progress add 改寫 meta（stdout 形狀不變），.git/speclink-app/ SQLite 寫入端退役；歸檔時 started_* 保留。(D) 看板中欄標記驅動——無 started＝提案中、有 started＝進行中、任務全完成＝已就緒；ChangeItem 加對應欄位，抽屜顯示誰於何時開工。第二刀（Speclink 增強）：討論看板——看板擴四欄，「討論」為第 0 欄，兩級呈現：open＝討論中與 concluded＝已結論用全尺寸卡（已結論卡帶 GUI 動詞 promote／archive）；promoted＝已促轉降級為欄底收合細列，列出 promoted_to chips 與各 change stage 點（○ 提案中 ◐ 進行中 ● 已就緒 ✓ 已封存），全數歸檔時隨自動歸檔離板；討論抽屜含脈絡／回合／結論／促轉四 tab，「再促轉」入口在促轉 tab（支援一討論扇出多刀）；change 側 💬 徽章＋抽屜「來自討論」標頭＋同源 change 清單互跳；已封存頁增「討論」節；desktop-core 新增 discussions 查詢橋接與 promote/archive 命令。狀態全由既有檔案派生（討論 frontmatter promoted_to ＋各 change meta/tasks），零新狀態機制。
**Rationale**: 0/0 根因是清單快照停在啟動時，SDD 常態是 app 外持續有寫者。標記存 .git/ 是 host-local 且零讀取者——parity 純儀式卻繼承跨機缺陷；遷入 meta 隨 repo 走、騎在文件真相上使 remote 三情境零新縫。歸屬止於三站里程碑（完整稽核＝git history）。討論看板獨立成刀：Speclink 自有增強與 parity 補洞性質不同，體量足撐一刀；促轉採兩級呈現因促轉是代表權轉移非終點——changes 在飛但飛行已由 change 卡代表，全卡留欄重複、完全離板則丟失再促轉入口與同源視角。
**Rejected alternatives**: 手動刷新鈕／輪詢／聚焦刷新；subscribe 進 SpeclinkDataSource；document_at 拼 archive 路徑 hack；徽章現場解析 tasks.md；維持 .git/ SQLite 補讀取端；SQLite 進版控（二進位不可合併、page 重寫髒樹、Windows 檔案鎖擋 git、remote 仍無解）；裸布林標記；meta 記完整操作歷史（git history 已覆蓋）；討論欄併入第一刀（30+ 任務且混性質）；討論放獨立頁不進看板；GUI 做 conclude（結論由 agent/CLI 撰寫）；promoted 全尺寸卡留欄或完全離板（兩級細列取代）；per-discussion 顏色編碼分組（過度設計）；先做 desktop-config-multiproject（同檔衝突，先小後大）。
**Deferred**: 封存列的復原（unarchive）與刪除鈕；備忘側欄項的內容定位；逐任務歸屬與 event log；promoted_to 中 change 被刪除（非歸檔）的語意——傾向 chip 標「已刪除」、討論維持 promoted，全數刪除是否回退 concluded 待第二刀 propose 查證引擎行為定案；web-server-postgres／web-agent-channel 骨架的現況註記（meta 標記欄位、LISTEN/NOTIFY→SSE、agent 寫共享標記、討論看板騎 Store）於兩刀 propose 時一併落。
**Capture to**: proposal
