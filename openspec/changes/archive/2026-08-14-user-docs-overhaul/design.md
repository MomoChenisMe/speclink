## Context

`docs/` 現有 11 個使用者面主題（多數中英成對）加上兩份 README，約 180KB，全部是隨能力逐次增修堆疊出來的，零截圖。正典 `user-documentation` 已規定漸進揭露、單一責任、中英對等與只寫可走的入口——本次不推翻這些原則，而是在其下重排內容、補上視覺與缺漏的兩個主題（使用者面路線圖、本地與遠端能力對照）。

技術限制有兩個，直接決定做法：

- **desktop 沒有資料目錄隔離**：Server 連線存在 appConfigDir 的 `connections.json`；workspace 分頁存在 WebView 的 localStorage（`speclink.projectTabs`），落在另一個使用者層級目錄。兩處 dev 與安裝版共用（appConfigDir 內的 `tabs.json` 是舊版殘留，現行程式碼已不讀寫，只搬它拍不到乾淨狀態）。要拍到「乾淨全新狀態」，必須在拍攝期間把這兩個目錄都移開再還原，沒有以旗標指定替代目錄的路徑。
- **截圖時機不可靠**：載入骨架、動畫、抽屜開闔與 tray 狀態都會影響版面，自動擷取容易產出品質不一或抓到中間態的圖片。

## Goals / Non-Goals

**Goals:**

- 首次接觸者在讀 README 時，能在安裝前就看到 Speclink 實際長什麼樣
- SDD 十一個站在單一處講完整：用途、對應技能、完成判準、下一站
- 本地與遠端能力差異有單一對照表，不需跨文件拼湊
- 對外方向（SDK、以引擎自建客戶端、遠端協作、agent 工具整合、系統整合）與內部交付順序分開陳述
- 截圖場景可重現，且拍攝過程不損毀使用者的既有 app 狀態
- 中英兩版在結構與事實上對等

**Non-Goals:**

- 不改寫兩份架構文件（平台架構藍圖、實作重構路線圖）
- 不自動化截圖擷取本身
- 不改動任何行為、CLI 動詞或 GUI
- 不建立文件網站
- 不引入截圖以外的新資產型別（錄影、GIF）

## Decisions

### D1：截圖以「腳本備份還原＋人工擷取」分工

新增 `scripts/docs-screenshots.mjs`，負責可重現且安全的場景佈置，不負責按快門：

1. **備份**：把上述兩個 desktop 狀態目錄整個搬到腳本自建的備份路徑（放在 home 而非暫存區——備份沒還原就等於使用者的分頁與連線消失，不能讓它隨暫存區被清掉）；任一目錄不存在時記錄「原本就不存在」，還原階段據此刪除而非搬回。備份路徑已存在代表上一次沒還原完成，此時 SHALL 拒絕開始而不覆蓋它。
2. **佈置**：在系統暫存區建出示範 workspace——git init、speclink init、造出分別位於提案中／進行中／已封存的示範變更各若干，以及一則已結論的討論，讓看板三欄與討論頁都非空。示範內容全部由腳本產生，不含使用者任何真實資料。
3. **交棒**：印出示範 workspace 路徑與待拍清單，然後等待；此時由人開啟 app、加入該 workspace、逐項擷取。
4. **還原**：收到繼續指示（或收到中斷訊號）時，先刪除拍攝期間產生的狀態目錄，再把備份搬回原位；示範 workspace 一併清除。

還原 SHALL 在中斷訊號（Ctrl+C）下也執行——備份沒還原就等於使用者的分頁與連線設定消失。腳本 SHALL 在備份前先確認 app 未執行（執行中直接拒絕），否則 app 會在退出時把記憶體中的狀態寫回、覆蓋還原結果。

理由：拍攝時機與版面判斷交給人，備份還原這種一步錯就毀掉使用者設定的環節交給腳本，各自做擅長的事。替代方案「請使用者手動備份」被否決——手動流程正是會漏掉還原的路徑。

### D2：截圖清單固定為九張，中英共用

| 檔名 | 內容 |
| --- | --- |
| `desktop-board.png` | 變更看板三欄與卡片 |
| `desktop-change-drawer.png` | 變更詳情抽屜（含任務與 artifacts） |
| `desktop-spec.png` | 規格檢視 |
| `desktop-discussion.png` | 討論記錄檢視 |
| `desktop-archived.png` | 已封存檢視 |
| `desktop-settings.png` | 設定（含 Server 連線） |
| `server-setup.png` | server 首次 `/setup` 畫面 |
| `server-overview.png` | 後台總覽 |
| `server-members.png` | 成員與 PAT 管理 |

中英兩版引用同一組圖片檔（介面語言以中文擷取，英文版於圖說註明介面可切換語言），避免兩套圖片各自腐化。圖片以相對路徑內嵌，符合 GitHub 上的呈現。

### D3：文件分層與各自的單一責任

沿用正典的漸進揭露，明確每份文件回答哪一個問題：

| 層 | 文件 | 只回答 |
| --- | --- | --- |
| 入口 | README（中英） | 這是什麼、長什麼樣、我要不要用、怎麼裝、從哪開始 |
| 上手 | getting-started（中英） | 本地第一輪怎麼跑完 |
| 上手 | remote-getting-started（中英） | 遠端從 setup 到登入怎麼跑完 |
| 正典 | workflow（中英） | 十一個站各自的用途、技能、完成判準、下一站 |
| 參考 | product-status（中英） | 現在哪些能用、哪些還沒 |
| 參考 | configuration（中英） | 設定欄位歸屬與意義 |
| 參考 | verb-contract（中英） | 動詞與旗標契約 |
| 參考 | sdk-node（中英） | Node SDK 介面 |
| 參考 | development（中英） | 開發環境與本機建置 |
| 參考 | server-deployment／server-store-drivers／server-backup | server 部署、選型、備份 |
| 方向 | roadmap（中英，新增） | 之後會往哪走 |

本地與遠端能力對照表放在 product-status——它已是「現在能不能用」的正典，對照表是同一問題的另一個切面，不另立文件。

「怎麼裝」留在 README 而不外推：安裝是讀者決定要不要用之後的下一個動作，推到別的文件等於在轉換率最高的地方製造一次跳轉。範圍限定在**三塊各一張表**——桌面安裝檔、server 一行啟動、CLI 一行安裝——每塊的細節（環境變數、compose profile、自訂安裝路徑）一律連往負責文件。桌面與 CLI 兩塊受 `release-signing-and-channels` 的 spec「安裝通路文件與發布狀態誠實化」約束，本次不得刪除或降級；server 那塊是本次新增，補上後三條路在 README 對等可見。

### D4：使用者面路線圖只寫方向、不寫日期

新增的 roadmap 文件涵蓋五條線，每條寫「要解決什麼、目前到哪、可觀察的下一步」：SDK 發布、以引擎自建客戶端與 server 端（把引擎當函式庫，自行開發桌面、其他前端或自家 server）、遠端協作完整化、agent 工具整合（Copilot／MCP 等）、系統整合能力。前兩條共用同一個引擎面，但問題不同——一條是「裝不裝得起來」，一條是「裝起來之後能不能拿它做出自己的東西」，因此分列而不合併。SHALL NOT 出現版本號承諾或日期。

不與內部的實作重構路線圖互相連結：那兩份架構文件是維護者自用、且將被移除，使用者文件指向它們等於預埋斷鏈。使用者要的背景一律指向 `openspec/specs/` 正典與專案能力狀態。

### D6：官方 server 寫成參考實作，遠端模式的定義歸契約

正典 `reference-server` spec 明寫 `speclink-server` 是「Speclink Host 的參考 server 實作」與「wire contract 的活基準」，但先前的文件把遠端模式寫成必須用這一份 server。改為：遠端模式由 `host-runtime` 與 `client-protocol` 兩份公開契約定義，官方 server 是照契約做出來的其中一個實作，用途是開箱即用與試用；使用者可用 Speclink 引擎自建 server 端。

落點取捨：不新增獨立文件，而是在讀者已經會停留的六個位置各補一段——README 的部署路徑與安裝章節、Remote 入門的開場、Node SDK 的用途段、Server 部署的開場、能力對照表的量測對象註記。理由是「server 可替換」是一個定位事實而非操作流程，另立文件會讓它落在沒人經過的地方。

### D5：中英對等以「同結構、同事實」定義

兩版 SHALL 有相同的章節結構、相同的截圖、相同的事實主張；容許差異僅限語言表達與必要的在地化說明。既有的 zh-TW 專屬 server 三份文件（部署、選型、備份）維持只有中文，不在本次擴充為雙語——那是既有範圍決定，本次不改。

## Implementation Contract

**Behavior（改完後可觀察）：**

- README（中英）首屏之後可見至少一張 desktop 截圖，且圖片以相對路徑內嵌、在 GitHub 頁面上正常顯示
- workflow（中英）以單一表格或等價結構列出十一個站，每站含用途、對應 `/speclink-*` 技能、完成判準、下一站
- product-status（中英）含本地與遠端能力對照表，查核日期為本次改寫當日，且不再宣稱 `docs/verb-contract.md` 不存在
- roadmap（中英）存在且無版本號或日期承諾
- 執行截圖腳本後，使用者原本的 desktop 分頁與 Server 連線設定與執行前一致
- 全部文件內部連結可解析（無指向不存在檔案的相對連結）

**Interface：**

- `scripts/docs-screenshots.mjs`：`--setup` 佈置並等待、`--restore` 還原；`--dry-run` 只印出將備份的路徑與將建立的示範內容，不搬移任何檔案

**Verification：**

- `scripts/docs-screenshots.test.mjs`：以 dry-run 驗證備份路徑推導、示範 workspace 內容清單、以及「目錄原本不存在」與「app 執行中」兩條分支的判斷；不實際搬移使用者目錄
- 連結完整性：以腳本或指令掃出全部 markdown 相對連結與圖片路徑，逐一確認檔案存在
- 中英對等：逐份比對章節標題數與截圖引用數
- 截圖與還原正確性屬人工驗證

**失敗模式與處置：**

- 備份還原中斷 → 腳本以訊號處理器在中斷時仍執行還原；還原失敗時印出備份路徑，讓人可手動搬回
- app 執行中 → 拒絕開始，不代為結束 app

## Risks / Trade-offs

- **截圖會隨介面演進而過時**：接受此代價；緩解方式是把場景佈置腳本留在 repo，重拍成本低於首拍。
- **與 `release-signing-and-channels` 在四份文件重疊**：本 change 在其合併後才開始，換取零對撞；代價是文件改寫要等發版前置完成。
- **拍攝期間動到使用者 app 狀態**：以備份還原＋中斷保護＋執行中拒絕三層降低風險，但仍是本次唯一會碰使用者環境的操作。

## Migration Plan

文件與截圖資產屬新增或就地改寫，無資料遷移。既有指向被改寫文件的連結路徑全部維持不變（僅新增 roadmap 兩份），因此外部引用不會斷。
