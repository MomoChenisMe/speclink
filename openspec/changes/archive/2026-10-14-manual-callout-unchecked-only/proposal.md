## Summary

桌面 app 任務文件閱讀卡的「N 個手動任務」提示框，只列還沒勾的手動任務；手動任務全部勾完，提示框就消失。

## Motivation

目標使用者是在 desktop 透過 AI 代理跑 SDD 流程的開發者（PO／PM 亦同），情境是 apply 停在手動任務前、使用者親自做完並勾選之後，回到變更詳情頁的任務文件確認「還剩哪些事要我做」。

- 現在提示框列出所有帶 `[M]` 的任務，不看勾選狀態。實例：add-ask-user-tool 的 38 條任務全部勾完（含 4 條手動任務），提示框仍寫「4 個手動任務」並列出四條，看起來像還有事沒做。
- 提示框的用途是提醒「還有事要你親自做」。同一頁的任務列淡底只在未勾選時出現，看板的「待手動」章也只算未勾的 `[M]`；提示框是唯一不看勾選狀態的手動訊號。

由討論 manual-callout-unchecked-only 定案。正式規格「任務群組標題與章節標籤同款式」現在寫「有手動任務時 SHALL 有提示框……沒有手動任務時提示框缺席」，其中的「手動任務」含已勾者，所以要改規格，不能只改程式。

## Proposed Solution

- 提示框標題「N 個手動任務」的 N 與列表只計未勾選的 `[M]` 任務；每列的序號、標題、行內程式碼等寬籤與「前往」鈕照舊。
- 所有 `[M]` 任務都已勾選時提示框缺席；沒有任何 `[M]` 任務時同樣缺席（現行行為不變）。全部勾完時不改顯示「都完成了」之類的訊息：籤槽的「全部完成」與「已完成」數字磚已經表達這件事。
- 「手動」數字磚維持為帶 `[M]` 的任務總數，不隨勾選變動，與「任務」為總數、完成數另由「已完成」表示的分工一致。
- 勾選狀態的來源就是已解析的 tasks.md：共用 UI 套件產生任務文件閱讀卡摘要的函式（tasksSummary）在挑手動任務時加上「未勾選」條件。勾選寫回、agent 經 CLI 勾選後的外部檔案變更，都會讓頁面重新讀 tasks.md，提示框跟著更新，不另做偵測機制。
- 已封存詳情頁共用同一個摘要函式，套同一條規則。
- 例：add-ask-user-tool 有 4 條 `[M]`（4.3、5.8、6.9、7.6）。只勾 4.3 → 提示框標題「3 個手動任務」，列出 5.8、6.9、7.6；四條全勾 → 提示框缺席；兩種情況「手動」數字磚都是 4。
- 規格改寫（desktop-app 1 條）：「任務群組標題與章節標籤同款式」的提示框條文改為只計未勾選的手動任務、全部勾選時缺席；改寫情境「數字磚與手動提示框」補上全部勾選後提示框缺席，並新增「部分勾選時提示框只列未勾者」情境。

相容性影響：只改 desktop 與共用 UI 套件的任務文件閱讀卡畫面。CLI 人眼輸出與 `--json`、tasks.md 格式、引擎、server API 全部不變；既有使用者不需遷移。

## Non-Goals

- 「手動」數字磚改為剩餘數：破壞數字磚清點總數的一致規則。
- 全部勾完時改顯示「手動任務都完成了」的提示框：不提供新資訊，只多一個框。
- 提示框說明文字（「要由你親自做完再勾……」）、提示框色調、「前往」鈕行為：不變。
- 任務列的手動徽章與淡底、看板「待手動」章：已依勾選狀態運作，不在範圍。
- tasks.md 格式、引擎的 manual 欄位與寫碼完成度判定：不變。
- server-web：變更詳情頁與已封存詳情頁目前只有 desktop 渲染，不在範圍。

## Alternatives Considered

- 只改程式、不改規格——規格與行為脫節，審查與驗證關卡會抓到。
- 另做「偵測勾選」的機制（監聽勾選事件再剔除列）——頁面在勾選寫回與外部變更時本來就重讀 tasks.md，摘要從解析結果直接算即可，多一層機制沒有收益。
