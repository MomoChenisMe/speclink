## Summary

桌面 app 任務文件的任務列，展開或收合改由勾選狀態決定：沒勾的任務展開、已勾的任務收合，勾選狀態一變就跟著翻；只改畫面，不動任何 markdown 檔。

## Motivation

目標使用者是在 desktop 透過 AI 代理跑 SDD 流程的開發者（PO／PM 亦同），情境是 apply 前後在變更詳情頁的任務文件看「還剩哪些事、每件事要做到什麼程度」，以及在已封存詳情頁回看任務。

- 現在所有任務列一律從收合開始，只露出序號與標題。沒勾的任務，內文與驗證就是接下來要做的事，每條都要多點一下列尾箭頭才看得到。
- 已勾的任務是做完的事，看標題就夠；把它們收合能讓沒勾的任務更顯眼。

由討論 task-row-expand-by-done 定案。正式規格「任務群組標題與章節標籤同款式」現在寫明任務列預設只顯示標題層，那是上一場討論 detail-content-redesign 為了「第一屏看得出層次」定的；這個理由對已勾任務仍成立，對沒勾任務不成立，所以只在沒勾的任務上翻轉預設。

## Proposed Solution

- 預設展開與否看勾選狀態：沒勾、且有內文或驗證的任務一開始就展開；已勾的任務一開始就收合；沒有內文也沒有驗證的任務本來就沒有展開鈕，不受影響。
- 勾選狀態一變，展開狀態就跟著變：勾下去當下收合、取消勾選當下展開。不論勾選狀態從哪裡改變都一樣——點列勾選、工具列「全部已完成」（全部收合）與「重置任務」（全部展開）、agent 經 CLI 勾掉任務後檔案變更觸發的重新載入。
- 手動點列尾箭頭照樣可以展開或收合，效力持續到這條任務的勾選狀態下次改變為止；任務列以任務的穩定識別記錄展開狀態，拖曳排序後手動選擇跟著原本那條任務走。
- 已封存詳情頁（唯讀）用同一條規則；拖曳時浮起的那一列只畫標題層，不變。
- 例：群組內 3.1 沒勾（有內文）、3.2 已勾（有內文）、3.3 沒勾（無內文）→ 打開頁面時 3.1 展開、3.2 收合、3.3 沒有箭頭；手動收起 3.1 → 維持收合；接著勾 3.1 → 收合；再取消勾 3.1 → 展開。
- 規格改寫（desktop-app 1 條）：「任務群組標題與章節標籤同款式」的「任務列預設 SHALL 只顯示勾選框、序號、標題、D 籤與手動籤」改為依勾選狀態決定預設展開；改寫情境「任務列三層與展開」，並補「勾選狀態改變時展開跟著翻」與「手動展開收合持續到勾選狀態改變」兩個情境。

相容性影響：只改 desktop 與共用 UI 套件的任務列畫面。CLI 人眼輸出與 `--json`、tasks.md 格式、引擎、server API 全部不變；既有使用者不需遷移。已知代價：剛開工的變更（例如 0/10）打開時整片展開，頁面變長——討論中使用者已接受。

## Non-Goals

- tasks.md 格式與引擎：不加任何標記或欄位來記住展開狀態，展開狀態只活在畫面上。
- 記住手動選擇跨頁面：離開任務文件再回來，展開狀態依勾選狀態重新決定。
- server-web：任務列元件目前只有 desktop 使用，不在範圍。
- 「下一個未完成」與手動提示框的「前往」：只捲動與高亮，不另外改展開狀態。
- 拖曳浮起列、群組卡、數字磚與手動提示框：不變。

## Alternatives Considered

- 只在打開頁面時套用、勾選後不自動收合——使用者明說要「勾選後再收合」。
- 手動選擇永遠優先於勾選狀態——勾選後就不會自動收合，與需求矛盾。
- 已封存頁一律收合——多一條例外，且現行規格本來就寫唯讀時展開收合照常。
- 併入進行中的 doc-tiles-fill-and-round-order——那個變更範圍是數字磚與討論輪順序、已做到只剩手動驗收，併入要重開它的範圍。
