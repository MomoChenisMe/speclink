## MODIFIED Requirements

### Requirement: 已知缺口逐項列出

<!-- BEFORE: 「至少要列」的清單含「沒有把封存的討論記錄搬回來的動詞」「沒有寫入詞彙表的動詞」，也沒有規定已解決的缺口放哪裡 -->

專案能力狀態（中英兩版）SHALL 有「已知缺口」一節，逐項列出這個系列刻意延後或不做的項目，每項 SHALL 說明影響誰與目前的替代做法。清單 SHALL 至少含：沒有本機規格檔的內嵌宿主不能用需要 checkout 的動詞；`task done` 不替宿主收集改了哪些檔；用 Node 內嵌的宿主沒有推送事件；baseline 與 manual 兩支技能在遠端專案被拒絕；連到沒有宣告技能的舊版 Server 時用本機的範本；已封存的文件不能改自由欄位，也沒有依欄位查詢的動詞；CLI 沒有匯入匯出的動詞；沒有 JavaScript 寫的儲存接口範例；示範用 server 只支援單一實例；規格放在 checkout 之外的本機位置（`spec_dir` 不檢查絕對路徑與 `../`，行為未定義）；唯讀引用另一套規格；遠端專案的自訂產出流程；嚴格一致的讀取快照；多個宿主實例之間的推送事件。已經由後面的變更解決的缺口 SHALL 從這一節的表格移到表格下方列出已解決缺口的清單，每項 SHALL 寫明它已經解決與現在的做法，SHALL NOT 直接刪除，也 SHALL NOT 留在表格裡。「沒有把封存的討論記錄搬回來的動詞」與「沒有寫入詞彙表的動詞」兩項已經由 speclink discuss restore 與 speclink language replace 解決，SHALL 列在表格下方的那份清單，SHALL NOT 列在表格。README 的「目前狀態」SHALL 用一行連到這一節，SHALL NOT 複製清單。路線圖 SHALL 為其中屬於之後方向的項目提供落點。

#### Scenario: 整合者在採用前看得到缺口

- **WHEN** 整合者開啟專案能力狀態的已知缺口一節
- **THEN** 可見每一項缺口、它影響誰，以及目前的替代做法

#### Scenario: 缺口與提案一致

- **WHEN** 把前二十個變更封存後的提案裡寫的「已知缺口」與討論結論的延後項目，逐項對照這一節
- **THEN** 每一項都在這一節，或在文件裡註明已經由後面的變更解決

#### Scenario: 已經解決的缺口留在表格下方的清單

- **WHEN** 讀者在專案能力狀態（中英任一版）的已知缺口一節找「把封存的討論記錄搬回來」與「寫入詞彙表」
- **THEN** 表格裡沒有這兩項；表格下方的清單各有一條，寫明已經解決，並分別指出 speclink discuss restore 與 speclink language replace
