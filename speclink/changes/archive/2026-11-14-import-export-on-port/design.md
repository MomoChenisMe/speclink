## Context

- **儲存契約**只有列出、讀取、提交三個函式，明寫不含匯入匯出。列出可以用空的前綴取得整個範圍的鍵；提交可以帶任意多筆「必須不存在」的寫入與事件，全部成功或全部不做。
- **舊儲存層的匯入匯出**：TeamStore 有 `export`（回傳整包）與 `import`（只建立，或覆寫）。包的每份文件用九種文件種類之一標示，另有格式版本、範圍與專案版本號。
- **線上**：`POST /import` 收 `ImportBundle`（線上型別，九種文件種類的標示，嚴格拒絕未知欄位），示範用 server 檢查格式版本、範圍相符、逐份的摘要，再呼叫 TeamStore 的匯入（只建立）；非空的範圍回 `refused`。這條路由在宿主套件搬移時留在 server。沒有線上的匯出；匯出只有管理介面的下載與備份指令。
- **大小**：示範用 server 的轉交層讀本文的上限是 32 MiB，匯入的路由用同一個值。宿主套件的設定裡沒有任何大小。
- **Speclink Desktop**：`migrate_workspace` 用引擎的儲存介面把本機的規格資料夾組成 `ImportBundle` 再呼叫匯入。它收集進行中變更的 metadata 與 artifact、正式規格、討論、已封存的變更、流程設定、詞彙表；沒有收集 evidence 與看板順序，雖然線上的型別有這兩種。本機的看板順序存在各變更與討論自己的順序鍵裡，不是一份文件。
- **鍵與文件種類的對照**今天在過渡用的 TeamStore 轉接裡（把鍵換成文件種類、把文件種類換成鍵）；把鍵解析成種類的函式在儲存視圖裡。
- 匯入今天不產生事件，只在成功後直接通知事件串流。

限制：

- 討論的裁定：兩個門都能用；上限由宿主設定；不做壓縮；匯入維持只能進空的範圍。
- 儲存契約不加第四個操作。

## Goals / Non-Goals

**Goals:**

- 任何實作三個函式的儲存都能匯出與匯入，不需要額外的實作。
- 內嵌的宿主能服務 Speclink Desktop 的搬移，也能自己呼叫匯出與匯入。
- 匯入是一次提交；失敗時範圍仍然是空的。
- 搬移不遺失 evidence 與看板順序。

**Non-Goals:**

- 合併與覆寫、壓縮與串流、CLI 的動詞、示範用 server 的備份、版本歷史的搬移。

## Decisions

### D1: 匯出

`speclink_host::transfer::export(port, scope) -> Result<ScopeBundle, TransferError>`：

1. 以空的前綴列出，得到全部的鍵與範圍版本號 V。
2. 分批讀取（每批最多 200 個鍵），收集內容。列得到但讀不到的鍵代表範圍在中途被改動。一次讀取回的份數和要求的鍵數不同，是儲存的失敗（原樣回報，不重試）：少了文件的包不是備份。
3. 再列出一次；版本號仍是 V 而且第 2 步沒有讀不到的鍵 → 完成。否則從第 1 步重來，最多 3 次；仍然不穩定 → 回報「暫時無法使用」，訊息說明範圍在匯出期間持續變動。HTTP 入口也把這段訊息交給用戶端：儲存的其他暫時失敗一律換成固定的文字（driver 的訊息可能帶出宿主的位址），這一種的原因是範圍，不是宿主的儲存。
4. 回傳 `ScopeBundle { format_version: 2, scope_version: V, documents }`，每份文件是鍵、內容、內容摘要（SHA-256，和既有的摘要函式相同），依鍵排序。

空的範圍匯出成沒有文件的包，不是錯誤。

成本：N 份文件是 2 次列出加 N/200 次讀取。參考量（約 2300 份文件、22 MB）是 2 次列出加 12 次讀取。

- **否決：一次讀取全部的鍵** — 宿主的儲存常把讀取對成一個帶 IN 清單的查詢，上千個鍵的清單在一些資料庫有上限。
- **否決：不檢查中途的變動** — 備份會拿到新舊混合的內容。

### D2: 匯入

`speclink_host::transfer::import(port, scope, actor, bundle, at) -> Result<ImportReport, TransferError>`，依序：

1. 格式版本不是 2 → 拒絕（第一版在進入這個函式之前由 D3 換成第二版）。
2. 每份文件：鍵符合契約的格式；鍵是引擎認得的命名規則之一（用儲存視圖既有的鍵解析，而且解析出的名稱要能由引擎建立鍵的函式組回同一個鍵——所以 `changes/archive/…` 這種命名規則不允許的變更名稱不算）；摘要等於內容的摘要；沒有重複的鍵；鍵是看板順序時，內容不超過看板順序寫入的大小上限（用寫入路由的同一個檢查——否則匯入會留下一份那條路由再也寫不回去的順序）。任何一項不過 → `InvalidBundle`，訊息指出第一個有問題的鍵與原因，不呼叫儲存。
3. 以空的前綴列出；有任何鍵 → `NotEmpty`。
4. 一次提交：每份文件一筆寫入，預期「必須不存在」；事件一筆 `scope-imported`，payload 是 `{ documents: <份數> }`；命令標籤 `scope-import`；操作者取自呼叫端。
5. 提交回報衝突（第 3 步之後有人寫入了包裡也有的鍵）→ `NotEmpty`。其他儲存失敗原樣回報。第 3 步之後有人寫入包裡沒有的鍵時，提交不會衝突：匯入成功，那份文件留著（見「稽核結論」的已知限制；規格寫明這個邊界）。
6. 回傳新的範圍版本號與份數。

只有一次提交，所以沒有半套狀態。包裡沒有文件時，不提交，回報 0 份與目前的版本號。

「引擎認得的鍵」這個檢查，擋的是把任意的鍵塞進宿主的儲存。它不檢查內容的格式：壞的 metadata 匯入後會在讀取時回報，和今天相同。

### D3: 包的兩個版本

`speclink-protocol`：

- 第二版（新增）：`{ "formatVersion": 2, "documents": [ { "key", "content", "digest" } ] }`。匯出的回應多一個 `scopeVersion`；匯入的請求可以帶它（不看它的值），所以匯出的回應可以原樣當成匯入的請求。型別是 `speclink-protocol` 的 `ScopeBundle` 與 `BundleDocument`，`transfer` 模組直接用這兩個型別，不另外定義一份。
- 第一版（既有的 `ImportBundle`）：不改。
- `POST /import` 的本文先讀 `formatVersion` 再決定用哪個型別解析。其他值 → `refused`（既有的錯誤）。
- 本文不是 JSON → 400 `invalid_argument`。本文是 JSON 但不是包的形狀（缺欄位、多了不認得的欄位，例如 `mode`；或根本不是物件，例如把欄位的值依序放進陣列）→ 422 `invalid_argument`。解析失敗的訊息是解析器的文字（截到 120 個字元）加上行與列。入口其他路由對這種本文回 400；匯入維持 422，因為這是它一直以來的狀態碼（原本由示範用 server 的框架回覆），既有的整合測試斷言它。

第一版換成第二版（`transfer::from_first_version`）：把九種文件種類換成鍵，用既有的建立鍵的函式。這段對照今天在 TeamStore 的轉接裡；把它搬到 `transfer` 模組成為公開的函式，轉接改呼叫它，不留兩份。第一版裡的範圍與專案版本號：範圍必須等於請求的範圍（既有的檢查，保留）；專案版本號忽略（既有行為）。換不成鍵的文件（名稱含 `/` 等）→ `invalid_argument` 並指出該文件。

回應：既有的 `ImportReportResponse` 逐份列出文件種類與結果（由 `transfer::first_version_report` 組出，入口與 Desktop 共用）。第一版的請求照舊回這個型別；第二版的請求回 `{ "scopeVersion", "documents": <份數> }`。

### D4: 兩個門

Rust（`HostKit`）：

- `export_scope(&self, caller) -> Result<ScopeBundle, ExecError>`
- `import_scope(&self, caller, bundle) -> Result<ImportReport, ExecError>`

兩者的流程和執行命令相同：先問執行前掛鉤——命令名稱 `scope-export`（參數空物件）或 `scope-import`（參數 `{ documents, bytes }`：份數與內容的總位元組數；不含內容）——再執行；匯入成功後通知提交後掛鉤（命令名稱 `scope-import`、新的版本號、那一筆事件）。掛鉤拒絕時以 `refused` 結束，儲存不變。

這兩個名稱不是引擎命令，所以不進線上歸屬表；它們和看板順序的寫入一樣，是「不經引擎命令的文件讀寫」。

HTTP 入口：

- `GET /export`：回傳第二版的包。需要寫入的能力（`can_write`）。路由和 `export_scope` 走宿主套件的同一個內部函式（`HostKit::export_asked`：先問掛鉤再匯出，把匯出自己的失敗和掛鉤的拒絕分開回傳），這樣「範圍持續變動」能對成帶原因的 503，問掛鉤與匯出的流程也只有一份。
- `POST /import`：需要寫入的能力。本文超過上限（D5）→ 413；之後依 D3 解析並呼叫 `import_scope`。
- 錯誤的對映：`InvalidBundle` → 400 `invalid_argument`；`NotEmpty` → 409 `refused`；格式版本不認得 → 409 `refused`；儲存的失敗照既有的對映。

匯出需要寫入能力的理由：它一次交出整個範圍；示範用 server 今天只讓管理者匯出。宿主要讓唯讀的人也能匯出時，自己呼叫 `export_scope`。

Node：`host.exportScope({ identity, scope })` 回傳包的物件；`host.importScope({ identity, scope, bundle })` 回傳 `{ scopeVersion, documents }`。`bundle` 可以是第一版或第二版。失敗時的錯誤碼：`invalid_argv`（包不合格）、`refused`（非空、掛鉤拒絕）、儲存的三種。

### D5: 大小上限

`HostKitOptions` 新增 `import_limit_bytes: Option<usize>`，沒有給時是 32 MiB（`33_554_432`）。

- HTTP 入口在 `POST /import` 先比本文的長度，超過就回 413，不解析。
- `import_scope`（直接呼叫）比的是內容的總位元組數，超過時 `InvalidBundle`。
- 入口拿到的是宿主的框架已經讀完的本文，所以宿主的框架自己的本文上限必須不小於這個值；這一點寫進型別的註解與文件。
- Node：`createHost({ limits: { importBytes } })`。值不是正整數時 `createHost` 同步拋出錯誤。
- 示範用 server：傳輸層的上限與這個設定用同一個常數。

匯出沒有上限：資料是宿主自己的儲存裡的，大小由它決定。

### D6: Speclink Desktop 的組包

`build_import_bundle` 的兩個補充：

- **evidence**：每個進行中的變更，引擎的儲存介面讀得到 evidence 時加一份。已封存變更的 evidence 是封存文件集的一份；確認既有的「已封存變更的全部文件」有沒有包含它，沒有就補上。（實作時確認：既有的收集只含資料檔與 schema 列出的 artifact，不含 evidence；已補上。）
- **看板順序**：從各變更的 metadata 與各討論記錄讀出順序鍵，組成看板順序文件（格式是 `speclink-protocol` 既有的型別），至少有一個順序鍵時加進包裡。變更的 metadata 裡的 `board_rank` 原樣留著（遠端不讀它，留著無害，搬回本機時還在）。

Desktop 改送第二版：把收集到的文件換成鍵（用 D3 公開的對照）。握手之後先送第二版；Server 以「格式版本不認得」拒絕時，改送第一版重試一次（舊版 Server）。兩版的內容來自同一次收集。

「不認得」在線上有兩種樣子，兩種都改送第一版：

- 照協定：`refused`，訊息以 `transfer::UNSUPPORTED_VERSION` 的固定用語開頭。協定沒有這種拒絕專用的 reason，所以用戶端看訊息；入口組訊息與用戶端判斷用同一個常數。要完全不靠訊息文字，得在錯誤信封加欄位，那是協定的變更，不在這個變更的範圍。
- 已發布的舊版示範用 server（0.12 與更早）：它的框架在處理函式之前就以 422 拒絕第二版的本文，因為本文缺第一版必填的欄位；回應不是錯誤信封。所以用戶端把 422 也當成「不認得」。

其他的拒絕（例如範圍不是空的）不重送。

搬移結果回給畫面的形狀不變：第二版成功時，Desktop 用收集到的文件清單組出和第一版相同的逐份回報（畫面顯示份數）。

組包的邏輯留在桌面的 Tauri 殼（它已經在那裡，而且只有 Desktop 用）；只把「文件種類換成鍵」共用。

- **否決：這次順便做 CLI 的匯入匯出動詞並把組包搬進共用的 crate** — 沒有需求來源；列為已知缺口。

### D7: 示範用 server

- 宿主套件的路由表加入 `/import` 與 `/export`，所以轉交的處理函式不再把 `/import` 留給 server。server 的匯入處理函式與它對 TeamStore 匯入的呼叫移除。
- 建立宿主套件時傳入匯入的上限（既有的常數）。
- 匯入成功後對事件串流的通知，改由既有的提交後掛鉤觸發（和其他寫入相同），不再由路由另外呼叫。
- 留在 server 的專案路由只剩事件串流（GET）。寫入檢查的中介層留著（fail-closed：之後有人在這裡加寫入路由時預設要 editor）；它原本把解析好的 binding 交給匯入的處理函式，這個交接已經沒有人讀，連同 `Binding` extractor 裡對應的取用一起移除。
- 管理介面的匯出下載、備份與還原不動。

## Implementation Contract

**行為**

- 對任何通過合格測試的儲存：匯出一個範圍，再把得到的包匯入另一個空的範圍，兩個範圍列出的鍵相同、每份文件的內容相同。
- 匯入非空的範圍、摘要不符、鍵不是引擎認得的規則、重複的鍵：各自被拒絕，目標範圍沒有任何變動。
- 匯入成功時儲存收到正好一次提交，帶一筆 `scope-imported` 事件。
- 示範用 server：既有的匯入整合測試（第一版的包）不改斷言就通過；Speclink Desktop 既有的搬移整條鏈測試通過，而且遠端多了 evidence 與看板順序。
- 宿主以較小的上限建立宿主套件：超過的匯入得到 413，範圍不變。
- 執行前掛鉤對 `scope-import` 回答拒絕：匯入以 `refused` 失敗，範圍不變。

**介面與資料形狀**

- Rust：`speclink_host::transfer::{export, import, ScopeBundle, BundleDocument, ImportReport, TransferError, key_of_document, from_first_version, first_version_report, UNSUPPORTED_VERSION}`；`HostKit::{export_scope, import_scope}`；`HostKitOptions.import_limit_bytes`。
- 線上：第二版的匯入包；`GET /export` 的回應；第二版匯入的回應。第一版不變。
- Node：`host.exportScope`、`host.importScope`、`CreateHostOptions.limits.importBytes`。

**失敗的樣子**

| 情況 | HTTP | 直接呼叫 |
|---|---|---|
| 本文或內容超過上限 | 413 | 包不合格 |
| 格式版本不認得 | 409 `refused` | 包不合格 |
| 本文是 JSON 但不是包的形狀（缺欄位、多了欄位、不是物件） | 422 `invalid_argument`（既有的狀態碼） | 不適用 |
| 本文不是 JSON | 400 `invalid_argument` | 不適用 |
| 摘要不符、鍵不合格、不認得的鍵、重複的鍵、看板順序超過上限 | 400 `invalid_argument` | 包不合格 |
| 第一版的範圍與請求不符 | 409 `refused`（既有） | 不適用 |
| 目標範圍不是空的（含提交時發現包裡的鍵已被寫入） | 409 `refused` | `refused` |
| 沒有寫入的能力 | 403 | 不適用（宿主自己決定誰能呼叫） |
| 掛鉤拒絕 | 409 `refused`，宿主的原因 | `refused` |
| 匯出期間範圍持續變動 | 503 `unavailable`，訊息說明原因 | 暫時無法使用 |
| 儲存的讀取回的份數與要求不同（匯出） | 500（儲存失敗） | 儲存失敗 |

**驗收**

- `cargo test -p speclink-host --test transfer`：用記憶體版儲存涵蓋 D1、D2、D3 與上表；往返的測試用本專案的規格資料夾當資料（沿用成本測試的載入方式）。
- `cargo test -p speclink-host --test http_door`：兩條路由、上限、能力、掛鉤。
- `cargo test -p speclink-server`：`import_api` 既有的測試不改斷言；新增 `GET /export` 的測試與「匯入後事件串流收到事件」。
- `cargo test -p speclink-desktop`：組包含 evidence 與看板順序；第二版失敗時退回第一版。
- Node：`transfer.spec.ts`。

**範圍**

- 在範圍內：上面列的介面、Desktop 的組包、示範用 server 的匯入改接。
- 不在範圍內：`speclink-core`、`speclink-cli`、store crates、備份與還原、使用者文件。

## Risks / Trade-offs

- [回歸對照] 匯入的路由換了實作。→ `import_api` 的既有測試逐條涵蓋（只建立、非空拒絕、reader 拒絕、過大、沒有半套狀態、匯入後各讀取面可讀）；不改斷言。
- [回歸對照] 匯入多了一筆事件。→ 刻意的變更；事件串流的測試新增一條。
- [提交的大小] 一次提交帶幾千筆寫入與幾十 MB。→ 宿主的儲存在一個交易裡寫入；參考量用記憶體版儲存與過渡的轉接各跑一次並記下耗時。轉接底下的舊 driver 若有單次寫入的限制，在任務裡回報，不自行分批（分批會破壞「不留半套」）。
- [記憶體] 整包在記憶體裡出現兩到三份（本文、解析後、提交）。→ 上限由宿主設定；預設值和今天相同。
- [跨平台] 沒有路徑與程序呼叫；鍵一律用 `/`。Desktop 組包時本機路徑換成鍵沿用既有的轉換。
- [匯出的一致性] 靠版本號重試，不是真正的快照。→ 三次都不穩定就失敗，不交出混合的內容。
- [儲存解耦] 匯入匯出從「每個 driver 各自實作」變成「用三個函式組出來」，宿主的儲存不用多做任何事。

## Migration Plan

沒有資料搬移。舊版的 Speclink Desktop 送第一版的包，照常可用。要退回時還原 commit。

## Open Questions

- 過渡用的 TeamStore 轉接能不能在一次提交裡寫入參考量的全部文件（三個舊 driver 各自的限制）。實作時量測；不能時停下來向使用者回報。
  - **已回答（2026-11-13 量測）：三個 driver 都能一次寫入。** 參考量是本專案的規格資料夾：2414 份文件、內容共 24,074,204 位元組、最大的一份 3,815,428 位元組。用未最佳化的測試建置、本機的 PostgreSQL 18 量測；「舊路徑」是改接之前 TeamStore 自己的匯入。

    | 儲存 | 匯入（一次提交） | 舊路徑的匯入 | 匯出 |
    |---|---|---|---|
    | 記憶體版儲存（不經轉接） | 0.8 秒 | — | 0.7 秒 |
    | SQLite（經轉接） | 2.1 秒 | 0.8 秒 | 1.8 秒 |
    | serverfs（經轉接） | 27.4 秒 | 23.3 秒 | 1.5 秒 |
    | PostgreSQL（經轉接） | 4.2 秒 | 1.8 秒 | 2.5 秒 |

  - 沒有任何一個 driver 有單次寫入的限制。經轉接的匯入比舊路徑慢（SQL 的兩個約 2.5 倍、serverfs 約 1.2 倍），多出來的時間在轉接：它在提交之前先載入整個範圍來回答「是不是空的」，再把每筆寫入轉成 TeamStore 的操作。轉接在變更 retire-teamstore-and-drivers 移除。
  - 要注意的一點：serverfs 的 27 秒接近用戶端 30 秒的請求逾時（`speclink-remote` 的 `Client`）。舊路徑就已經是 23 秒，這不是這次才有的；這個變更不改逾時。參考量再長大、或磁碟較慢時，對 serverfs 的搬移會逾時。
- 匯出的每批 200 個鍵是不是合適的值。實作時用參考量比較 100、200、500 三種的耗時，差異不大就維持 200。
  - **已回答（2026-11-13 量測）：維持 200。** 用同一份參考量（2414 個鍵），讀完全部文件的時間（五次取最快，未最佳化的建置）：

    | 儲存 | 每批 100（25 次讀取） | 每批 200（13 次） | 每批 500（5 次） |
    |---|---|---|---|
    | 記憶體版儲存 | 1.6 毫秒 | 1.6 毫秒 | 1.6 毫秒 |
    | SQLite（經轉接） | 736 毫秒 | 387 毫秒 | 148 毫秒 |
    | serverfs（經轉接） | 111 毫秒 | 59 毫秒 | 24 毫秒 |
    | PostgreSQL（經轉接） | 1655 毫秒 | 860 毫秒 | 332 毫秒 |

  - 直接實作儲存接口的儲存，三種大小沒有差別。經轉接的三個 driver，時間跟著「讀取的次數」走：轉接的每次讀取有固定成本（先確認範圍的版本），和每批幾個鍵無關。每批 500 在最慢的 PostgreSQL 上讓一次匯出少約半秒（匯出總共約 2.5 秒）。這個差距來自過渡用的轉接，它在變更 retire-teamstore-and-drivers 移除。
  - 維持 200 的理由：宿主的儲存把一次讀取對成一個查詢時，每個鍵常綁兩個參數（範圍與鍵）；200 個鍵是 400 個參數，500 個鍵是 1000 個，超過常見的 999 個參數上限。

## 稽核結論

對新增的介面（`transfer` 的函式、`HostKit` 的兩個方法與上限設定、兩條路由、Node 的兩個方法與 `limits.importBytes`）用 sharp-edges 的三個角度（故意使壞的人、照範例複製的開發者、搞混用法的開發者）檢查。日期：2026-11-13。

**確認沒有問題的項目**

- **鍵只能落在請求的範圍裡。** 提交只送到呼叫端的範圍；包裡沒有任何欄位能指定範圍。鍵先通過契約的格式（`..`、`.`、開頭或結尾的 `/`、空的段落、反斜線、控制字元都被拒絕），再通過命名規則。測試涵蓋 `..`、開頭的 `/`、反斜線、空字串、不認得的鍵。
- **第一版的包裡的範圍與請求不符時被拒絕**（409 `refused`）。第一版的專案版本號不被採用；第二版的 `scopeVersion` 不被採用。寫入的操作者一律取自呼叫端的身分，不取自包。
- **上限在解析之前生效。** HTTP 入口先比本文的長度；超過時不解析（測試用 33 MiB、不是 JSON 的本文）。很深的巢狀：JSON 解析器有深度上限（128 層），十萬層的 `[` 在解析時被拒絕，不會遞迴到底。
- **上限以內的本文，記憶體的用量有界。** 最壞情況是整包同時有本文、解析後的包與提交三份，約為上限的三到四倍。上限設成 0 時每一次匯入都被拒絕（安全的那一邊）。
- **匯出的路由要求寫入的能力**，`HEAD` 也是（它走 `GET` 的路由）。沒有寫入能力時儲存不會被呼叫。直接呼叫 `export_scope` 不檢查權限：誰能呼叫由宿主決定，型別註解寫明這一點。
- **掛鉤的參數不帶文件內容**：`scope-import` 只有份數與位元組數，`scope-export` 是空物件。事件的 payload 只有份數。
- **匯入失敗的每一條路徑都沒有寫入。** 全部檢查在第一次呼叫儲存之前；非空在提交之前；提交是全有或全無。測試逐條斷言：包不合格、超過上限、掛鉤拒絕時儲存沒有被呼叫；非空時沒有提交；提交衝突時包裡的文件一份都沒寫入。
- **匯出的重試有次數上限**（3 次），之後回報暫時無法使用。

**找到並在這個任務修正的問題**

1. **命名規則的檢查太寬。** 原本只看鍵「解析得出一種文件」。`changes/archive/<名稱>/…` 解析得出「名為 archive 的變更的 artifact」，但命名規則不允許變更叫 archive（那是本機放已封存變更的資料夾）：引擎自己寫不出這個鍵，包卻塞得進去，範圍裡會多出一個叫 archive 的變更。修正：鍵解析出的名稱要能由引擎建立鍵的函式組回同一個鍵。補測試。
2. **錯誤訊息會隨輸入變長。** 換不成鍵的第一版文件，訊息原本帶出整個名稱；本文的形狀不對時，JSON 解析器的訊息會把型別不對的那個值整個寫出來（一個 30 MB 的字串放在 `formatVersion` 就會得到 30 MB 的錯誤訊息）。修正：鍵、名稱與解析器的訊息一律截到 120 個字元；鍵另外跳脫控制字元。補測試。（品質關卡第 1 輪補上漏掉的一處：第一版的包「範圍不符」訊息裡的專案名與 repo 名。）

**已知的限制（沒有修，契約層級的）**

- **確認「範圍是空的」和提交之間有空窗。** 另一方在這段時間寫入的文件，鍵和包裡的任何一份相同時，提交會衝突，匯入以「範圍不是空的」被拒絕，沒有寫入。鍵和包裡的都不同時，提交不會衝突：匯入成功，範圍裡同時有包的全部文件與那一份別人的文件。兩次提交各自完整，沒有半套狀態；但「只匯入空的範圍」在這個空窗裡不成立。原因是儲存契約的提交只能對個別文件下預期，不能對整個範圍下預期。要關掉這個空窗得改儲存契約（提交可以帶「範圍版本必須是 V」），不在這個變更的範圍。實務上會同時對同一個空範圍動手的只有「兩次匯入同一個專案」（鍵相同，會被擋下）。規格「範圍的匯出與匯入」原本的字面沒有這個邊界；品質關卡第 1 輪後改成寫明它，並各有一個情境（鍵相同被擋下、鍵不同兩邊都留著）。
- **serverfs 的匯入時間接近用戶端的請求逾時**（見 Open Questions 的量測）。

**品質關卡第 1 輪的修正（2026-11-14）**

兩站第 1 輪找到 1 條必修與 15 條建議，全部處理。會改變行為的：

- **規格承諾得比實作多**（必修）。「匯入只接受空的範圍」在列出與提交之間的空窗不成立。程式修不了（見上面的已知限制），所以改規格：需求本文寫明邊界，情境拆成兩個。
- **匯出少文件卻不報錯。** 儲存的讀取回的份數比要求的少時，原本的配對會默默截短。現在是儲存的失敗。
- **不是物件的 JSON 本文**（例如陣列）原本落在「不是 JSON」（400）；現在和其他形狀不對的本文一樣是 422。
- **解析失敗的訊息**原本截短時連行列位置一起截掉；現在位置一定留著。訊息仍可能帶出型別不對的那個值的開頭（最多 120 個字元），型別註解改成照實寫。
- **匯入不檢查看板順序的大小上限**，匯入後那份順序再也寫不回去。現在匯入用寫入路由的同一個檢查。
- **第一版「範圍不符」的訊息**原樣帶出本文裡的名稱；現在截短並跳脫控制字元。
- **HTTP 的匯出在範圍持續變動時**原本回固定的「儲存暫時無法使用」；現在訊息說明原因。

不改行為的整理：匯入的事件只建一次（`import_with_events`）；第一版的逐份回報由一個函式組出（入口與 Desktop 共用）；Desktop 判斷「格式版本不認得」與入口組訊息用同一個常數；Desktop 的 `keyed_bundle` 併回呼叫處；Node 的三個入口共用建立宿主套件的那一段；`limits` 不認得的名稱只在原生層檢查，JS 只檢查原生層看不出來的兩件事（它必須是物件而不是陣列、數字必須是正整數）；示範用 server 測試的計數包裝併進既有的 `Racing`；示範用 server 移除沒有人讀的 binding 交接；讀本專案規格資料夾的測試不再把雜檔當成文件。
