# 桌面上的品質關卡

審查與驗證兩個品質關卡的狀態，會出現在看板卡片、變更詳情頁、已封存清單與已封存詳情頁四個地方。工單還沒結的時候，變更詳情頁多出「審查」「驗證」分頁，可以逐輪看工單寫了什麼。這一頁講桌面怎麼顯示這些狀態與工單，以及封存時遇到未結工單會發生什麼。兩個關卡的流程與蓋章本身，見[品質關卡總覽：審查與驗證](quality-stations.md)、[審查站](review.md)與[驗證站](verify.md)。

> [!NOTE]
> 桌面只呈現品質關卡的狀態與工單內容。審查、驗證分頁是唯讀的，沒有蓋章、放棄或追加輪的按鈕；蓋章請用 CLI 或請 agent 跑審查與驗證的技能。桌面上唯一會動到工單的地方，是封存時的三選項對話框（見下方）。

## 兩枚章怎麼看

- **審查章**是徽章形，**驗證章**是盾牌形。形狀代表關卡。
- 顏色代表狀態。同一狀態在兩個關卡用同一個顏色。
- 兩枚章並排時順序固定：審查章在前、驗證章在後。
- 「已審查」「已驗證」的蓋章用紫色系。紫色是品質關卡蓋章專屬，介面其他元素不用紫色，所以它和主色（進度條、分頁、連結籤）一眼可分，淺色、深色主題都一樣。看板卡片、變更詳情頁、已封存清單、已封存詳情頁四處用同一份配色。
- 把指標停在章上 300ms 會顯示狀態詞。提示出現後在同一組章之間連續移動，下一個提示立刻出現，不再等。中文介面用正典詞，見下表。

| 狀態 | 審查章 | 驗證章 | 顏色 |
| --- | --- | --- | --- |
| 沒有痕跡 | 無標示 | 無標示 | — |
| 工單未結 | 「審查中」 | 「驗證中」 | 藍 |
| 已蓋章 | 「已審查」 | 「已驗證」 | 紫 |
| 蓋章後內容又動了 | 「已審查·其後有變動」（降級樣式） | 「已驗證·其後有變動」（降級樣式） | 琥珀 |
| 封存時工單無章 | 「曾審查未通過」 | 「曾驗證未通過」 | 紅 |

前四種出現在看板卡片與變更詳情頁；最後一種只出現在已封存側。

## 看板卡片

變更卡依審查狀態與驗證狀態各渲染一枚行內小章，不增加文字列。沒有痕跡的關卡不顯示章。例如：

- 審查已蓋章、驗證已蓋章：卡片依序顯示審查章與驗證章，兩枚都是紫色，形狀不同。
- 審查沒有痕跡、驗證蓋章後內容又動了：卡片只顯示一枚降級樣式的驗證章，提示為「已驗證·其後有變動」。

卡片上其他標示見[看板與任務](desktop-board.md)。

## 變更詳情頁的「品質關卡」列

變更詳情頁左欄下方的「狀態」有三列，中間那列是「品質關卡」（版面見[看板與任務](desktop-board.md)）。品質關卡的章籤只出現在這裡，不出現在左欄上方的身分區。

- 審查或驗證有痕跡時，這一列以章籤呈現（圖示＋狀態詞），審查在前、驗證在後。
- 已蓋章的章籤旁直接寫出蓋章日期，例如「已審查 2026-10-12」。指標停在章籤上，提示顯示該關卡自己的蓋章日期與蓋章者的完整識別（含 email）。可視文字不出現 email。
- 工單未結（「審查中」「驗證中」）時只顯示狀態詞，沒有日期，指標停留也沒有提示。
- 兩個關卡都沒有痕跡時，這一列顯示灰字「尚未經過品質關卡」。
- 不論資料怎麼組合，詳情頁都不會出現水平捲軸。

| 情況 | 「品質關卡」列 |
| --- | --- |
| 審查 2026-10-12 蓋章、驗證 2026-10-13 蓋章 | 「已審查 2026-10-12」「已驗證 2026-10-13」 |
| 審查工單未結、驗證沒有痕跡 | 「審查中」，沒有日期、沒有提示 |
| 兩邊都沒有痕跡 | 「尚未經過品質關卡」 |

## 審查與驗證分頁

### 什麼時候出現

變更詳情頁左欄的「文件」節點在「排程」之後，有兩個看情況才出現的節點：

- 審查工單未結（審查中）時出現「審查」（英文介面為「Review」）。
- 驗證工單未結（驗證中）時出現「驗證」（英文介面為「Verify」）。
- 兩個都在時，審查在前、驗證在後，各自讀自己那一份工單，內容不會混在一起。
- 兩個都不是未結狀態時（包括已蓋章），文件節點維持提案、設計、任務、規格、排程五個，app 也不會去讀工單。

工單在節點出現時載入，載入中的樣子與其他文件相同。工單檔在外部變動時會自動重新載入：例如分頁開著時有人用 `speclink review add-round` 追加了第 3 輪，籤槽就變成「第 3 輪」，第 3 輪的卡展開、前兩輪收合。

看板刷新後，若該關卡已經不是未結狀態（例如工單蓋章後被刪除，狀態翻成「已審查」），對應節點就從左欄消失；你正停在那份文件時，詳情頁切回「提案」，「品質關卡」列的章籤也跟著改。

載入完成卻沒有工單時（檔案不存在、remote 的 server 回應找不到、讀取或解析失敗），分頁顯示「工單尚未抵達或已被刪除」，不跳錯誤，籤槽、數字磚與提示框都不出現。本地、worktree 與 remote 專案呈現同一套內容。

### 閱讀卡上方的摘要

- **籤槽**：「第 N 輪」（N 是最後一輪的序號），再加最後一輪的階段詞籤：首輪顯示「首輪」（英文「First pass」），複驗顯示「複驗」（英文「Re-check」）；沒有階段記錄的舊工單不顯示階段詞。
- **數字磚**：依序是「輪」（輪數）、「CRITICAL（末輪）」、「WARNING（末輪）」、「SUGGESTION（末輪）」，後三格是最後一輪各嚴重度的條數，標籤維持英文。
- **「可以蓋章」提示框**：最後一輪的 CRITICAL 與 WARNING 都是 0 時出現（提示樣式），內文是「末輪只剩 N 條 SUGGESTION，不擋章」（N 為 0 時寫「末輪無發現」），並點名用 CLI 或 agent 跑該關卡的蓋章指令，例如 `speclink review stamp`。最後一輪還有 CRITICAL 或 WARNING 時，沒有這個提示框。

### 每一輪一張卡

摘要下面依輪次由小到大，每一輪一張有邊框的卡。最後一輪預設展開，其餘預設收合。

**卡頭**：16px 粗體的「第 N 輪」（會列進本頁目錄）、階段詞、「範圍 N 檔」、這一輪的發現條數，以及各嚴重度的計數籤（條數為 0 的不出現）。例如收合的第 1 輪卡頭是「第 1 輪 · 首輪 · 範圍 3 檔 · 2 條」加一枚「WARNING 2」。

**展開後**依序是：

1. 「套用規則」列（只在這一輪有記錄規則時出現，見下一節）。
2. 範圍路徑，等寬字型，照原樣顯示，不做平台轉換。
3. 每一條發現：
   - 嚴重度色章：CRITICAL 紅、WARNING 琥珀、SUGGESTION 灰。
   - 軸向籤：描述以「Correctness:」「Standards:」或「Coherence:」開頭時，把那個詞拿出來做成一枚籤，描述去掉這個前綴；沒有前綴時沒有籤，描述照原樣。
   - 路徑（等寬字型）與描述原文，不翻譯、不截斷。
   - 描述以 `(accepted)` 結尾時，拿掉這段字並附一枚「已接受」籤；`(accepted)` 出現在句中時照原樣顯示。

一輪沒有任何發現時，卡內顯示「本輪無發現」。

| 這一輪的階段 | 發現的原文 | 顯示的描述 | 已接受籤 |
| --- | --- | --- | --- |
| 首輪 | Correctness: 未處理空清單 | 未處理空清單（軸向籤 Correctness） | 無 |
| 複驗 | Standards: 命名不一致 (accepted) | 命名不一致（軸向籤 Standards） | 有 |
| 沒有階段記錄 | Standards: (accepted) 語意不清 | (accepted) 語意不清（軸向籤 Standards） | 無 |

### 套用規則

審查工單的輪次若記錄了當時套用的審查規則，該輪卡展開後最上面多一列「套用規則」（英文「Rules applied」）。舊工單、驗證工單、複驗輪沒有這份記錄，就沒有這一列，直接從範圍路徑開始。審查規則本身怎麼設定，見[審查站](review.md)。

這一列預設收合，點列頭展開或收合（箭頭樣式與輪卡卡頭相同）。收合時列頭依「預設 code smell 清單是保留還是整份換掉」與專案規則的條數，顯示一段文字與條數籤。條數籤是嚴重度色章加數字（例如「CRITICAL 2」），條數為 0 的嚴重度不出現；沒有專案規則時沒有條數籤。下表以預設清單有 12 條為例：

| 規則設定 | 列頭文字 | 英文介面 | 條數籤 | 底色 |
| --- | --- | --- | --- | --- |
| 保留預設，沒有專案規則 | 預設 12 條 code smell | 12 baseline code smells | 無 | 一般 |
| 保留預設，CRITICAL 2 條、WARNING 1 條 | 預設 12 條＋專案規則 | 12 baseline smells + project rules | CRITICAL 2、WARNING 1 | 一般 |
| 換掉預設，SUGGESTION 1 條 | 只用專案規則（沒有套用預設 12 條） | Project rules only (baseline not applied) | SUGGESTION 1 | 一般 |
| 換掉預設，也沒有專案規則 | 整份換掉且沒有專案規則：只依 repo 文件審查 | Baseline replaced, no project rules: judged against repo documents only | 無 | 琥珀 |

展開後依序列出：

1. 保留預設時：一枚 SUGGESTION 色章、「預設 N 條 code smell」與 N 個 smell 名稱（等寬字型）；換掉預設時：一行「沒有套用預設 N 條 code smell」。
2. 每個有規則的嚴重度一組：嚴重度色章、「專案規則 N 條」與規則原文，不翻譯、不截斷。
3. 最後一行註記：「記錄首輪當時的設定；之後改了審查規則，這裡不會跟著變。」

N 是桌面內建引擎的預設 smell 數，不是寫死的數字；smell 名稱清單與設定頁審查規則頁的清單是同一份。

## 封存時遇到未結工單

從任何封存入口（卡片的封存鈕、詳情頁的封存動作、拖曳到封存落點）封存一個變更時，若該變更有未結的審查工單，會先彈出三選項對話框。你沒選之前不會封存。

| 選項 | 效果 |
| --- | --- |
| 「去蓋章」 | 導引你去完成審查收尾：開啟該變更的詳情頁。不論你當時在哪一頁，關掉詳情頁後回到的是看板。 |
| 放棄審查 | 等同先放棄審查工單（`speclink review discard`），再封存。 |
| 「照樣帶走」 | 等同帶著工單封存（`speclink archive --carry-review`）。對話框會說明已封存側將永久顯示「曾審查未通過」。 |

有未結的驗證工單時，同樣彈出驗證的三選項：前往完成驗證蓋章、放棄驗證、照樣帶走並警示永久標示。審查與驗證工單同時未結時，你要對兩種工單分別選定處置，全部選完才封存。

沒有未結工單的變更，封存行為不變。封存的前置守門與失敗訊息見[封存](archive.md)與[看板與任務](desktop-board.md)。

## 已封存側

已封存頁的清單與已封存詳情頁，依封存時的結局標示：

- 帶章的變更顯示「已審查」／「已驗證」（紫色）。
- 封存目錄裡留有工單、但沒有章的變更顯示「曾審查未通過」／「曾驗證未通過」（紅色）。
- 兩者皆無的變更沒有標示。
- 審查與驗證的結局標示可以並存。

已封存詳情頁的結局標示在左欄「狀態」列的品質關卡那一列，不在身分區。

**已封存詳情頁的工單分頁**：結局是「曾審查未通過」時，左欄「文件」節點在「規格」之後多一個「審查」；結局是「曾驗證未通過」時多一個「驗證」；兩者都有時審查在前。結局是已蓋章或沒有痕跡時，不出現對應節點，app 也不去讀工單。分頁內容、載入方式、空白時的文字都與上面的審查與驗證分頁相同，資料來自封存目錄裡的工單檔；remote 專案也一樣。分頁唯讀。

| 結局 | 已封存詳情頁的文件節點 |
| --- | --- |
| 曾審查未通過、已驗證 | 提案、設計、任務、規格、審查 |
| 已審查、驗證沒有痕跡 | 提案、設計、任務、規格 |

封存對話框與已封存側共用同一份配色對照，但對話框只用到「曾審查未通過」，不呈現已審查蓋章。
