# 認識資料：變更、討論與規格

Speclink 的資料都是純文字檔，放在專案的規格資料夾（預設是 `speclink/`）。你不用打開 Speclink 也能讀寫它們，每一次變動都會出現在 git diff 裡。這一頁介紹資料夾長什麼樣、一個變更會經過哪些狀態、討論記錄與變更怎麼連在一起。

## speclink 資料夾

本地模式的 `speclink/` 內容全是 Markdown 與 YAML：

| 路徑 | 放什麼 |
| --- | --- |
| `specs/<capability>/spec.md` | 正式規格。每個 capability 一份，是「現況唯一真相」 |
| `changes/<名稱>/` | 進行中的變更。裡面有提案、設計、任務清單與 delta 規格 |
| `changes/archive/` | 已封存的變更 |
| `config.yaml` | 工作流政策與專案設定，見[工作流政策與設定](policy-config.md) |

Speclink 在這些產物之外多加了兩樣東西：

- `discussions/`：討論記錄，每份一個 `.md` 檔。已封存的討論在 `discussions/archive/`。
- 每個變更資料夾裡的 `.meta.yaml`：這個變更的狀態檔。

> [!NOTE]
> 這種可攜性只適用本機專案。遠端專案的正式規格由 Server 持有，checkout 裡沒有規格檔。見 [remote 模式總覽](remote-overview.md)。

可以從 OpenSpec 專案匯入，但只能單向：在 OpenSpec 專案執行 `speclink init`，會把 `openspec/` 搬到 `speclink/`，之後 OpenSpec CLI 就讀不到這個專案。舊版 Speclink 建立的專案仍是 `openspec/` 資料夾與 `.openspec.yaml` 狀態檔，怎麼搬過來見[規格資料夾與舊佈局遷移](spec-folder.md)。

## 變更的生命週期

變更的狀態真相只有一個地方：它自己資料夾裡的 `.meta.yaml`。這個檔案記錄三站的章：

| 站 | 記錄什麼 | 何時寫入 |
| --- | --- | --- |
| 建立 | 建立時間、建立者、建立工具 | 變更建立時 |
| 開工 | 開工時間、開工者 | 第一次標記開工、或第一次完成任務時 |
| 封存 | 封存時間、封存者 | 封存時 |

封存不會剝掉開工站的欄位。三站的章會一起留在封存目錄裡。

**建立者的識別**：從帶有使用者識別的環境建立變更時（例如把 Speclink 內嵌進自己系統的宿主），狀態檔除了建立者，還多一行建立者的識別，`speclink new change` 與 `speclink discuss promote` 都會寫。本機 CLI 以 git 身分建立時不寫這一行；既有的變更不會事後補上。桌面 app 的建立者篩選靠它把同一個人的卡片歸在一起，見[看板與任務](desktop-board.md)。

**就緒時間**：一次完成任務讓全部任務（至少一個）都勾完時，狀態檔多一行就緒時間。`speclink task done` 與桌面 app 的勾選、「全部已完成」都會寫；之後再次全部勾完時換成新的時間，檔內只留一行。取消勾選不會清掉這一行；直接編輯 tasks.md、整份寫回任務清單或匯入，都不會寫這一行，事後也不補。就緒日只在目前全部任務都勾完時才輸出，所以取消勾選一個任務後，桌面 app 詳情頁出身行的「就緒」那一段就不見了。寫這一行失敗時，任務不會被勾選，指令以非零結束碼結束並說明原因；排除原因後重試同一個指令即可。

**時間怎麼記、怎麼顯示**：新寫入的時間（建立、開工、就緒、認領、審查章、驗證章、封存）都是帶本機時區、精確到秒的時戳，例如 `2026-10-21T14:05:00+08:00`。對外輸出只給日期部分：CLI 的一般輸出與 `--json`（例如 `speclink show`、`speclink list --json`、drift 報告）、server 的回應與桌面 app 都只顯示 `2026-10-21`。所以同一天寫入的舊式純日期記錄與新式時戳記錄，輸出完全相同。既有的純日期記錄不會被改寫。變更放了幾天（過期判定）也只看日期部分。值既不是日期也不是時戳時（例如 `someday`），照原樣輸出，也不計算過期天數。

**封存時間**：封存成功時，封存目錄裡的狀態檔多一行封存時間。它與封存目錄名的日期前綴、正式規格上的更新時戳，取自同一個時刻。封存守門拒絕時不寫這一行。上一次封存在搬移資料夾時失敗、留下了一行封存時間的話，下次封存成功會換成新的時間，檔內只留一行。沒有狀態檔的舊式變更照常封存，不會為了這一行新建狀態檔。

狀態檔還可以有一行「前置變更」（`depends_on`）：逗號分隔的變更名清單，意思是這個變更要等那些變更先落地。這一行由 `speclink change depends` 寫入，沒有這一行就是沒有依賴。有沒有這一行，`speclink list` 與 `speclink status` 的輸出都一樣，前置只影響 `speclink plan` 算出來的順序與波次。見[執行順序：plan 與依賴](plan.md)。

**產出流程那一行**：狀態檔的 `schema:` 那一行指名這個變更用哪一個產出流程，換法見[產出流程 schema 管理](schemas.md)。這一行的值是空的時，視同沒有這一行：這個變更照預設的 spec-driven 執行。進行中與已封存的變更都一樣；CLI、Speclink Desktop、Server 與把 Speclink 內嵌進自己系統的宿主，都這樣讀。讀取不會改寫狀態檔，檔案內容一個字元都不變。

| 狀態檔裡的 `schema` | 這個變更的產出流程 |
| --- | --- |
| 沒有這一行 | spec-driven |
| `schema: ~` | spec-driven |
| `schema: ''` | spec-driven |
| `schema: '   '`（只有空白） | spec-driven |
| `schema: no-spec-change` | no-spec-change |
| `schema: nope`（沒有這個產出流程） | 找不到。需要產出流程的指令照舊失敗，錯誤訊息含 `Schema not found: Schema 'nope'` |

較早的工具可能留下 `schema: ''`。以前這樣的變更被讀成名為空字串的產出流程，`speclink status` 這類指令會以 `Schema not found: Schema ''` 失敗；現在照 spec-driven 執行。

### 開工標記

有兩種方式讓變更進入「進行中」：

- 執行 `speclink in-progress add <變更名>`。
- 執行 `speclink task done` 完成任何一項任務。這會在同一個動作裡順手蓋開工章。

開工章只蓋一次。已經開工的變更再標記或再完成任務，章不會變。狀態檔裡沒有開工欄位的變更（例如較早建立的），視為還沒開工；所有指令照常運作，不會出現警告。

> [!NOTE]
> `speclink in-progress add` 對不存在的變更名會靜默成功：沒有輸出、不寫任何檔案。這是刻意保留的既有行為。打錯名字時不會有錯誤提示。

遠端專案也一樣：`speclink in-progress add` 交給 Server 執行，開工者記的是 Server 認得的登入身分。輸出與本機專案相同：第一次標記、重複標記、變更名不存在，都沒有輸出、直接成功。變更不存在或早已開工時，Server 上什麼都不寫。

### 退回提案中

誤開工的變更可以退回「提案中」：

```
speclink in-progress remove <變更名>
```

只有「零工作痕跡」的變更才能退回：任務清單裡沒有任何已勾的任務，而且沒有任何觸及檔案的記錄。不符合時指令拒絕，stderr 列出已勾任務數與觸及檔案清單，並說明出路：已勾任務可以取消勾選後重試；觸及記錄要由人或 agent 判斷處理。這個指令沒有強制旗標。

與 in-progress add 不同，remove 對不存在的變更名會明確報錯。未開工的變更執行 remove 會直接成功、不寫檔。

### 廢棄變更

不做了的變更用 discard 刪掉：

```
speclink discard <變更名>
speclink discard <變更名> --force
```

discard 會刪掉整個變更資料夾與它的觸及記錄檔，並解開它與討論記錄之間的鏈結（見下文）。有工作痕跡的變更不帶 `--force` 時拒絕：stderr 提示有工作痕跡與 `--force`，任何檔案都不會動。

| 已開工 | 有已勾任務 | 不帶 --force 的結果 |
| --- | --- | --- |
| 否 | 否 | 放行 |
| 是 | 否 | 拒絕 |
| 否 | 是 | 拒絕 |
| 是 | 是 | 拒絕 |

成功時 stdout 報告已刪除的變更名，以及每份解鏈討論的 slug 與回退後的狀態。遠端專案同樣可以 discard：指令經 Server 執行，工作痕跡的守門、`--force` 的放行與輸出都和本機專案相同。被守門拒絕時，stderr 一樣指出工作痕跡與 `--force`，Server 上的變更不變。

### 封存

變更完成後用封存把 delta 規格併入正式規格，並把變更移到 `changes/archive/`。封存前有三道守門：任務完成度、不能在 linked worktree 內執行、品質關卡的章沒有失效。細節見[封存](archive.md)。

### 待重新反映

變更曾經反映某份討論的結論，而那份討論後來又重新下了結論時，變更會被標為「待重新反映」。這時：

- `speclink show <變更名>` 會列出待重新反映的討論。
- `speclink analyze <變更名>` 會出一條資訊性的發現，提醒你重新 ingest 以同步新結論。

重新反映完成、執行 seal 後，標記會清掉。

### 認領

遠端專案支援「認領」變更：

```
speclink claim <變更名>
```

認領後狀態檔記錄認領者與時間；你的身分帶有識別時，也一併記下識別。同一人重複認領直接成功；別人已認領時拒絕，並指出目前持有人。本機專案不支援認領。

判斷是不是同一人時，兩邊都有識別就只比識別：識別相同、顯示的名字不同，仍算同一人；識別不同、名字相同，算不同人。任一邊沒有識別時，才比名字。

**釋放認領**：要把認領放掉時執行：

```
speclink claim <變更名> --release
```

釋放會把認領記錄從狀態檔移除，其他欄位一個字元都不動。釋放之後，任何人都能重新認領這個變更。引擎不限定誰可以釋放：執行的人不必是當初認領的人。把 Speclink 內嵌進自己系統的宿主可以自己加限制；被擋下時，你看到的是宿主給的原因。

| 情況 | 結果 |
| --- | --- |
| 變更已被認領 | 成功。輸出 `✓ Released claim on change: <name> (was claimed by <holder>)` |
| 變更沒有被認領 | 仍算成功，不寫任何東西。輸出 `Change '<name>' is not claimed — nothing to release` |
| 狀態檔只剩認領時間、沒有認領者（這時認領會被拒絕） | 成功，殘留的記錄被清掉，之後可以重新認領。輸出 `✓ Released claim on change: <name>`，沒有括號那一段 |
| 變更不存在 | 拒絕，訊息指出找不到這個變更 |
| 本機專案 | 拒絕，訊息與 `speclink claim <變更名>` 被拒絕時相同 |

碰上版本衝突時，釋放會失敗並請你重跑。離線或登入失效時直接失敗，不排隊。

**查看誰認領了**：執行 `speclink show <變更名> --json`。被認領的變更會多帶一段認領記錄：認領者，以及有記錄時的識別與認領時間。連到不提供識別與時間的舊版 Server 時，只有認領者。沒有被認領的變更，輸出和以前完全相同。`speclink show` 的一般輸出與 `speclink list --json` 都不因認領而改變。

### 狀態檔壞掉時

`.meta.yaml` 存在但無法解析時，所有會改狀態的動作都會拒絕，並指出檔案位置與解析原因：標記開工、認領、釋放認領、完成任務、取消完成、新增產物、封存、廢棄。壞掉的狀態檔不會被當成「未開工」處理，discard 帶 `--force` 也一樣拒絕。修好檔案再重試。

## 討論記錄

討論記錄放在 `speclink/discussions/<slug>.md`。slug 是檔名，也是所有討論指令的把手。每份記錄有三個區段：Context（背景）、Rounds（輪）、Conclusion（結論）。輪只能往後追加，不能改寫既有的輪。

記錄的狀態有三種：

| 狀態 | 意思 |
| --- | --- |
| open | 討論中 |
| concluded | 已寫入結論 |
| promoted | 已轉出變更：至少連結了一個變更 |

狀態之外，記錄的 frontmatter 還可能有一行 `hold: true`，意思是「保留在途」：這份討論之後還要再轉出變更，引擎不要在最後一個變更封存時自動把它收走。這行只由 `speclink discuss conclude --hold` 寫入。解除它的方式有三種：不帶 `--hold` 的 conclude、轉出時帶 `--last`（宣告這是最後一刀）、或 `speclink discuss archive`。不帶 `--last` 的轉出不會清掉它。用法見[討論：需求還模糊時](discuss.md)。

建立討論時會蓋建立者章，取自 git 身分。git 身分取不到時省略。從帶有使用者識別的環境建立討論時，另記一行建立者的識別；本機 CLI 不寫這一行。

已封存的討論可以用 `speclink discuss restore <slug>` 搬回進行中，內容一個字元都不變。不要自己搬 `discussions/archive/` 底下的檔案。用法見[討論：需求還模糊時](discuss.md)。

## 討論與變更怎麼連起來

鏈結有兩個方向：

- 變更側：變更的狀態檔記錄它來自哪些討論。一個變更可以來自多份討論。
- 討論側：討論記錄記錄它轉出了哪些變更。一份討論可以轉出多個變更。

三個指令會動這條鏈：

| 指令 | 效果 |
| --- | --- |
| `speclink discuss promote <slug>` | 中途轉出：建立新變更骨架並連結 |
| `speclink discuss link <slug> <變更名>` | 把討論連到既有變更。只寫變更側，討論記錄不動 |
| `speclink discuss seal <slug> <變更名>` | 標記討論的內容已反映到該變更：討論狀態變成 promoted |

promote、seal 與 `speclink new change --from-discussion` 都可以帶 `--last`，表示這次轉出的是結論規劃的最後一刀：記錄的「保留在途」旗標一併解除。`speclink new change` 的 `--last` 要與 `--from-discussion` 一起用，單獨帶會以錯誤結束、不建立任何檔案。

變更封存時，它來源的每份討論各自檢查三個條件，全部成立才一起封存：

1. 該討論的結論已經寫入（scaffold 留下的佔位註解不算）。
2. 沒有其他進行中的變更引用它。
3. 記錄沒有「保留在途」的 `hold: true` 行。

任一條不成立的討論留在原地，不出現在封存輸出的隨行封存清單裡，之後照常可以加輪、下結論與轉出。判定第 2 條時，只要有任何一個進行中變更的狀態檔存在但解析失敗，就當成那個變更仍在引用這份討論：討論留在原地，變更本身照常封存。修好那個狀態檔之後，再封存任一引用這份討論的變更，討論就會照常隨行封存。

變更被 discard 時，討論側的連結會移除；連結清空後，討論狀態退回 concluded（有結論）或 open（無結論）。

操作細節見[討論：需求還模糊時](discuss.md)。
