# 品質關卡總覽：審查與驗證

封存之前有兩道可選的品質關卡，由你決定要不要跑：

- **審查**：看實作的工藝品質。技能 `/speclink-review`，說明見 [審查站](review.md)。
- **驗證**：看實作有沒有符合規格。技能 `/speclink-verify`，說明見 [驗證站](verify.md)。

兩站各自獨立。每站有自己的工單（變更目錄裡的 review.md 與 verify.md）與自己的章。兩張工單可以同時存在於同一個變更。兩站都要跑時，用 `/speclink-quality` 合跑，見本頁「兩站合跑」一節。桌面 app 上怎麼看兩站的狀態，見 [桌面上的品質關卡](desktop-quality.md)。

## 前提：寫碼任務全部完成

兩站都要求變更的寫碼任務全部勾完。只剩 `[M]` 手動任務未勾也算成立，這時站內報告會點名尚餘的手動任務。寫碼任務沒完成時，審查站直接拒絕並停止，驗證站改成中途盤點報告、不落工單。`/speclink-quality` 不另設守門，照兩站各自的做法呈現。

## 審查面：站內到底看哪些程式碼

兩站不會審整個工作樹，只審「這個變更動過的差異」。這個範圍叫審查面，決定方式如下。

1. **apply 開始時先記基準點**。apply 技能在標記開工之前，會執行 `speclink review prepare <變更名>`，記下當時的 commit 與當時已經髒掉的檔案。這一步失敗，apply 不會繼續開工。
2. **從基準點算到現在**。`speclink review scope <變更名>` 用 git 算出基準點到目前工作樹的完整差異，包含已暫存、未暫存、改名、刪除，以及你在這個變更新增的未追蹤檔。候選檔案來自任務證據裡記的 touched 檔案。speclink 底下的產物與 Speclink 自己的工作資料不會進審查面。
3. **凍結快照**。算好的差異會凍結成一份快照，存在本機的 `.speclink/review-scopes/<變更名>/`，之後的每一輪都以這份快照為準。

範圍有歧義時，指令會停下來要你決定，不會自己猜。歧義包括：基準點缺失、記得太晚、沒有 git；某個 touched 檔在開工前就已經髒了；另一個進行中的變更也認領了同一個檔案。這時你有三種處置：

- 給 `speclink review scope` 一個可信的基準 commit（`--base`）。
- 用指令列出的差異段落 ID，明確挑選要納入的段落（`--candidate-hash` 加 `--include-hunk`）。挑選時工作樹又變動了，指令會拒絕舊的選擇。
- 改到隔離的 worktree 裡實作，見 [平行實作與合回](worktree.md)。

沒有任何 touched 記錄時，指令不會自動審整個工作樹。就算你給了基準 commit，也還是要用段落挑選才能凍結。

歧義只會發生在首輪。複驗的範圍只含「上一輪之後內容有動的地方」，會自動算出來：上一輪收錄過、之後又被改的檔案（就算這次沒被發現點名，也會從它最近一次被收錄的狀態算起），加上上一輪之後才變動的新檔。內容沒動的檔案不會再進來。複驗還會多一行「範圍外變動」，列出你在審查面之外改動的檔案，只是告知，不進工單。快照不見時，指令直接失敗，不會退回整檔重審。

驗證站的 `speclink verify scope <變更名>` 用同一套算法，但快照分開存。一站蓋章或放棄時，只清自己的快照，不動另一站的。

### 在別的 checkout 做完後重設基準點

變更在另一個 checkout（例如 worktree）裡做完、合回目前這個 checkout 後，這裡沒有該變更的基準點，算範圍時就會停下來。這時用：

```
speclink review prepare <變更名> --base <commit> --from <來源 checkout 的路徑>
```

- `--base` 指定一個可信的 commit 當新的基準點。解析不到 commit，或它不是目前 HEAD 的祖先，指令就失敗。
- `--from` 選填，但一定要搭配 `--base`。帶了它，指令會把來源 checkout 裡這個變更兩站的快照逐檔複製過來，同名的直接略過，讓已經跑過的輪次能在這裡接著複驗。來源的基準點本身不會複製；來源沒有快照也照常成功，只寫基準點。
- 這個 checkout 已經有該變更的基準點，而審查或驗證任一站的工單還沒結時，指令拒絕並點名是哪一站，因為那一站的快照綁著舊基準。

上面任一項檢查失敗，指令一個檔都不寫。複製快照到一半失敗時，已複製的留著、基準點還沒寫；用同樣的參數重跑，會略過已經在的快照，把剩下的做完。成功時不印任何東西。remote 模式下基準點與快照仍是本機資料，行為相同。不帶旗標的 `speclink review prepare` 行為不變。

## 工單：逐輪追加、不改舊輪

每跑一輪，技能就把這一輪的範圍與發現寫進工單的一個新區段。舊輪不會被改寫。第一輪是首輪（discovery，第一次完整檢查），之後每一輪都是複驗（validation，只驗收上一輪的修正）。

發現分三級：CRITICAL、WARNING、SUGGESTION。前兩級是「必修」，會擋章。SUGGESTION 不擋章。

工單不會影響 `speclink status` 與 `speclink validate` 的輸出。

### 發現的路徑必須落在範圍內

`speclink review add-round` 與 `speclink verify add-round` 寫入前，會逐條檢查每筆發現指向的檔案路徑。任何一條不合，整輪拒收、工單一個位元組都不動，stderr 逐一列出違規的路徑與原因：

- **不能帶行號**。`src/a.rs:42`、`src/a.rs:42-50`、`src/a.rs:42-`、`src/a.rs:L42` 這類寫法，或以單獨的冒號結尾，都會被拒。
- **必須在工單範圍內**。路徑要落在工單各輪範圍行（含本輪）的聯集裡，指向範圍外檔案（例如某個呼叫端）的發現會被拒。規格目錄（預設 `speclink/`）與 `.speclink/` 底下的路徑不受這一條限制，這類路徑本來就不進複驗範圍；驗證站常把發現錨在 delta 規格檔上。
- **沿用的未解項不檢查**。和上一輪某筆發現的嚴重度、路徑、描述完全相同的行（行末的 `(accepted)` 不計）視為原樣沿用，上面兩條都不查。

反斜線會先換成正斜線再比對。路徑問題和「變更不存在」「輪次順序不對」這類問題同時發生時，先報路徑問題；格式錯誤照舊報原本的錯誤。remote 模式下 CLI 先讀工單、在送出前做同樣的檢查，違規時 server 上的工單不動。

### 首輪記下套用了哪些審查規則

審查站的首輪會在工單裡多記幾行：一行標明預設清單模式（extend 或 replace），以及每條專案審查規則各一行（嚴重度加規則原文）。這幾行是選填的，只能出現在帶階段標記的首輪，複驗或舊格式的輪帶了就整輪拒收；格式不對（模式拼錯、一輪兩行模式、有規則行卻沒有模式行、嚴重度不是三級之一、規則行沒有原文）也會拒收。兩站的工單格式都接受這幾行，實際會寫的只有審查技能。`speclink review show` 會把它們隨原文印出來。審查規則是什麼、技能怎麼寫這幾行，見 [審查站](review.md)；怎麼設定，見 [工作流政策與設定](policy-config.md)。

## 蓋章：條件與效果

`speclink review stamp <變更名>` 與 `speclink verify stamp <變更名>` 守同一組條件：

1. 寫碼任務全部完成。
2. 工單最後一輪沒有未解的必修發現。帶 `--accept` 可以豁免這一條，章會帶保留。

守門通過時，引擎在同一次原子寫入裡做兩件事：把章寫進變更的 .meta.yaml，並刪掉工單。不會出現「章寫了、工單還在」的中間狀態。

章裡記了四樣東西：

- 蓋章的時間、人、工具。
- 蓋章時的任務總數（含 `[M]` 任務）。
- 審查面每個檔案的內容指紋。
- 這一站累計跑了幾輪：原有的輪數（沒有就當 0）加上這次工單的輪數，檔內只有一行。例如審查章失效前記 3 輪，重開的工單跑了 2 輪，重新蓋章後記 5。帶 `--accept` 的蓋章一樣記錄。

守門失敗或放棄該站（discard）時，輪數不變。原有的輪數不是非負整數時（例如 `many`），狀態檔當成無法解析，蓋章拒絕、什麼都不寫。累計的輪數會出現在桌面 app 已封存頁的流程成本摘要，見[規格、討論、已封存與搜尋](desktop-browse.md)。

蓋章後，fs 模式的工單文字只留在 git 歷史；remote 模式的 store 不保留已刪文件，工單文字不可回讀。所以蓋章後 `speclink review show` 回報「無工單」是正常的。

審查面裡的檔案如果在修正過程中被刪掉或改名，蓋章時會自動排除，不會因此失敗。但整個審查面的檔案全部消失時，蓋章會拒絕並列出檔案，要你還原或放棄工單。

## 章什麼時候失效

章綁在被審查的內容上。以下任一情況，章就失效：

- 任務總數與蓋章時不同（例如新增了一個任務）。
- 任何一個寫碼任務變回未完成。
- 審查面裡任何一個檔案的內容與指紋不符，含檔案已不存在。

以下情況不影響：補勾或取消勾選 `[M]` 任務；檔案只是行尾由 LF 變成 CRLF。

章失效會擋封存，見 [封存](archive.md)。

## 未結工單擋封存

變更還有工單沒結掉時，`speclink archive` 預設拒絕，並列出三種處置：完成蓋章、放棄該站（`review discard` 或 `verify discard`）、或帶 `--carry-review`／`--carry-verify` 明示把工單一起搬進封存區。兩張工單都在時，會並列兩組處置，兩個旗標可以同時帶。

## 兩站合跑：/speclink-quality

事前就知道兩站都要跑時，用 `/speclink-quality`。它只管兩站的先後、什麼時候派出子代理（主對話另外派出、只讀不改檔的助手）、何時暫停，不重述兩站各自的檢查內容與簡報規則。只跑一站就直接叫該站技能，quality 不會啟動，該站照舊修完即蓋章，派法也照舊：審查站兩軸同時派、驗證站派一個。

時序是「每輪暫停制」：

1. **檢查輪**：技能先依序做完兩站的準備步驟。審查站是選定變更、守門、查工單、鎖定範圍、讀產物與專案審查規則；驗證站是選定變更、讀狀態、讀產物、分流與鎖定範圍。接著在同一則訊息裡一次派出三個子代理：審查的 Standards 軸、審查的 Correctness 軸、驗證檢查，三份簡報各照該站的規則組成，不會等審查站寫完工單才派驗證站。三者回報後，先完成審查站（呈現、分類、寫工單）、再完成驗證站（報告、分類、寫工單），兩站都先不蓋章。
2. **彙整報告**：依站分組，必修與其餘分開列；保留審查站呈現開頭那一行「套用了哪些審查規則」；修正會動到產物（規格、design、tasks）的發現單獨標出，讓你先決定。你沒裁示前，技能不會開始修正。
3. **停下時的選項**：至少有全修、挑選部分修正、不修就停（兩站的工單與快照留著、不蓋章）。必修還沒清空時，不會提供「補蓋章」這個選項。
4. **修正輪**：你裁示的修正統一由主線依專案 TDD 慣例落地，並通過兩站各自的修復迴圈驗證門（內容見 [審查站](review.md) 與 [驗證站](verify.md)）後，用與檢查輪相同的「先準備、同一則訊息派出」方式跑兩站複驗。每輪複驗完再停下來問，直到你決定收尾或停止。
5. **乾淨輪**：兩站都零發現，或必修清空且這一輪沒有新修正，技能同樣停下來報告「兩站皆綠」。要不要補蓋章由你決定，技能不會自動蓋。
6. **收尾補蓋**：你裁示補蓋後，技能向兩站明示「這是收尾補蓋」，審查章與驗證章接連蓋下、中間零編輯，這樣兩章到封存為止都不會出現「其後有變動」。工單裡還留著你裁示不修的必修發現時，那一站的章是帶保留章，技能會在選項裡先講明，並以你的裁示為授權。只剩 SUGGESTION 不算保留，照常蓋乾淨章。

你在「進入收尾補蓋」或「挑選部分修正」時留下不修的必修裡如果有 CRITICAL 級，技能會在停下處逐條列出這些 CRITICAL 的原文，請你明確確認一次。之後呼叫審查站時，技能會明示「CRITICAL 已逐條確認」，審查站就不再問你第二次。

執行環境沒辦法派出子代理時，技能退回依序自己跑三份檢查、各自分開報告，其餘時序（先不蓋章、彙整後停下）不變。

封存由技能提建議、你來執行。變更還有 `[M]` 任務未勾時，建議會提醒你做完手動任務並勾選後才能封存。

### 蓋章前的預防提醒

有兩種情況會讓章在蓋下之後失效。合跑技能會在事前提醒你，但不會替你 rebase、合併或 push：

- **跑關卡前先比對主分支**：準備兩道關卡、凍結第一輪範圍之前，如果目前不在 repo 的主分支上（例如在 worktree 或功能分支），技能用 git 找出主分支在分岔點之後改過的檔，再與本分支改過的檔取交集。
  - 交集不是空的：技能停下來列出這些檔，說明之後再 rebase 會讓章失效、重蓋要從首輪重跑兩道關卡，並建議你先 commit 本變更的檔（含新檔）再 rebase 或合併主分支。你回答之前，技能不會建立任何工單或範圍。
  - 你 rebase 或合併之後：技能先確認本變更的檔（含新檔）都已 commit。沒 commit 的檔會被當成開工前就有的修改，讓第一輪範圍停下來。還有沒 commit 的檔時，技能請你 commit，或經你同意代為 commit。接著它執行 `speclink review prepare --base <新的分岔點>`，把兩站的起點移到新的分岔點；不移的話，第一輪會把主分支的修改算成本變更的。這個指令失敗時，技能回報錯誤，排除原因後在任何關卡開跑之前重跑。
  - 交集是空的、目前就在主分支上、或找不到主分支：直接開始，不停頓。
- **收尾蓋章前先看 CI**：repo 有 CI 設定（例如 `.github/workflows/` 底下有工作流程檔）時，每輪停下來問你的時候，「進入收尾補蓋」選項的說明會多一句：建議先 commit 並 push，再確認該 commit 的 CI 已在所有平台通過；蓋章後為了 CI 再修，章就失效。選項數量不變，技能不會為此多問一題，也不會自己 push 或查 CI 狀態。沒有 CI 設定時沒有這句附註。

> [!WARNING]
> 一站蓋章後才臨時決定加跑另一站，是有代價的。新站如果需要修正程式碼，前一站的章就失效，封存會被擋下，得回去重跑前一站補章。新站零改動時前章維持有效。兩站都要跑時，一開始就用 `/speclink-quality`。

## 中斷後接續

合跑到一半 session 被關掉（例如修正做到一半），再執行一次 `/speclink-quality` 就能接著跑。兩站的工單在變更目錄裡、快照在本機；工單還有必修項目，兩站就判定這一輪是複驗，關閉前落地的修正都會算進複驗的範圍。

接續時技能多守三條：

- **先跑驗證門**。派出子代理之前，先通過兩站的修復迴圈驗證門，因為上一個 session 的測試狀態不明。
- **複驗範圍是空的站要先確認**。某站的複驗範圍一個檔都沒有、而該站上一輪還有必修時，技能先列出變更目錄裡未提交與未追蹤的檔案（兩張工單不算）。原因是複驗範圍不含規格目錄，只改產物的修正從範圍裡看不出來，git 也分不出這些修改發生在上一輪之前還是之後。
  - 一個檔都沒列出來：這一站這輪不派子代理、不寫新輪。兩站都這樣時，技能直接停下來，用上一輪的發現請你裁示。照常記一輪的話，會被判成「沒有進展」而以 failed 收場。
  - 有列出檔案：技能把清單給你看，問你上一個 session 是不是靠改這些產物修正發現。答是，這一站照常派複驗，簡報附上改過的段落原文；答否，當作一個檔都沒列出來處理。
- **接續前不要 commit**。技能會提醒你：關掉之後、接續之前不要提交修正。複驗範圍是靠「內容有沒有動、檔案是不是髒的」收錄修正，提交之後，沒被快照收錄過的新檔會離開複驗範圍。

你上一輪「修哪些、不修哪些」的裁示不會保存。接續後停下來問時，只列仍未解的發現，請你再裁示一次。只有一站有修正可驗時，技能只派那一站的子代理、只寫那一站的工單，彙整報告會註明另一站這輪沒有修正可判。

## remote 模式

remote 模式下，工單與章都經 store 讀寫，不落本機投影。離線、版本衝突、認證失效時，工單指令以非零結束並在 stderr 說明。審查面的計算仍在你本機的 checkout 上進行：基準點與快照存在本機，server 不會收到差異內容，也不提供 git diff。touched 檔案的認領改從 server 的證據記錄讀取，多位協作者的證據取聯集。證據缺席時同樣停下來要你決定範圍，不會靜默當成沒動過。

首輪的規則記錄由 server 用同一套格式規則檢查，不合就拒收。舊版 server 回傳的輪次沒有規則記錄時，CLI 當作沒有；server 回傳 CLI 不認得的預設清單模式時，`speclink review show` 會失敗，說明這支 CLI 比 server 的工單格式舊。

**出處**：`quality-skill`、`review-station`、`verify-station`、`change-diff-scope`、`desktop-app`
