# 驗證站

驗證站看實作有沒有符合變更的產物：規格寫的都做了嗎、做對了嗎、彼此一致嗎。技能是 `/speclink-verify`，底下的工單指令是 `speclink verify ...`。審查面怎麼決定、章怎麼失效，見 [品質關卡總覽](quality-stations.md)。工藝品質的檢查在 [審查站](review.md)。

## 三個維度

驗證從三個維度檢查：Completeness（完整）、Correctness（正確）、Coherence（一致）。發現分 CRITICAL、WARNING、SUGGESTION 三級。

## 不改規格的變更：行為檢查

變更的產出流程是 no-spec-change（不改規格）時，它沒有 delta 可以對照。這時技能改做「行為檢查」，取代以 delta 為準的規格涵蓋與需求對應：

1. 從提案 Why 列出的正式規格出發。
2. 再用凍結差異裡的具體名稱（指令、旗標、輸出欄位、檔名、畫面文案）找出涵蓋這些程式區域的正式規格需求。
3. 逐一比對：差異有沒有改變這些需求承諾的、看得到的行為。

任務完成度與設計遵循照常檢查。產出流程不是 no-spec-change 的變更，照原本的流程依 delta 檢查。

| 結果 | 報告與工單 |
| --- | --- |
| 沒有改到承諾的行為 | 報告列出比對過的正式規格，沒有切換產出流程的建議 |
| 改到了某條需求承諾的行為 | 一條 WARNING `Behavior change in a no-spec-change change: <capability> / <requirement>`。它是必修，會擋乾淨蓋章；不帶 `--accept` 時 `speclink verify stamp` 拒絕蓋章 |

例：凍結差異改了 `speclink list --json` 的一個欄位名，而正式規格承諾了這個欄位，就會出這條 WARNING。差異只搬移函式、改內部變數名，任務全部完成，就沒有這條 finding。

這條 WARNING 的建議會依序寫出修正步驟，報告的下一步也指向這組步驟：

1. `speclink verify discard <變更名>`：放棄這張驗證工單。
2. `speclink change schema <變更名> spec-driven`：切回 spec-driven（見[產出流程 schema 管理](schemas.md)）。
3. `/speclink-ingest <變更名>`：補上該需求的 delta。
4. 重新執行 verify。

> [!WARNING]
> 不要用 `--accept` 帶過這條 WARNING。技能不會這樣建議：變更改到了承諾的行為，就要回到 spec-driven 把行為寫進 delta。

## 技能怎麼跑

檢查由一個子代理（主對話另外派出、只讀不改檔的助手）執行，結束時依寫碼任務完成度分流：

- **寫碼任務全部完成**（含只剩 `[M]` 手動任務）：先用 `speclink verify scope` 取得凍結的差異，再用 `speclink verify add-round` 把這一輪寫進工單，報告裡告訴你工單已建立與輪次。只剩手動任務時，報告一併點名剩餘的手動任務。
- **寫碼任務還沒完成**：技能只給對話式的進度盤點，列出未完成的任務。它不算範圍、不落工單，變更目錄不會出現 verify.md。引擎那一側也守同一條：寫碼任務沒全完成時，add-round 直接拒絕。

沒有工單時執行唯一一次首輪：讀全部產物，以凍結的差異加上判斷所需的呼叫端與測試作為證據，完整跑三個維度。程式碼的檢查面限定在凍結的差異段落，不掃描工作區其他既存問題。

已有工單時執行複驗：只把上一輪未解的發現、已接受清單、修正差異與必要脈絡交給子代理。逐筆判定已解或未解，只回報修正本身直接引入的退化。未解的發現以原本的嚴重度、路徑與文字寫回新一輪，不改寫文字假裝進步。已解的移除。不重掃整個變更、不重掃發現所在的整個檔案、不新增沒改到區域的問題。

## 子代理簡報的查找紀律與證據順序

為了讓子代理查得快、不亂翻，技能派出的簡報守這幾條：

- 凍結差異在 25 KB 以內就直接貼進簡報；超過時只給檔案路徑與每段差異的行號範圍。
- 自動產生的檔案（golden snapshot、assets.lock、由 `speclink update` 再生的技能檔）只給路徑，子代理對它們最多搜尋一次。
- 子代理不整份讀大檔（只按行號範圍讀），也不做沒有目標的遞迴搜尋，只搜簡報列出的函式名、型別名與檔案。
- 首輪不限工具呼叫次數；複驗限 5 次，簡報只附上一輪未解的發現與修正差異。
- 簡報結尾要求「沒查完就直說，不要猜」。子代理回報沒查完的部分，會原樣列進報告，由你決定要不要補查。
- 發現指向凍結差異以外的呼叫端時，要錨在差異內被呼叫的那個檔案，路徑不帶行號。工單會拒收不合這條的路徑，見 [品質關卡總覽](quality-stations.md)。

**證據順序**：判 Completeness 與 Correctness 時，子代理先在凍結差異裡找每條 Requirement 的實作證據。差異裡完全找不到某條的實作（例如它由變更前就有的程式碼滿足）時，才往差異外搜尋，而且只搜具體的函式名、型別名或檔名，不拿關鍵字搜整個 codebase；報告會註明這條的證據在差異外。

例如 delta 規格有 8 條 Requirement，其中 7 條的實作與測試都在差異內，子代理就只在差異內判那 7 條，只對剩下的 1 條用具體函式名往外找。

在 `/speclink-quality` 合跑時，簡報照同樣的規則組成，由合跑技能和審查站的簡報在同一則訊息裡派出。

## 處置與三選項

主線接手子代理的報告後做處置分類。必修＝CRITICAL 與 WARNING；可裁事項一律以 SUGGESTION 記錄，不進接受機制，不擋章。修正一律回主線依專案 TDD 慣例做，子代理不改任何檔案。

首輪有必修時問三選項：修正後重驗、接受現狀蓋章（`speclink verify stamp --accept`）、先不蓋章結束。零發現或只有 SUGGESTION 時：單站直接呼叫就記錄這一輪並蓋乾淨章；在 `/speclink-quality` 合跑時改成「先不蓋章」結束，章留到合跑的收尾補蓋。

收尾補蓋的呼叫在入口就分流：最後一輪必修已清空、凍結點之後內容沒動，就跳過檢查直接蓋章，不多落一輪空輪；內容有動，就在同一次呼叫裡先跑一輪複驗，必修清空後再蓋。不會對沒驗過的變動直接補章。

### 修復迴圈的驗證門

你選「修正後重驗」（或在合跑時裁示修正）後，技能在修正完、派下一輪檢查之前，先跑建置與受影響範圍的測試，全綠才進下一輪；沒過就先修到全綠。受影響範圍依序判定：

1. 修正改到的檔案落在某個任務說明列出的路徑內：跑那個任務說明寫的驗證指令。
2. 任務沒涵蓋的檔案：依專案文件寫的測試政策（CLAUDE.md、AGENTS.md 或 config.yaml 的產出規則）挑測試。
3. 專案完全沒寫測試政策：跑 repo 慣例的完整測試。

建置一定照跑，不因範圍判定而略過。報告會列出這次跑了哪些測試指令、略過哪些範圍，並註明略過的部分交給 CI 守門。例如修正只改了任務 3.2 列出的前端檔案，而任務 3.2 寫明用 `npm test -w packages/ui` 驗證，技能就只跑建置與這一條，不跑完整測試。

修正動到產物（規格、design、tasks）時分三種情況：

- **只改程式碼讓它符合規格**：不動產物。
- **規格字面要修、意圖不變**：主線直接改產物，`speclink validate <變更名>` 通過後才進下一輪。報告會列出改了哪幾段，下一輪的檢查簡報附上改過的段落原文，檢查據此判定原本的發現有沒有解掉。複驗的差異不含規格目錄，不附上就看不到這個修正。
- **意圖或範圍改變**（修正需要新增任務，或改變某條 Requirement 的意圖）：技能以「範圍改變」結束本站，工單留著、不蓋章，建議先跑 `/speclink-ingest` 再重跑。技能不會在迴圈裡自己改任務。

### 每輪之後怎麼收

每輪複驗寫入工單後的收尾規則：

| 情況 | 結果 |
| --- | --- |
| 必修清空，且沒有已接受的必修 | 執行 `speclink verify stamp`，結果 passed clean。殘留的 SUGGESTION 不擋章 |
| 必修清空，但有已接受的必修 | 等你明示執行 `speclink verify stamp --accept`，結果 passed with reservations |
| 必修數減少但沒清空 | 再問一次三選項 |
| 必修數沒有減少 | 記錄這一輪後以 failed 結束，工單留著、不蓋章、不自動重試 |

必修數減少只決定能不能繼續，不是品質分數。技能沒有固定的最大輪數。沒有互動選單工具的環境，技能用純文字問並等你回覆。

## 複驗遇到重大新問題

規則與審查站相同：與修正無關的新問題不進目前的發現，也不重開首輪。只有同時有現實觸發路徑、有重現方式或失敗測試或明確不變量破壞、且影響安全、資料損失或錯誤行為時，技能以 scope changed／failed 結束本站，工單留著、不蓋章，建議另開一輪或衍生一個變更。

舊格式工單有發現、卻沒有對應的快照時，技能無法精確重建修正差異，會保留工單，等你明示放棄後再重跑首輪。

## 工單指令

| 指令 | 做什麼 |
| --- | --- |
| `speclink verify scope <變更名>` | 算出並凍結審查面。無工單時是首輪，有工單時是複驗 |
| `speclink verify add-round <變更名> --stdin` | 從標準輸入讀一輪內容，追加到工單。寫碼任務沒全完成時拒絕 |
| `speclink verify show <變更名>` | 印出工單原文。無工單時報錯「該 change 無驗證工單」 |
| `speclink verify stamp <變更名> [--accept]` | 蓋章。條件與審查站同一組 |
| `speclink verify discard <變更名>` | 刪掉工單，不寫任何章，並清掉本站的快照。無工單時報錯 |

scope 停下要你決定範圍的情況與審查站一樣：基準點不可信、開工前就髒的檔案、與另一個進行中變更重疊、挑選時內容漂移、快照缺失。這時不會建立快照，也不會退回整檔檢查。驗證站與審查站的快照分開存；`verify stamp` 或 `verify discard` 只清驗證站的快照，審查站的快照與 apply 的基準點不動。

add-round 會拒絕的內容：缺少範圍行；階段與指紋兩欄只出現其中一個；第二個首輪；變更不存在；寫碼任務沒全完成；發現的路徑帶行號，或不在工單範圍內。路徑規則與審查站相同，規格目錄與 `.speclink/` 底下的路徑免查範圍，所以錨在 delta 規格檔上的 Requirement 層級發現可以照常寫入（規則見 [品質關卡總覽](quality-stations.md)）。路徑檢查排在變更存在、寫碼任務守門與輪次檢查之前，同時違反時先報路徑問題；格式錯誤照舊報原本的錯誤。拒絕時工單零寫入。

stamp 通過時，同一次原子寫入把驗證章寫進變更的 .meta.yaml 並刪掉 verify.md，然後清掉驗證站的快照。同一次寫入也記下驗證站的輪數：原有的輪數（沒有就當 0）加上這次工單的輪數，檔內只有一行。例如原本記 2 輪，章失效後重開的工單跑了 3 輪，蓋章後記 5。帶 `--accept` 的蓋章一樣記錄；守門失敗或放棄驗證（discard）不改輪數。原有的輪數不是非負整數（例如 `-1`）時，狀態檔當成無法解析，蓋章拒絕、什麼都不寫。章裡記蓋章時的任務總數（含 `[M]`）與審查面每個檔案的內容指紋。失效規則與審查站同構：任務總數改變、任何寫碼任務未完成、任何審查面檔案內容不符，章就失效；補勾 `[M]` 與行尾差異不影響。

## 封存時的處置

變更還有 verify.md 時，`speclink archive` 預設拒絕，列出三種處置：`verify stamp`、`verify discard`、或帶 `--carry-verify` 把工單一起搬進封存區。審查與驗證兩張工單同時在時，並列兩組處置，`--carry-review` 與 `--carry-verify` 可以同時帶。詳見 [封存](archive.md)。

## remote 模式

工單走 store 讀寫。離線、版本衝突、認證失效時，指令以非零結束並在 stderr 說明；離線時追加輪次，遠端與本機投影都不會變。`verify scope` 仍在你本機的 checkout 上算，與 apply 的基準點、touched 記錄、驗證快照共用；server 不會收到差異或快照。本機的 git 錯誤不會被包裝成版本衝突。add-round 的路徑檢查在 CLI 送出前就做，違規時 server 上的工單不動。
