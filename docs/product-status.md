# Product status

[繁體中文](product-status.zh-TW.md) · **English**

Last check: **2026-11-18** (the source code after 0.12.0).

This document tells you if a capability is available now. The specs in `speclink/specs/` define the behavior. The [Roadmap](roadmap.md) lists the work that is not done yet. Code, a crate, or a spec alone does not make a capability available to users.

To try a remote project with the demonstration server, Speclink Desktop, and the CLI, follow [Remote getting started](remote-getting-started.md).

## <a id="status-model"></a>Status model

| Status | Meaning |
| --- | --- |
| Available | It has a user entry point and two independent pieces of evidence, or one end-to-end test. |
| Partial | Some of it works. The full flow has a known gap. |
| Planned | It has no usable entry point yet. For details, see the [Roadmap](roadmap.md). |
| Deprecated | The code still has it, but it is not part of the target architecture. No item has this status now. |

## <a id="local-and-remote"></a>Local projects and remote projects

This table holds all the differences between a local project and a remote project. The "Remote project" column measures the official demonstration server, `speclink-server`. A host that embeds the engine uses the same host kit and the same store contract, so it behaves the same. The differences are in the [known gaps](#known-gaps).

Most CLI verbs work in local projects and in remote projects. There are only two exceptions. For the full list, see the [Verb and flag contract](verb-contract.md):

- Local projects only: `demo`.
- Remote projects only: `claim`.

`trace`, `change rank`, and `plan --strict-overlap` work in both. If you run `demo` or `claim` in the wrong kind of project, the CLI rejects it. It does not switch to the other kind.

| Capability | Local project | Remote project | Note |
| --- | --- | --- | --- |
| Read and write specs and changes | Available | Available | A local project reads and writes `speclink/` directly. A remote project writes only through the Server, and the checkout has no writable spec files. |
| Change lifecycle (`propose` → `apply` → `archive`) | Available | Available | A remote project archives one change at a time and keeps no local backup of the archive. A remote project does not accept the `--schema` flag of `status` and `instructions`: the workflow config of the Server sets the schema. |
| Discussions (`discuss`) | Available | Available | Promote, link to an existing change, and archive work the same in both. |
| Quality stations (`review`, `verify`) | Available | Available | Tickets, rounds, and stamps follow the same rules in both. |
| Execution order (`plan`, `change depends`, `change rank`, `change schema`) | Available | Available | `change rank` and `plan --strict-overlap` work in both. In a remote project, `change schema` resolves built-in schemas only. |
| Trace (`trace`) | Available | Available | The output is the same in both. |
| Claim a change and release the claim (`claim`, `claim --release`) | Not applicable | Available | The change data keeps the claimant after a Server restart. A claim on a change that another person holds returns 409, and the message names the holder. Each person who can write can release a claim; a host that wants a stricter rule refuses the release in its hook. `show --json` shows the claimant. |
| Demo data (`demo`) | Available | Not applicable | Local projects only. A remote project rejects it and sends no request. |
| Agent context | Available | Available | A local project reads the repo. A remote project reads the read-only `.speclink/context/`. |
| Evidence of the files that a task touched | Available | Available | A local project writes `.evidence.json`. In a remote project the Server keeps it, and `speclink evidence show` or `GET /changes/{name}/evidence` returns it. |
| Board and detail page in Speclink Desktop | Available | Partial | When you check a task of a remote project in Speclink Desktop, the app does not report the touched files. |
| Accounts, access tokens, and membership | Not applicable | Available | A local project needs no account. The demonstration server manages its own accounts. A host that embeds the engine uses its own accounts and login. |
| Backup and restore | Git does it | Available | A backup of the demonstration server needs a stopped server. A host that embeds the engine backs up its own database, or exports a scope with `host.exportScope`. |
| Offline work | Available | Needs a connection | When the connection drops, a remote project is read-only and rejects writes. |

## <a id="known-gaps"></a>Known gaps

This section lists the items that this version delays or does not do. Each item shows who it affects and what you can do today. The items that belong to a later direction have a place in the [Roadmap](roadmap.md).

| Gap | Who it affects | What to do today |
| --- | --- | --- |
| A host that embeds the engine and has no local spec files cannot use the verbs that need a checkout: `drift`, `review prepare`, `review scope`, `verify scope`, and `instructions` with `--skill`. A skill input such as "read the file path that the user gives" also works only when the agent has a file system. | Hosts that run verbs through `host.dispatch`, and their Agent tools. These verbs are rejected with the code `invalid_argv`. | An engineer runs these verbs with the CLI in a checkout that is connected to the remote project. If the agent has no file system, ask the user to paste the document content into the conversation. |
| `task done` does not collect the changed files for the host. Stamps and in-progress markers do not read the commit and the branch for the host either. The host kit does not read git. | Hosts that check tasks, stamp, or mark a change as in progress through `host.dispatch`. The task is checked as usual, but the evidence has no files, no repo, and no commit. | When you need the evidence, an engineer runs `speclink task done` with the CLI in a checkout. The CLI collects the files. For a stamp, the host puts the commit in the `--stdin` JSON (`headCommit`). To report the landed commit and the branch, use `speclink change landed <name> --commit <sha> --branch <branch>`. |
| A host that embeds the engine with Node has no ready push events. | Speclink Desktop and other clients that connect to such a host. The screen updates by polling, not at once. | You do not set anything: clients poll by themselves. A host that needs updates at once serves its own SSE stream and declares the URL in `pushTransports` of `createHost`. Speclink Desktop connects to the first SSE URL that the handshake declares, when it has the origin of the host. |
| Speclink Desktop has no button to release a claim. | People who use only Speclink Desktop for a remote project and must hand over a change that they claimed, or that a person who left claimed. | Run `speclink claim <change> --release` in a checkout that connects to the remote project. In a host that embeds the engine, the Agent tool runs the same verb. Then claim the change again in Speclink Desktop. |
| The `baseline` and `manual` skills are refused in remote projects. | People in a remote project who want to create a spec baseline from existing code or to generate a manual. | The tour mode of `manual` works as usual (`/speclink-manual tour`). Create the spec baseline in a local project first. Then move it to an empty remote project with "Migrate to Server" in Speclink Desktop. For the manual of a remote project, there is no alternative today. |
| With an old Server that does not declare skills, the CLI uses its local templates, and the two worktree skills are not generated. | Users of a remote project on an old demonstration server. | Upgrade the Server to a version that supplies skills, and then run `speclink update`. Before the upgrade, the other skills from the local templates work as usual. |
| You cannot change the free fields of an archived change or discussion. No verb queries by field. | Hosts that use free fields to connect changes to their own tickets or boards. | Set the fields before you archive. The fields go into the archive with the document. To query, read `fields` in `speclink list --json`, `speclink show <name> --json`, and `speclink discuss list --json`, and filter in your own program. |
| The CLI has no import or export verb. | People who move a project into or out of a remote project, or who make regular backups. | To move a local project to a Server, use "Migrate to Server" in Speclink Desktop. In the program of a host, call `host.exportScope` and `host.importScope`, or use `GET /export` and `POST /import` of the HTTP entry point. To move local projects from the program of a host, call `exportScope()` of `createEngine` on each project folder, then `host.importScope` (see [Export a local project](sdk-node.md#export-local)). On the demonstration server, use the export on the System page of the admin console, or `speclink-server backup`. |
| No store port example is in JavaScript. | Integrators who embed with Node and write the three store functions themselves. | Start from the smallest example, which uses a Map, in [Implement the three store functions](sdk-node.md#store-port) of the Node SDK document. Compare your tables and commit steps with the three Rust examples. Then check your code with `runStoreConformance`. |
| The demonstration server supports one instance only. | Admins of the demonstration server. | Run one server process for one store. If you need more instances, embed the engine in your own system and let your own database handle the transactions. |
| A spec folder outside the checkout. Today `spec_dir` does not check absolute paths or `../`. The CLI accepts them, but the behavior is not defined. | Users of a local project who want the spec folder outside the repo. | Give `spec_dir` only a relative path inside the project root. To share one set of specs between repos, use a remote project. |
| A read-only reference to another set of specs. | People who want to refer to the specs of another project from their project. | There is no built-in reference. To compare, run `speclink show <capability> --item-type spec` in the other project and read the content. |
| Custom artifact workflows for remote projects. | Teams that want their own schema in a remote project. | Use the two built-in schemas: `spec-driven` and `no-spec-change`. A custom schema works only in a local project. |
| A strictly consistent read snapshot. One read can make two or three calls to the store. If a commit lands between them, the read shows old and new content together for a short time. | People who read the board, lists, and search. Writes are not affected: the version check at commit still protects them. | Read again, and the content is consistent. A host that needs strict consistency handles it in its own `list` and `read` functions. `host.exportScope` is not affected: it starts again when the scope changes during the export. |
| Push events between several host instances. | Systems that run several host instances and need updates at once. | The default is polling, which needs no event transfer between instances. For push, the host transfers the events between instances itself (the store's `commit` gets the events) and declares its stream in `pushTransports`. |
| No cache by scope version. With many active changes, a list of changes makes more calls to the store. | Hosts and demonstration servers with many active changes or a slow store. | Archive finished changes soon, so the active list stays short. Read verbs do not read the content of archived documents. |
| An archive in a remote project keeps no local backup. `snapshotCreated` in the response is always `false`. | Users of a remote project who restore from the local archive backup. | The archived content is on the Server. Read it with `speclink artifact cat` or the Archived page of Speclink Desktop. To back up a full scope, use `host.exportScope` or `speclink-server backup` on the demonstration server. |

Earlier proposals listed some gaps that later changes solved. They are not in the table above:

- Lists from the demonstration server had no last-modified time: solved. `speclink list --json` has `modifiedAt`.
- The Node SDK supported only 9 verbs and no workflow-config verbs: solved. Every verb that has an engine command works.
- A host could not supply its own store, no entry point took an identity with each call, and nothing checked a command before it ran: solved. See `createHost`, `host.dispatch`, and the before-command hook.
- A host that embeds the engine could not import: solved. See `host.importScope` and `POST /import` of the HTTP entry point.
- No Server answered which login methods it supports: solved. A host declares them in `authMethods`, and the demonstration server answers too.
- The skills of a remote project came from the local CLI, and the two worktree skills were not generated: solved. The Server supplies the skills. After you connect to a remote project, the skill files do not update by themselves. [Remote getting started](remote-getting-started.md) has this step: run `speclink update`.
- No verb brought an archived discussion back: solved. Run `speclink discuss restore <slug>`. The newest archived record of the slug becomes a live record again, and its content does not change. The verb works in a local project, in a remote project, and in a host that embeds the engine.
- No verb wrote the glossary: solved. Read the full glossary with `speclink language show`, change it, and write the full document back with `speclink language replace --stdin`. The verb works in a local project, in a remote project, and in a host that embeds the engine.

## <a id="recheck"></a>How to check again

When you update this document, check again with the current checkout. Do not keep the result of an old check date:

1. Run `speclink --help` and the `--help` of each subcommand to check the CLI entry points.
2. Run `speclink-server --help` to check the entry points of the demonstration server, its accounts, and its backup.
3. Compare the folder lists of `.claude/skills/` and `.agents/skills/`. The only difference is `speclink-analyze` (Claude only).
4. Use the [mode declarations of the CLI](../crates/adapters/speclink-cli/src/main.rs) (the functions `dispatch` and `spec_dispatch`) and the [verb contract spec](../speclink/specs/verb-contract/spec.md) to check the table of local and remote projects.
5. Use the [type declarations of the Node SDK](../crates/adapters/speclink-node/index.d.ts) to check the exports of the Node SDK and the host kit, and the list of verbs that need a checkout.
6. Use `npm view @speclink/engine version` and similar commands to check the versions on npm.
7. Compare `Cargo.toml`, the package scripts, the integration and end-to-end tests, and the specs. A crate without a user entry point does not make a capability available.
8. Compare each known gap with the code. Move a solved gap to the list below the table. Do not delete it.
