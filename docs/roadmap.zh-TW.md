# 專案路線圖

**繁體中文** · [English](roadmap.md)

這份文件收集 Speclink 還沒做完的方向。它寫方向，不寫排程，所以不會出現版本號或交付日期。

每條方向回答三件事：

- **要解決什麼**：這條方向存在的理由。
- **目前到哪**：今天已經做到的部分。是否可用以[專案能力狀態](product-status.zh-TW.md)為準。
- **可觀察的下一步**：做完之後，你可以親手確認的事。

## <a id="sdk"></a>SDK

**要解決什麼**

想在自己的程式裡驅動 Speclink 引擎的人，應該只要裝一個套件，不必準備一套編譯環境。裝好之後，呼叫方式也要好寫、出錯時要說得清楚。

**目前到哪**

- `npm install @speclink/engine` 就裝得起來，不需要 Rust 工具鏈。npm 上有五個平台的原生套件。
- 引擎、Store bridge 與 `dispatch` 契約都有測試守著。用法見 [Node SDK](sdk-node.zh-TW.md)。
- 還沒做：
  - 型別化的 JS 方法。目前所有動詞都經 `dispatch` 以字串參數呼叫。
  - 契約版本握手：JS 套件與原生 binary 的版本不合時，直接拒絕而不是靜默出錯。
  - Store bridge 的並行上限、逾時與取消。目前沒有這三項限制。
  - Rust 使用者只能用 git 依賴 `speclink-core`；crates.io 上沒有這個 crate。

**可觀察的下一步**

用型別化的方法列出變更與讀取規格，編輯器能自動補完參數。JS 套件與原生 binary 版本不合時，錯誤訊息直接寫出兩邊的版本。

## <a id="own-client"></a>以引擎自建客戶端與 server

**要解決什麼**

桌面 app 只是引擎的其中一個前端。同一套指令、查詢與背景資料的路徑，CLI、server 與 Node SDK 都在用。你應該也能用它做出自己的東西：貼合團隊流程的桌面 app、VS Code 擴充、內部網頁看板，或接上自家認證與資料庫的 server。

**目前到哪**

- 規則只在 `speclink-core` 實作一次。Host 負責認證、版本、交易與事件。
- [Client Protocol 正式規格](../openspec/specs/client-protocol/spec.md)定義跨客戶端的線上契約。[動詞與旗標契約](verb-contract.zh-TW.md)寫下每個動詞在本地與遠端的歸屬與輸出格式。
- 還缺：
  - 一份「從零做一個客戶端」的文件。
  - JS 版的遠端 HTTP client。目前只有 Rust 的 `speclink-remote`。
  - 可供第三方使用的 UI 元件與整合契約。`@speclink/ui` 目前是私有套件。

**可觀察的下一步**

只讀公開文件、不讀 Speclink 原始碼，就能做出一個最小客戶端：列出變更、讀一份規格、勾掉一個任務。做不出來的地方，就是還缺的文件或介面。

## <a id="remote"></a>遠端協作

**要解決什麼**

一個人在自己的 repo 裡用 Speclink 已經完整。多人共用一份正式規格時，還有幾段路沒鋪平。

**目前到哪**

- Remote CLI 可用：`link`、`auth`、唯讀投影，絕大多數動詞都有遠端版本，包括 `plan` 與前置宣告。
- 桌面 app 可以開遠端看板：瀏覽變更、勾任務、讀寫 artifact，看到建立者、認領人與 capability 清單。
- 認領會存進 Store；認領到別人持有的變更會被拒絕，訊息寫出持有人。
- 斷線時看板變成唯讀 snapshot，寫入一律被拒，重連後自動收斂。
- 還沒做：
  - 在桌面遠端看板勾任務時，回報動到的檔案（CLI 已經會）。
  - 認領的釋放與接手。
  - 稽核歷史的查詢介面。Store 已保存每份文件的不可變歷史，但還沒有 API 或畫面可以查「誰在什麼時候用哪個指令改了什麼」。
  - 本機投影快取的清理：逾期清除、登出或切換專案時清除，以及只限本人讀取。目前投影已是唯讀，並排除在 Git 之外。
  - PM 到 RD 的交接關卡（核准後被改動就失效），以及 apply 時記下依據的規格版本。品質關卡與認領已涵蓋一部分，還要重新決定是否需要。

**可觀察的下一步**

在桌面遠端看板勾掉一個任務之後，查得到它動了哪些檔案，和在 CLI 上勾一樣。持有人離開之後，有辦法釋放或接手認領。

## <a id="agent-tools"></a>Agent 工具整合

**要解決什麼**

Speclink 目前透過生成的技能檔與 Agent 協作。技能檔是「把流程知識寫給模型讀」，不是「把能力當成工具給模型呼叫」。只有後者能讓 Agent 在對話中直接查規格、開變更、勾任務，不必每次重讀一整份技能說明。

**目前到哪**

- 技能這一側已經成熟：Claude Code 與 Codex 涵蓋每一站，見[完整 SDD 工作流](workflow.zh-TW.md)。其他 AI 工具可以用自訂工具描述子產生技能，見[設定說明](configuration.zh-TW.md)。
- Claude Code 外掛 `speclink-skills` 提供技能按鈕列與側邊面板。
- 工具這一側還沒有入口：沒有可安裝的工具套件，也沒有 MCP adapter。
- 目前討論中的方向（尚未定案）：
  - 先在 `@speclink/engine` 提供一個通用工具，接收 CLI 參數與 stdin，並附上接到 Agent SDK 的範例。
  - 工具呼叫的身分綁在宿主那一端，模型不能自己帶入身分。
  - MCP adapter 排在後面；沒有 checkout 時，用 MCP resources 提供背景資料。

**可觀察的下一步**

在一個 Agent 框架裡把 Speclink 掛成工具，直接以工具呼叫列出變更與讀取規格，不必請模型去跑 CLI。工具呼叫用的帳號與可寫的 Store，和 CLI 走同一套判定。

## <a id="system"></a>系統整合

**要解決什麼**

Speclink 進到一間公司之後不會是孤島。帳號要接既有的身分系統，規格的變動要能通知別的工具，部署要跟著既有的維運方式走。

**目前到哪**

- Server 的營運已經可用：安裝、帳號管理、存取金鑰、device 登入、備份還原都有入口與端到端測試。
- Server 提供 SSE 事件串流（`/events`），客戶端可以即時收到變動。
- 還沒做：
  - 企業 SSO（OIDC）。目前只有 server 自己管理的帳號。
  - 對外通知，例如 webhook。
  - runtime plugin：不改程式碼就換 Store 或掛上自訂行為。
  - 多節點部署。目前定位是單一 instance。
  - 不停機的線上備份。
  - WebSocket 傳輸（優先度低）。

**可觀察的下一步**

用公司既有的身分提供者登入 Speclink server，不必另建帳號。其餘項目目前沒有可觀察的入口，也沒有排定先後；有進展時會先反映在專案能力狀態。
