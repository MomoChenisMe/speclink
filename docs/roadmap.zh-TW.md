# 專案路線圖

**繁體中文** · [English](roadmap.md)

這份文件收集 Speclink 還沒做完的方向。它寫方向，不寫排程，所以不會出現版本號或交付日期。

每條方向回答三件事：

- **要解決什麼**：這條方向存在的理由。
- **目前到哪**：今天已經做到的部分。是否可用以[專案能力狀態](product-status.zh-TW.md)為準。
- **可觀察的下一步**：做完之後，你可以親手確認的事。

這一版刻意延後的項目，連同今天的替代做法，列在專案能力狀態的[已知缺口](product-status.zh-TW.md#known-gaps)。其中屬於之後方向的，在下面各有落點。

## <a id="sdk"></a>SDK

**要解決什麼**

想在自己的程式裡驅動 Speclink 引擎的人，應該只要裝一個套件，不必準備一套編譯環境。裝好之後，呼叫方式也要好寫、出錯時要說得清楚。

**目前到哪**

- `npm install @speclink/engine` 就裝得起來，不需要 Rust 工具鏈。npm 上有五個平台的原生套件。
- SDK 這個工具箱裡有四樣：引擎、宿主套件、儲存接口的契約與合格測試。它們與 `dispatch` 的契約都有測試守著。用法見 [Node SDK](sdk-node.zh-TW.md)。
- 還沒做：
  - 型別化的 JS 方法。目前所有動詞都經 `dispatch` 以字串參數呼叫，回傳值也沒有個別的型別。
  - 契約版本握手：JS 套件與原生 binary 的版本不合時，直接拒絕而不是靜默出錯。
  - 儲存函式與掛鉤的逾時與取消。目前引擎會一直等到你的函式回來，要逾時得自己寫在函式裡。
  - Rust 使用者只能用 git 依賴 `speclink-core`；crates.io 上沒有這個 crate。

**可觀察的下一步**

用型別化的方法列出變更與讀取規格，編輯器能自動補完參數。JS 套件與原生 binary 版本不合時，錯誤訊息直接寫出兩邊的版本。

## <a id="own-client"></a>以引擎自建用戶端與內嵌宿主

**要解決什麼**

Speclink Desktop 只是引擎的其中一個前端，官方 server 只是示範與試用用的。同一套引擎，你應該也能拿來做自己的東西：貼合團隊流程的桌面 app、VS Code 擴充、內部網頁看板，或把引擎內嵌進自己的系統，用自己的帳號、登入、權限與資料庫。

**目前到哪**

- 規則只在 `speclink-core` 實作一次。
- 內嵌已經可用。宿主套件（`createHost`）替你處理每次呼叫的身分與範圍，以及兩個掛鉤：執行前可以拒絕，提交後只能旁觀。
- 儲存接口只有三個函式：列出、讀取、提交。你用自己的資料庫實作它們，再用套件裡的合格測試（`runStoreConformance`）檢查。
- 入口有兩個，共用同一個儲存與同一組掛鉤：
  - HTTP 入口（`host.handleRequest`）：你只掛一條路由，原版的 CLI 與 Speclink Desktop 就能連上來。
  - 呼叫入口（`host.dispatch`）：給你自己的 Agent 工具。
- 儲存接口的範例有三個，都用 Rust 寫：SQLite、PostgreSQL 與檔案系統。官方的示範用 server 就是用它們和同一套宿主套件組成的。見[儲存接口的範例](server-store-drivers.zh-TW.md)。
- [Client Protocol 正式規格](../speclink/specs/client-protocol/spec.md)定義跨用戶端的線上契約。[動詞與旗標契約](verb-contract.zh-TW.md)寫下每個動詞在本機專案與遠端專案的歸屬與輸出格式。
- 還沒做：
  - JavaScript 寫的儲存接口範例。目前用 Node 內嵌的人要對照 Rust 範例自己寫。
  - 多個宿主實例之間的推送事件。宿主套件預設只宣告輪詢；要推送，串流與跨實例的傳遞都得由宿主自己做。
  - 一份「從零做一個用戶端」的文件。
  - JS 版的遠端 HTTP 用戶端。目前只有 Rust 的 `speclink-remote`。
  - 可供第三方使用的 UI 元件與整合契約。`@speclink/ui` 目前是私有套件。

**可觀察的下一步**

用 Node 內嵌的人拿一個 JavaScript 寫的儲存接口範例，換成自己的資料庫就通過合格測試。只讀公開文件、不讀 Speclink 原始碼，就能做出一個最小用戶端：列出變更、讀一份規格、勾掉一個任務。做不出來的地方，就是還缺的文件或介面。

## <a id="remote"></a>遠端協作

**要解決什麼**

一個人用本機專案已經完整。多人共用一份正式規格、改用遠端專案時，還有幾段路沒鋪平。

**目前到哪**

- 遠端專案的 CLI 可用：`link`、`auth`、唯讀投影，絕大多數動詞兩邊都能用，包括 `plan`、前置宣告、`change rank` 與溯源。
- 登入有三種方式：瀏覽器登入、裝置登入與存取金鑰。技能由 Server 提供，連上之後執行 `speclink update` 取得。
- Speclink Desktop 可以開遠端專案的看板：瀏覽變更、勾任務、讀寫 artifact，看到建立者、認領人與 capability 清單；也能把本機專案遷移到 Server。
- 認領人由 Server 保存；認領到別人持有的變更會被拒絕，訊息寫出持有人。
- 審查與驗證的狀態、變更的分支與落地的 commit 都讀得到；`speclink change landed` 回報落地。
- 斷線時看板變成唯讀 snapshot，寫入一律被拒，重連後自動收斂。
- 還沒做：
  - 在 Speclink Desktop 勾遠端專案的任務時，回報動到的檔案（CLI 已經會）。
  - 認領的釋放與接手。
  - 遠端專案的手冊產生。目前只有導覽模式可用；規格基準（`baseline`）同樣只能在本機專案做。
  - 遠端專案的自訂產出流程。目前只能用內建的兩種。
  - CLI 的匯入與匯出動詞。目前搬專案要用 Speclink Desktop 或宿主自己的程式。
  - 把封存的討論記錄搬回來的動詞。
  - 寫入詞彙表的動詞。
  - 稽核歷史的查詢介面。每次提交都把是誰、用哪個命令交給儲存，但還沒有 API 或畫面可以查「誰在什麼時候用哪個指令改了什麼」。
  - 本機投影快取的清理：逾期清除、登出或切換專案時清除，以及只限本人讀取。目前投影已是唯讀，並排除在 Git 之外。
  - PM 到 RD 的交接關卡（核准後被改動就失效），以及 apply 時記下依據的規格版本。品質關卡與認領已涵蓋一部分，還要重新決定是否需要。

**可觀察的下一步**

在 Speclink Desktop 勾掉遠端專案的一個任務之後，查得到它動了哪些檔案，和在 CLI 上勾一樣。持有人離開之後，有辦法釋放或接手認領。在遠端專案也能產生手冊。

## <a id="agent-tools"></a>Agent 工具整合

**要解決什麼**

Speclink 主要透過生成的技能檔與 Agent 協作。技能檔是「把流程知識寫給模型讀」，不是「把能力當成工具給模型呼叫」。只有後者能讓 Agent 在對話中直接查規格、開變更、勾任務，不必請模型去跑 CLI。

**目前到哪**

- 技能這一側已經成熟：Claude Code 與 Codex 涵蓋每一站，見[完整 SDD 工作流](workflow.zh-TW.md)。其他 AI 工具可以用自訂工具描述子產生技能，見[設定說明](configuration.zh-TW.md)。
- Claude Code 外掛 `speclink-skills` 提供技能按鈕列與側邊面板。
- Herdr mod `speclink` 提供面板，並把側欄清單接上 Speclink。
- 工具這一側有了第一個入口：`@speclink/engine` 匯出一個通用的工具定義 `agentTool`。模型只填動詞的參數與 stdin；身分與範圍由宿主的程式從自己的 session 帶上，再呼叫 `host.dispatch`。模型不能自己帶入身分。見 [Node SDK](sdk-node.zh-TW.md#agent-tool)。
- 還沒做：
  - MCP adapter。目前要自己寫宿主的程式，才能把 Speclink 掛成工具。
  - 沒有 checkout 的 Agent 用不了需要 checkout 的動詞，例如 `drift`。

**可觀察的下一步**

在支援 MCP 的 Agent 工具裡加上 Speclink，直接以工具呼叫列出變更與讀取規格，不必自己寫宿主的程式。

## <a id="system"></a>系統整合

**要解決什麼**

Speclink 進到一間公司之後不會是孤島。帳號要接既有的身分系統，規格的變動要能通知別的工具，部署要跟著既有的維運方式走，規格也可能分散在好幾個 repo。

**目前到哪**

- 內嵌的宿主今天就能接自己的系統：帳號、登入與權限都是宿主的；要通知別的工具，在提交後掛鉤或自己的提交函式裡發。
- 示範用 server 的營運可用：安裝、帳號管理、存取金鑰、裝置登入、備份還原都有入口與端到端測試。
- 示範用 server 提供 SSE 事件串流（`/events`），用戶端可以即時收到變動。
- 還沒做：
  - 示範用 server 的企業 SSO（OIDC）。目前它只有自己管理的帳號。
  - 示範用 server 的對外通知，例如 webhook。
  - runtime plugin：不改程式碼就替示範用 server 換一種儲存或掛上自訂行為。
  - 多節點部署。目前示範用 server 只支援單一實例。
  - 不停機的線上備份。
  - 規格放在 checkout 之外的本機位置：`spec_dir` 的路徑規則。目前它不檢查絕對路徑與 `../`，行為未定義。
  - 唯讀引用另一套規格。
  - WebSocket 傳輸（優先度低）。

**可觀察的下一步**

用公司既有的身分提供者登入示範用 server，不必另建帳號。其餘項目目前沒有可觀察的入口，也沒有排定先後；有進展時會先反映在專案能力狀態。
