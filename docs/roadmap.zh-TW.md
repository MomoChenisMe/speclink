# Speclink 專案路線圖

**繁體中文** · [English](roadmap.md)

這份文件回答「Speclink 之後會往哪走」。它寫的是**方向**，不是排程。每條線只交代三件事：要解決什麼問題、目前走到哪裡，以及下一步做完之後你會看到什麼。這裡不會出現版本號或交付日期。

## How to read this / 這份路線圖怎麼讀

- **要解決什麼**：這條線存在的理由。沒有這段，方向就只是功能清單。
- **目前到哪**：今天已經能做到的部分，以[專案能力狀態](product-status.zh-TW.md)的判定為準。那份文件是「現在能不能用」的正典，本文不重複維護狀態。
- **可觀察的下一步**：做完之後你可以親手確認的事。例如一行指令跑得起來、一個入口出現，或一份文件從缺口變成可照著走的步驟。刻意寫成可觀察的樣子，這樣「有沒有進展」不必靠公告判斷。

本文寫的每一條，判斷基礎都是**目前實際做出來的東西**——已經在跑的程式碼、`openspec/specs/` 底下的正典規格，以及專案能力狀態的判定。

本文是**給使用者看的方向**，只回答「我在等的能力有沒有在路上」。要判斷某項能力今天能不能用，這裡不是入口——查專案能力狀態。

## SDK / SDK 發布

**要解決什麼**

想在自己的程式裡直接驅動 Speclink 引擎的人，現在得先有 Rust 工具鏈，自己建置 `crates/speclink-node`，再用路徑載入。對「寫個腳本把規格接進既有流程」這種需求來說，這個門檻太高。真正該裝的東西是一個套件，不是一套編譯環境。

**目前到哪**

N-API 綁定本身可用：Engine 與 Store bridge 已經接通，dispatch 契約也有測試守著。通路也接上了——release 管線每推一個 tag 就建置五平台、以該 tag 版號蓋章，並把 `@speclink/engine` 與五個平台子套件發布到 npm。差的只剩「跑過一次」：registry 上還沒有套件，所以 [Node SDK 文件](sdk-node.zh-TW.md)仍保留自 repo 建置作為替代路徑。Rust 使用者則已經可以直接依賴 `speclink-core` crate。

**可觀察的下一步**

首個帶 engine 的 release tag 推出之後，在一個全新的資料夾裡 `npm install @speclink/engine` 裝得起來，而且不需要本機有 Rust 工具鏈。屆時專案能力狀態的 Node SDK 一列也會改判。

## Build your own client / 以引擎自建客戶端

**要解決什麼**

Speclink 的桌面 app 只是**引擎的其中一個前端**，不是引擎本身。同一套 typed command／query／context 路徑，CLI 用、Server 用、Node 綁定也用。

既然如此，你應該也能拿它做出自己的東西：一個貼合團隊流程的桌面 app、一個 VS Code 擴充，或一個內部網頁看板。官方前端的取捨不該綁住你。

這條線與上一條共用同一個引擎面，但問的問題不同。SDK 那條問「裝不裝得起來」。這條問「裝起來之後，能不能只讀文件就做出自己的客戶端」。

**目前到哪**

引擎面已經是共用的。`speclink-core` 是唯一的規則實作。Host 負責組合認證、revision、交易與事件。[Client Protocol 正典](../openspec/specs/client-protocol/spec.md)定義跨客戶端的線上契約。[動詞與旗標契約](verb-contract.zh-TW.md)寫下動詞的模式歸屬與輸出保證。

缺的是「以第三方身分接上去」的完整路徑。目前的文件是寫給這個 repo 的維護者看的，還沒有一份「從零做一個客戶端」的文件，SDK 也還沒進 npm（見上一條）。

**可觀察的下一步**

只讀公開文件、不讀 Speclink 自己的原始碼，就能做出一個最小客戶端：列出變更、讀一份規格、勾掉一個任務。做得出來，代表引擎面的邊界說清楚了。做不出來，代表還缺文件或缺介面——那正是這條線要補的。

## Remote collaboration / 遠端協作

**要解決什麼**

一個人在自己 repo 裡用 Speclink 已經完整。多人共用一份規格正典則還沒走完。命令列與桌面看板現在都指得到遠端，剩下的是這條路上還沒鋪平的幾段。

**目前到哪**

遠端的命令列路徑可用。`link`、`auth` 與唯讀的 Context Projection 都有測試守著，絕大多數動詞也都有遠端臂；模式歸屬見[動詞與旗標契約](verb-contract.zh-TW.md)。Server 端的安裝、帳號、成員資格與備份還原也都可用。

桌面看板已能指向遠端：登入後在 chooser 選 Project 與 Repo，可選擇只讀規格或綁一個本機 checkout，開出來的看板和本地一樣能瀏覽 change、勾任務、讀寫 artifact。看板與詳情面板也直接從 server 看得到 change 的詮釋資料（建立者與開工歸屬）與 capability 清單，已轉成 change 的討論也標得出去向。遠端勾任務回報的 touched files 也已存進 Store，可經證據端點查回。

認領現在是玩真的。在共用 Store 上執行 `speclink claim`，認領人會寫進該 change 的 meta——跨重啟仍在、每個隊友都看得到；認領到別人持有的 change 會被拒絕，409 裡直接寫著持有人是誰。桌面看板的卡片顯示誰認領了，詳情面板也能直接認領（editor 以上）。

還沒鋪平的：桌面遠端勾任務本身還不會回報 touched files（只有 CLI 會）——這是目前刻意的取捨，沿「無新髒檔不新增記錄」的語意、不偽造證據；認領也還沒有釋放或搶佔的動詞，撞到別人的認領就停在 409。離線與衝突處理則已離開這份清單：斷線期間是唯讀 snapshot、寫入一律被拒到重連為止；看板對設定、退回提案、刪除與看板排序的版本衝突都有對應的呈現，剩下的（勾任務或搬移撞到過期版本時走一般錯誤訊息）面積很小，暫不立案。

**可觀察的下一步**

在桌面遠端看板勾掉一個任務之後，查得到它動了哪些檔案——就像在 CLI 上勾一樣。更遠一點：持有人離開後，認領有辦法釋放或接手。

## Agent tool integration / Agent 工具整合

**要解決什麼**

Speclink 目前透過生成的技能檔與 Agent 協作：Claude 用斜線指令，Codex 用 `$` 指令。這條路能走，但它做的是「把流程知識寫成文件給模型讀」，不是「把能力當成工具掛給模型呼叫」。

只有後者能讓 Agent 在對話中直接查規格、開變更、勾任務，不必每次重讀一整份技能說明。

**目前到哪**

生成技能這一側已經成熟。`propose`、`apply`、`ingest`、品質關卡、封存等站別都有對應技能，兩個 Agent 平台都涵蓋，見[完整 SDD 工作流](workflow.zh-TW.md)。工具側則還沒有可用入口：沒有可安裝的 Copilot 工具套件，也沒有 MCP adapter。

**可觀察的下一步**

在支援 MCP 的用戶端裡把 Speclink 掛成一個 server，然後直接以工具呼叫列出變更與讀取規格，不必請模型去跑 CLI。這一步做完，身分與權限的收口也要一起成立：工具呼叫走的是哪個帳號、能寫到哪個 store，都必須和 CLI 走同一套判定。

## System integration / 系統整合

**要解決什麼**

Speclink 進到一間公司之後不會是孤島。帳號要接既有的身分系統，規格的變動要能通知別的工具，部署要能跟著既有的維運方式走。目前這三件事都得靠人工橋接。

**目前到哪**

Server 本身的營運面已經可用：安裝、帳號管理、PAT 與 device 登入、備份還原都有入口與端到端測試。

但還缺三塊。身分僅限 server 自己管理的帳號，沒有企業 SSO。擴充只能改 codebase，沒有 runtime plugin 機制。部署定位是單一 instance，沒有 cluster 操作。備份目前也還需要維護窗口。

**可觀察的下一步**

以公司既有的身分提供者登入 Speclink server，不需要另外建一組帳號。再往後還有兩件事：不改 codebase 就能掛上自訂行為，以及多節點運行。兩者目前都還沒有可觀察的入口，也沒有排定先後。有了會先反映在專案能力狀態。
